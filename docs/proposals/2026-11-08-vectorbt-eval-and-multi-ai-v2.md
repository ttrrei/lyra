## 0. 结论先行（TL;DR）

**Q1 — vectorbt：不建议引入（核心与运行时都不要）。**
它的三个"卖点"（参数网格扫描、组合净值 / CAGR / Sharpe / HWM、组合优化）
**恰好是我们 R2 / R9 明确排除的目标**；我们保留的差异点（R4 执行合约、R5 报告口径）
它**都不建模**——用它的代价是：多一个信号表示层（YAML→SQL 之外再加 YAML→pandas 桥）、
68 个包（vs 我们核心 8 个）+ numba/llvmlite 这个 JIT C 运行时、以及被"组合指标"诱惑去违反 R9。
**不是"重复造轮子"，而是我们故意不造它负责的那些轮子**（参数扫描 / 账户净值 / 组合），
而它不负责的（我们的执行合约与报告口径）我们无论如何都要自己写。

**Q2 — 多 AI 并行：不需要新基建，R12 版本树本身就是并发原语。**
"同一方向、不同 AI 各按节奏、互不影响" = 版本树的**分支**天然隔离（每分支一个唯一文件 +
append-only 日志 + 只读对比）；"我要求时做跨 AI 对比 / 学习 / 整理" = 现成的
`lyra compare --siblings` + 判定段（人工 / 指定 AI 触发，不是后台自动，契合 R9 的"有界"边界）。
只需补 **4 个最小规则**（分支名唯一、日志原子追加、对比只读、隔离边界=方向），
**不引入分布式 / 多进程 / 锁服务**（R9 排除分布式 / 多进程；"互不干扰"主要靠 G1 唯一分支 → 唯一文件
的**数据分片**，文件锁仅为罕见重叠的兜底）。对 0004 的具体要求只有 3 条：**编译确定性**、
**廉价 `validate` 门禁**（让弱 AI 不烧 run）、**每合约输出**（compare 表要逐合约行）。

## Q1. vectorbt 取舍

### 1.1 实证（2026-11-08，隔离 venv，py3.12）

> 可复现：`python -m venv .vbt && .vbt/bin/pip install vectorbt && .vbt/bin/python probe.py`
> （probe 已跑完即删，不留痕迹；下列为实测输出摘要。）

| 维度 | 实测 | 对我们的含义 |
|---|---|---|
| 版本 / 环境 | vectorbt **1.2.0**，依赖 numpy **2.5.4**、pandas **3.1.1** | 与我们的数值栈兼容，装得上 |
| 依赖体量 | venv 共 **68** 个包（含 **numba 0.68.1 + llvmlite 0.50.0 + scipy + llvmlite**） | vs 我们核心 **8** 包（[pyproject.toml](../../pyproject.toml)）。numba 是 **JIT C 运行时**，正是 0003-D2 已标记的"无 wheel / C 构建 / ABI 断裂"风险类 |
| 数据模型 | `Portfolio.from_signals(df, entry, exit_, price=df['Close'])` 里 `df` 是 DataFrame → 被当作**多资产**，信号沿**所有列**广播；`total_return()` 返回 **Series（每资产一列）**而非标量 | vectorbt 的默认心智是"一次调用 = 多资产 × 多参数"，不是"一个标的、逐个跑、永不合成"——与我们 R9"永不合成 portfolio"相反，用它必须**逆着它的设计**逐标量隔离 |
| 招牌能力 | 一次调用扫 N×M 参数网格（RSI 窗口 × 阈值），`total_return` 形状 `(n_bars, n_params)` | 这就是 people 找 vectorbt 的**核心原因**——**参数扫描**。而 R2 **明令禁止参数扫描**（"参数固定…不做参数扫描（防 overfit）"）。它最方便的功能恰好是我们刻意删掉的 |
| 指标 | 原生计算 CAGR（`annualized_return()`）、Sharpe（`sharpe_ratio()`）、最大回撤（`max_drawdown()`） | 这些是 **R9 明确"不做"的账户级指标**。库自带 = 持续诱惑去违反 R9（moneta 正是栽在"外围过度工程"上） |
| 执行合约 | 提供 `sl_stop` / `tp_stop`（比例止损 / 止盈），**不建模**：每标的最多一笔、不 pyramiding、不重入、末 bar 排队入场作废、TP+SL 同根→亏损方优先、数据结束平仓、冲突多空→两关 | **R4 的边缘情形它一个都不建模**。用 vectorbt 跑 0005，等于要自己把这套执行合约在它的信号框架外重做一遍 |
| 收益模型 | `direction × (exit−entry)/entry − cost` 的 PnL 算术**能算**；但它的成本 / 融资 / 交易日口径与 R4 不一致 | 简单 PnL 算术可借，但"交易日融资（周末/节假日不计）/ 2% 触发器非净损上限 / 跳空可超 2%"这些 R4 细节它不管 |

**关键判断**：把"它做的"和"我们不要的"对齐，重叠的部分（PnL 算术、月度聚合、胜率、平均持有
bar 数）是**几百行 numpy over trades** 的量级；不重叠的部分（R4 执行合约、R5 报告口径、
因果性、past-only 编译）是**我们的核心差异点，它都不做**。也就是说，用它 = 为了省几百行
"商品级"代码，背上 68 个包 + numba + 一个会一直往 R9 方向拉我们的库，还得自己重写它不做的
难的部分。**净负。**

### 1.2 建议

1. **核心 / 运行时不引入 vectorbt**（不进 [pyproject.toml](../../pyproject.toml) 核心依赖，不进 R10 ≤15 核心包预算）。
2. **trade engine（0005）不用它**：R4 的执行合约（2% 触发器、跳空可超、TP+SL 亏损方优先、
   不重入、末 bar 作废、交易日融资）它都不建模，用它必须自建桥 + 重写合约，反而更复杂、更不"开源简单"。
3. **（可选、低优先）对照组**：如未来需要跨引擎交叉验证，最多把它当**测试期对照组**
   （像 [pandas-ta-classic](../decisions/0003-feature-builder.md) / tulipy 那样放 `[control]`），
   且**只验证简单 PnL 算术**、明确标注"不覆盖 R4 边缘情形"——因为它 sl_stop/tp_stop 与我们 2%
   触发器语义不同，拿它当执行合约的验证器会**误导**（简单用例过、边缘用例恰好是我们最该对的）。
   **默认不做**，避免又开一个"对照组"口子。
4. **一句话回应用户**："没必要重复造轮子"——对。但我们不是要造它那种轮子（参数扫描 / 组合 /
   账户净值）；那些是我们**故意不造**的（R2/R9）。它不造的那种轮子（我们的执行合约 / 报告）
   才是要造的，省不了。

### 1.3 如果用户仍想引入（风险清单，供裁决参考）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 依赖膨胀 | 68 包 + numba/llvmlite（JIT C 运行时） | 只能 `[control]` 可选、绝不进核心；运行时 import 需白名单 |
| R9 诱惑 | 自带 CAGR/Sharpe/HWM/组合，易被"顺手"算进报告 | 报告层显式禁用其 portfolio 指标，只允许逐标的 PnL |
| 合约不匹配 | sl_stop/tp_stop ≠ R4 的 2% 触发器 + 跳空 + 亏损方优先 | 明确"仅作信号→PnL 算术对照"，不碰执行合约 |
| 维护面 | 多一个第三方引擎 = 多一个版本锁定 + 升级面 | 固定版本、CI 锁；不升级除非有需求 |
| 心智漂移 | "一次多资产多参数"的默认模型与 R9 相反 | 文档明确"逐标量隔离、永不合成"，用它的 API 时要逆着设计写 |

### 1.4 优势（如实记录，避免"只写缺点"的偏差）

- **装得上、跑得快**：1.2.0 在当前栈干净安装；numba 让批量 PnL 快。
- **多资产 / 多参数 API 成熟**：做"组合级"研究时省事（但我们不做组合级）。
- **文档 / 生态**：上手快、例子多。
- **这些优势都落在"组合 / 参数扫描 / 账户净值"上**——即我们 R2/R9 明确不做的区域，
  所以对"逐标的、参数固定、无组合、无账户净值"的 Lyra，优势几乎不兑现。

## Q2. 多 AI（不同能力）并行搜索

### 2.1 需求澄清（把用户的话映射到 R12）

| 用户原话 | 映射 |
|---|---|
| "同一个方向，不同的 AI 能够按照自己的节奏进行" | 同一 **direction 文件夹**下，多个 AI 各自在**不同分支**（`vNNa` / `vNNb`）迭代，各写各的 |
| "互相不影响" | 写操作**按分支隔离**（唯一分支文件 + 唯一 run 目录）；日志**追加不覆盖**；对比**只读** |
| "不同智商的 AI 都能参与" | 框架保证**循环足够简单 + 上下文自包含**（读 1 → 写 1 → 跑 1 → 记 1），弱 AI 也能可靠完成；`validate` 在烧 run 前拦截错 YAML |
| "除非我要求时，让某个 AI 对方向内不同 AI 的演进做对比 / 学习 / 整理" | **用户触发**的跨 AI 评审：`lyra compare --siblings` 出并排摘要 → 指定 AI / 用户写**判定段**（continue / prune / cross）；这是**有界（同方向内）+ 人发起**的，契合 R9"有界迭代"边界，**非**后台自主 |

**核心洞察**：R12 的版本树（direction=隔离单元，branch=候选，lessons=append-only 日志，
compare=只读对比）**本身就是并发原语**。"多 AI 并行"不是要新造一个调度系统，而是要保证
这套既有结构在"多个进程同时写一个方向文件夹"时不互相踩踏。

### 2.2 现状盘点（哪些已支持 / 哪些是 gap）

| 操作 | 现状 | 多 AI 并发下 |
|---|---|---|
| 写分支 `vNNa.yaml` | 每分支一个**唯一文件**（R12 命名：代数+字母后缀+`_n`） | ✅ 天然隔离——只要分支名唯一（**G1**） |
| 写 run 结果 `runs/<dir>/<branch>/…` | 每分支唯一 run 目录 | ✅ 天然隔离（0005/0006 落） |
| 追加 `lessons.md` / `hypothesis.md` | I17 已定为 **append-only + 超集校验** | ⚠️ 需**原子追加**（**G2**），否则两进程同时 append 可能交错 / 丢行 |
| `lyra compare --siblings` | 读兄弟分支 run 摘要 → 只读 | ✅ 只读，无写冲突 |
| 跨 AI 对比 / 学习 / 整理（用户触发） | = compare + 判定段 + 可选 merge | ✅ 已是模型；需**显式触发**（**G4**），不自动 |
| 跨方向写 | R12 未定义 | 需**明确禁止**（**G4** 隔离边界=方向） |

### 2.3 四个最小规则（不引入分布式 / 锁服务 / 多进程基础设施）

> R9 明确排除"分布式 / 多进程 / 云原生"。本设计**不违反** R9，理由是：
> 多 AI 协作是**用户驱动的工作流**（用户在多个会话/时点各自推进），**不是**一个要
> **常驻协调的并发系统**。框架**不提供任何多进程 / 分布式 / 锁服务机制**；"互不干扰"
> 完全靠**数据模型分片**（G1 分支名唯一 → 唯一文件）实现，即**默认单写者友好**：
> 即便两个 AI 在**不同时刻**碰同一方向文件夹，也不会互相破坏。文件锁**仅作为**
> "极罕见的真重叠"的 belt-and-braces 兜底，**不是**并发引擎，**不**构成 R9 所指的多进程。

- **G1 分支名唯一（fail-fast）**：`lyra new-version --branch <id>` 若 `<id>` 已被占用，
  **立即报错**（沿用 0003 F5"注册名冲突→报错、不覆盖、不 `_2` 后缀"的先例），让 AI 换一个。
  **不做自动分配、不做重试队列**——保持弱 AI 也能用的简单语义。**这是互不干扰的主要机制**
  （唯一分支 → 唯一文件，天然无写冲突）。
- **G2 日志原子追加（best-effort 兜底）**：`lessons.md` / `hypothesis.md` 的"一段"是
  **原子单位**；正常情形是**单写者顺序 append**，**无需锁**；仅当**极罕见**出现真重叠时，
  工具**可**加本地 advisory 文件锁（`fcntl`/`flock`）防交错——**这是兜底，不是并发机制**；
  push 时 I17 超集校验最终兜底（漏追加会被 push 拒绝，不静默丢）。
- **G3 上下文自包含（弱 AI 平权）**：`lyra context <dir>` 输出单文件上下文包（R12 已定义），
  任何能力的 AI 读同一份、走同一个循环（读 1 → 写 1 → 跑 1 → 记 1），I8 护栏（只动策略层）+
  `validate` 前置拦截 = 弱 AI 不烧 run、不改坏特征。**框架的职责就是"保证循环简单到弱 AI 能可靠完成"**
  ——这正是"不同智商都能参与"的落地方式，而非给不同 AI 造不同流程。
- **G4 隔离边界 = 方向**：写操作**只在本方向文件夹内**；跨方向**只读引用**（分支 `driven_by_lesson`
  可引用他方向 lessons，但**不自动 import**）；跨 AI 的"对比 / 学习 / 整理"是**用户显式触发**的
  `compare`+判定，**永不后台自动**。这样"互不影响"由**数据模型分区**保证，而非运行时协调。

### 2.4 对 0004 编译器的具体要求（只有 3 条，都是 0004 职责）

| # | 要求 | 理由 | 落点 |
|---|---|---|---|
| C1 | **编译确定性**：`compile(yaml, feature_snapshot, git_commit)` 是**纯函数**——同样输入必得同样 SQL，无墙钟 / 随机 / 进程内状态 | 多个 AI 并行跑同一分支时必须结果可复现、可比（compare 的前提）；否则"对比 / 学习"没有意义 | 0004 不变量 + 测试（两次编译 SQL 逐字节一致） |
| C2 | **廉价 `validate`**：`lyra validate` 在**任何 run 之前**拦截特征名 / 参数 / 时间算子 / 右值错误，精确到行 + 报错文案对 LLM 友好 | 弱 AI 最浪费时间的就是"写了个坏 YAML 才跑一次 run 才发现"；把拦截前移到 validate，弱 AI 迭代成本骤降 | 0004 CLI（HLD §2.3 已列 `lyra validate`） |
| C3 | **每合约输出契约**：编译产物是**逐合约**的 past-only SQL（对单个特征宽表视图，如 `features_5m` / `features_1h`），**不**产"合成 portfolio" | compare 表要**逐合约行**（R5）；R9 永不合成。逐合约也是多 AI 逐分支可比的基础 | 0004 方案 §3.1 + 不变量 |

### 2.5 风险与优势

**优势**：
- **零新基建**：并发隔离由 R12 版本树的**数据分区**提供，不引入调度器 / 锁服务 / 消息队列。
- **弱 AI 平权**：同一套简单循环 + 自包含上下文 + I8/validate 护栏，能力弱的 AI 也能可靠出活。
- **人保留控制权**：跨 AI 对比 / 学习 / 整理是**用户触发**的有界操作，契合 R9"有界迭代"边界，不滑向"无人值守批量生成"。
- **可审计**：每分支 `driven_by_lesson` + `parent`/`parents` + 写者（AI 声明）→ 任意一次演进可回溯是谁、为何。

**风险（及缓解）**：
| 风险 | 缓解 |
|---|---|
| 两 AI 同时 append `lessons.md` 交错 / 丢行 | G2 本地文件锁 + 原子追加 + I17 超集校验兜底 |
| 分支名撞车 | G1 fail-fast 报错（F5 先例），不自动分配 |
| 弱 AI 写出坏策略烧大量 run | G3 简单循环 + C2 廉价 validate 前置 + I8 护栏 |
| "多 AI"被误解成"分布式 / 多进程系统" | 明确：**用户驱动的工作流 + 数据模型分片**（G1 唯一分支 → 唯一文件），**非**常驻并发系统、非分布式（R9 不违反）；文件锁仅为罕见重叠的兜底；文档写清 |
| 跨 AI"学习"越界成"自主生成" | 对比 / 学习 / 整理**仅用户触发** + 仅同方向内（G4），守住 R9 边界 |

### 2.6 建议

1. **不新建并发子系统**。把上面 **4 条最小规则（G1–G4）**写进 0004/0006 的决策文档不变量，
   把 **3 条编译器要求（C1–C3）**写进 0004 不变量。
2. **多 AI 并发是"既有版本树 + 几个本地文件纪律"的自然结果**，不需要新的架构层。
3. 若未来真的需要"多个 AI 争一个方向"的协调，再考虑（届时才评估是否需要更强机制）；
   **现在不做**（YAGNI，且 R9 排除分布式）。
