| 编号 | 审查主张 | 判定 | 处置 |

| A1 | **纯 Python clean 在 12 GB / 48M 行不可行**：`csv.DictReader` 逐行解析 + Python dict 去重，实测卡死（>30 min 无进展）；而 bronze 落盘要几分钟——**fixture 上的"正确"代码在真实规模下完全不可用** | **合理（致命，真缺陷）** | ✅ 重写 `clean.py`：DuckDB `read_csv(union_by_name)` + `ROW_NUMBER` 去重 + `COPY` 落盘（moneta `load_data.py` 同款，独立重实现）。48M 行 clean ≈ 15 min，可跑通 |
| A2 | **I22 误判"1m 有缺口"为非法**：真实 1m 数据有 **73 万处** bar 缺失（周末/休市/无成交），原始 `LAG` 逐对检查把它们全判成 `I22 violation` → 真实数据**必崩**。fixture 全是连续 1m，测不到 | **合理（真 bug，真实数据暴露）** | ✅ 精确化 I22 判据为"**原生分辨率 = 1m**"（每标的**最小**间隔 ≈1m，59–61s），**缺口合法**。验证：21 标的 min gap 全 = 1.00 min → 0 违规；新测试 `test_aggregate_gapped_1m_accepted` 证明缺口 1m 被接受、5m 原生分辨率被拒 |

| A4 | **`read_parquet(?)` 不接受 `PosixPath` 绑定参数**：本 DuckDB 版 `execute(..., [Path])` 抛 `NotImplementedException: Unable to transform PosixPath`——fixture 小路径恰好没触发，真实 pipeline 计数查询直接崩 | **合理（真 bug，版本相关）** | ✅ 所有 `read_parquet(?)` 绑定参数统一 `str(path)` |
| A5 | **`COPY` 落盘行序不稳定**：无 `ORDER BY` 时 Parquet 行序随并行度漂移 → I18"逐行一致"的**顺序**承诺被破坏（两次跑行内容同但次序可能不同） | **合理（真缺陷）** | ✅ `COPY (SELECT ... ORDER BY instrument, time)`；测试 `test_aggregate_deterministic` 两次跑逐行相等 |

| A7 | **时间列为 `TIMESTAMPTZ` 而非 naive `TIMESTAMP`**：源带 `Z`（UTC），DuckDB 自动推断为带时区类型。这是**正确**的（数据确实带时区信息），但 0002 文档原写"naive UTC" | 契约需精确化 | ✅ 0002 I21/bronze schema 说明补充：bronze/5m/1h 的 `time` 实为 **TIMESTAMPTZ(UTC)**（源 `Z` 推断），下游读需 pytz（A3）；`n_bars` 语义不变 |

## 关键修正细节

### A1 + A2（本批次核心）

**A1** 是"fixture 测不到的致命项"的教科书案例。批次 04 的 clean 在 70 根 1m 的 fixture 上"全绿"，
但在 4884 万行上 `csv.DictReader` 逐行 Python 解析直接不可行（实测卡死）。
重写后用 DuckDB 单条 `COPY` 完成过滤 + 去重 + 落盘，48M 行 ≈ 15 min，
**且内存平稳**（DuckDB 流式，不物化全表）。

**A2** 更微妙：它不是"代码错"，而是**契约在真实数据下不成立**。原始 I22
（"相邻两根 bar 必隔 1m"）隐含假设源是**连续** 1m——但真实市场数据有
周末、休市、无成交分钟，必然缺 bar。真实数据 731,078 处 ≥5m 缺口证明
这一点。修正后的判据（**最小**间隔 ≈1m）区分了"1m 分辨率带缺口"（合法）
与"5m/1h 原生分辨率"（该拒），这才是 I22 的本意。

### 验证记录（真实数据）

- `lyra pull` 端到端成功：raw 163 zips → 183 CSVs → **bronze 48,846,896 行** → **5m 9,986,167 bars** → **1h 838,272 bars**（15m51s）
- 21 标的，min inter-bar gap 全 = **1.00 min**（I22 原生分辨率判据 → 0 违规）
- 5m `n_bars` 直方图：峰值 n_bars=5（9,350,811 bars）+ 部分窗口 n_bars=1..4（缺口，合计 ~63 万）——**I21 部分窗口标记工作正常**
- XAU_USD 时间跨度 **2020-01-02 → 2026-11-06**（6 年完整）
- 三份 Parquet schema 正确：bronze 15 列（含 bid/ask）、5m/1h 8 列（含 `n_bars`），`time` 均为 `TIMESTAMPTZ`
- fixture 套件 **24 passed** + pyflakes clean（真实数据修复未破坏 fixture 覆盖）

## 结论

0002 代码在**真实数据端到端**上**通过**批次 05 审查。本轮的价值是把 4 个

A3 pytz 未声明、A4 Path 绑定、A5 COPY 行序），并精确化 1 项契约（A7

"fixture 全绿"到"真实可用"的关键跨越。可进入 commit。
