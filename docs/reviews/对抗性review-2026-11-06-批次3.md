## 审查明细

### A1 派生缓存陈旧漏洞（合理，真缺陷 → 已修）

**攻击面**：幂等只定义在 raw 下载层（I20）。派生层（`raw_csv` →
`all_data.parquet` → `ohlcv_5m/1h`）没有定义重跑语义。场景：
① 用户删了 `all_data.parquet` 想重建 → `lyra pull` 因 raw 全幂等跳过
下载，若 clean 也"输出已存在即跳过" → 用户永远拿不回 bronze；
② 更隐蔽：`all_data.parquet` 损坏（磁盘/进程被杀）→ 同上，且**不会
报错**，静默丢失。

**定案（0002 v0.3 §3.1/§3.3）**：**只有 raw 下载层做幂等跳过；
clean 与 aggregate 每次 `lyra pull` 恒重算并覆盖输出**。理由：
bronze/5m/1h 全部是 raw 的确定性函数（I18），重算成本 ≈ 一次
DuckDB 扫描，而"输出已存在即跳过"引入的语义漏洞远大于收益；
"raw 未变 → 输出必逐行相同"由 I18 直接保证。

### A2 bronze schema 未显式定义（合理 → 已修）

**攻击面**：0002 v0.2 只说"必需列 `instrument,time,is_complete` +
可选 mid/bid/ask"，bronze 输出列集合是**隐式**的。0003 feature
builder 的输入契约必须确定。且 `is_complete` 是 clean 的过滤条件，
留在 bronze 里是死列。

**定案（0002 v0.3 §3.3）**：bronze 1m Parquet 的 schema =
**输入 CSV 列的并集**，其中：
- 必有：`instrument, time, volume, mid_o, mid_h, mid_l, mid_c`；
- 依源：`bid_*, ask_*`（moneta 数据源有则保留）；
- **不含** `is_complete`（clean 已消费，bronze 内该行恒为 true，
  无信息量）。
