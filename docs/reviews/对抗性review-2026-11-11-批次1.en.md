## Scope and conclusion

This review covers the user's listed changes: final rejection of M3, the O18 deep-dive archive and closure, bilingual synchronization of 0008 §3.1, and the `.gitignore` `scratch/` rule. I compared ACTION_LOG, HLD, requirements, the 0007/0008 decision documents, open-questions, and the previous 0007 review, and checked the local Lyra/Nova data artifacts plus the ignored `scratch/barcov/one/*.json`. This turn records findings only; it changes no code, configuration, or ruling, and does not run the test suite.

**Conclusion: the user's rulings remain valid (do not implement M3; use Lyra's bar set for O18), but the current document set still contains contradictions that prevent a clear sign-off.** I found three high-priority and four medium-priority issues. The core arithmetic `179,550 + 4,359 = 183,909` and the per-symbol attribution identity for all 21 instruments are reproducible; the problems are the report's interpretation of 2019 inputs, the raw-row delta, and its claim of “100% aggregation attribution,” which conflict with the data and with the report's own figures.

Severity: **High** means active wording can mislead implementation about a rejected capability or undermine confidence in the data cause/counts. **Medium** means bilingual consistency, evidence boundaries, or historical status needs clarification.

## High-priority findings

### H1 — M3 is rejected, but active design text still promises an SDK fallback

**Evidence**

- 0007 D4 still says `auth_file` is optional immediately before the final rejection note. The two statements contradict each other in the same decision section, in both languages.
- 0007 B5 still says to use the OCI SDK when PAR is read-only and calls this 0007's largest implementation uncertainty. C1 still says OCI SDK signing is required and that D3/D4 leave an SDK exit. These are not marked as superseded historical notes, in either language.
- Active HLD §2.5, requirements R7, and `config/config_example.yml` still present `~/.lyra/credentials` / OCI auth as an optional route, contrary to the HLD dependency table and the final M3 ruling.
- The previous batch-2 review's original acceptance summary still says “13 accepted / 1 held / 0 rejected,” while its 2026-11-11 follow-up says the final outcome is “13 accepted / 1 rejected / 0 held.” The follow-up is dated, but the old summary is not marked as superseded.

**Impact**: a reader may still treat the SDK or `auth_file` as a fallback if R10 fails; the sample config implies that supplying credentials is supported. The user ruled this capability out, and R10 should validate only the PAR path.

**Recommendation**: make D4's current state PAR-only; remove SDK-fallback wording from B5/C1 or mark it explicitly as a pre-2026-11-11 assumption superseded by the M3 ruling; sync HLD, R7, and the config example. Historical revision entries may remain, but the later final state must clearly supersede them. Mark the previous review's old count as a pre-ruling snapshot.

### H2 — The 2019 and 1m row-count attribution cannot be reproduced from current data

**Independent checks**

- Read-only query of the current Lyra catalog: `bronze` has **48,846,896** rows; its earliest time is in the 2020-01-01 UTC window; rows before `2020-01-01T00:00:00Z` = **0**; rows after `2026-10-23T21:00:00Z` = **258,445**.
- The current Nova 1m Parquet set has **48,588,451** rows. The Lyra/Nova total difference is **258,445**, exactly the number of Lyra 1m rows after the Nova cutoff.
- Lyra's raw subdirectories do contain 42 2019-11/12 CSV files totaling **943,529** rows, but these rows are not in the current `bronze` table. This contradicts report §1.1's statement that the 2019 rows entered bronze.
- Report §1.2 says bronze exceeds Nova by **125,815** rows; using the reported bronze total and the current Nova Parquet total, the difference is **258,445**, not 125,815. The Nova input-row count minus the reported duplicate-removal count also does not derive the stated Lyra/Nova difference.
- §3 attributes the 4,359 1h tail bars to “the 2026 tail + 2019 monthly files,” then immediately says the 2019 files did not enter 1h. Based on the report's tail definition and per-symbol JSON, all 4,359 are Lyra bars after Nova's cutoff; they cannot also include a 2019 contribution.

**Impact**: the report gives mutually incompatible accounts of whether 2019 data entered bronze, the size of the raw-row delta, and what the 4,359 bars represent. The claim that all extra raw data has been accounted for is therefore not established.

**Recommendation**: rewrite §1.1–§1.2 and §3 from reproducible SQL results. Separately list 2019 CSVs present in raw, rows actually loaded into bronze, and rows included in 1h. Keep the 1h attribution identity, remove the unsupported 2019 attribution, and explain or correct the original `125,815` calculation.

### H3 — “100% caused by aggregation rules” conflicts with the report's 2.4% tail

The report's own 21-row table and JSON can be reproduced:

- Lyra 1h total **838,272**, Nova **654,363**, difference **183,909**.
- Partial hours **179,550**; Lyra-only 1h tail **4,359**. Each instrument satisfies `Δ = partial + tail`, with **21/21** zero-residual identities; shared-window 1m row counts also match for **21/21** instruments.
- `179,550 / 183,909 = 97.63%`; the report's rounded 97.6% is correct. The remaining **2.37%** is a data-window difference, not an aggregation-rule difference.

Yet the report TL;DR, English §3.1 of the 0008 migration doc, and several open-questions/HLD/ACTION_LOG summaries say “100% of the difference comes from aggregation rules.” Open-questions also says “filter + data-window tail,” so these statements disagree.

**Impact**: readers may mistake a data-window difference for aggregation behavior, and conflate “no raw re-pull needed” with “the data windows must be aligned.”

**Recommendation**: standardize on “total difference 183,909 = 179,550 (97.6%, partial-hour filter) + 4,359 (2.4%, window tail).” Explain separately that local-timezone display accounts for the 21/24-bars-per-day observation; it is not another source of the total-count difference.

## Medium-priority findings

### M1 — The Chinese migration doc still presents O18's pre-closure ruling

In `docs/decisions/0008-migration-and-regression.md` §3.1, the data-layer section still says the raw sources are unconfirmed, asks for a data-owner ruling, and repeats the old “Lyra 21 bars/day, Nova 24 bars/day, 115 SPX bars/week” narrative. The conclusion in the same section says O18 is closed. The English §3.1 has been replaced with the SHA256, partial-filter, and final-ruling account. The default Chinese document and English version therefore do not state the same ruling.

**Recommendation**: sync the Chinese §3.1 data-layer section to the current English ruling. Keep the old conclusion only in a dated history entry and mark it as superseded by the O18 deep dive.

### M2 — The archived O18 report has no English pair

`docs/decisions/0008-bar-coverage-analysis.md` exists, but `0008-bar-coverage-analysis.en.md` does not. This breaks the project requirement that documents ship as Chinese/English pairs, and leaves the key calculations linked from English §3.1 without a complete English review path.

**Recommendation**: add a full English pair and keep every number, scope statement, and attribution aligned with the Chinese version.

### M3 — Claims of complete raw coverage and “closer to consensus” exceed the evidence

I verified that the 21 instrument CSVs have matching SHA256 values on both sides. I also checked 43,103 instrument-date observations in the JSON: Lyra's daily bar count was never below Nova's. This supports “same source bytes” and “Lyra has at least as many bars per UTC day as Nova in the report's date range.” But identical raw bytes on both sides cannot show that both datasets lack a market hour that is missing from both. The report gives no market-open calendar or external availability benchmark. Its “consensus hours per day” table for FX, indices, and other groups also provides no source or reproducible rule.

**Recommendation**: narrow “raw has no missing full hours” to “no inter-side raw-hour difference was found”; label “closer to consensus” as an internal observation/judgment or document the per-category source and calculation. The user's “Lyra is canonical” ruling does not depend on this stronger claim of external completeness.

### M4 — The `scratch/` archive is correctly ignored, but its evidence does not ship with the repository

The `.gitignore` `scratch/` rule works, so the referenced calculation JSON and script do not enter Git. That fits the boundary for temporary artifacts. The tradeoff is that repository readers cannot inspect the referenced JSON, script, or sampling detail, and the report has no English pair.

**Recommendation**: retain complete query/field definitions or archive the generating script through a stable review artifact; do not describe ignored scratch output as permanently reproducible repository evidence. There is no need to undo the `scratch/` ignore rule.

## Checks that passed and limits

- **The user's M3 ruling is clear**: reject the SDK fallback; use PAR for R10. “Held” in dated revision history records the state at that time and may remain if the later ruling clearly supersedes it.
- **The core bar-count identity is correct**: across all 21 instruments, `lyra_1h = nova_1h + partial + tail`; 179,550 + 4,359 = 183,909; partial bars are 97.6% of the difference.
- **Raw SHA256 check passed**: the 21 top-level per-instrument CSVs match between Nova and Lyra; `scratch/` is ignored by Git.
- **Timezone claim scope**: local JSON supports Lyra having no fewer daily bars than Nova across 43,103 instrument-date observations; this comparison over the included window does not prove complete shared raw coverage.
- I did not rerun the full test suite: this review targets documents and existing data evidence, with no program change.

## Recommended disposition

Resolve H1–H3 and M1–M2 first, then use the corrected bilingual documents for 0007 R10 / 0008 sign-off. M3–M4 improve evidence boundaries and archive transparency; they do not overturn the user's Lyra-bar ruling or require another raw-data download.
