## Key corrections

### A1 (this batch's core: preventing "looks like success")

The **necessity** of the three layers: Parquet is an "append row-groups + write footer at the end" format.
The most likely corruption from an interruption is — **footer written, but an
earlier row-group's page data is corrupt / a page is missing**. In that case
`SELECT COUNT(*)` (via footer metadata) **does not error** and returns the
"correct" count; only a genuine per-row-group decompression exposes it.
So "footer correct + COUNT correct" is **not enough** to prove the data is
uncorrupted — a **full row-group decompression scan** (each row-group triggers
page decoding) is required.
Measured: 484 of 484 row groups (395 + 82 + 7) **all** decoded successfully,
rows scanned match the footer exactly → **no silent corruption**.
A final cut on the raw layer: 163/163 zips match the remote PAR per-object by
**both md5 and size** (md5 rules out the extreme "same size, different content"
case).

### A2 + A3 (the user ask, landed)

The user explicitly wants "DuckDB as metadata / external-table catalog". The key
to landing it is **separating "data" from "metadata"**:

* **Data**: the bronze / 5m / 1h **Parquet files** (I18 single source of truth,
  the 0007 push target).
* **Metadata**: `catalog.duckdb` (274 KB), holding only three
  `CREATE VIEW ... AS SELECT * FROM read_parquet('…')` statements.

Downstream (0003 feature builder / 0005 trade engine) just `SELECT ... FROM
bronze` — a **stable named entry point**, no path to remember, no re-glob, and
column order is defined by the Parquet file itself (I18). If the catalog breaks,
delete it and `upsert_views` rebuilds it — **zero data risk**.
This is exactly the "efficient, manageable, extensible" form the user asked for.

### A6 (honest efficiency bound)

A2/A3 are not "zero memory" magic: the VIEW removes the full-bronze copy, but
aggregate's **grouping working set** (`time_bucket` hash table + `ARRAY_AGG`
sort buffer) peaks ≈9.5 GB at 48M rows. This is the inherent form of DuckDB
aggregation, **not a bug, and not removable by streaming** (unless rewritten as
a pure external / sharded aggregation). The docs must state this honestly, or
0003 on a larger feature surface will wrongly assume "memory is free".
