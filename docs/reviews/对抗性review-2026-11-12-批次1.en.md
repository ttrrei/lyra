# Independent Adversarial Review of 0009 Polish (2026-11-12 Batch 1)

> **中文**: [0009 Polish 独立对抗性审查](./对抗性review-2026-11-12-批次1.md)

## Scope and conclusion

I independently checked the 0009 decision document, implementation, tests, README, Python/lock/CI configuration, and cross-checked requirements R10/R12, HLD §8, and ACTION_LOG. The review attacked multi-track isolation, run comparability, feature-generation publication, doctor acceptance gates, and clean-environment installation.

**Conclusion: the main 0009 features have landed, but the current implementation and documentation do not support the claim that all D1–D11 are complete as specified and the project can proceed directly to 0010.** I found **5 high-priority (P1) and 4 medium-priority (P2) findings**. Multi-track data leakage, false comparability across data, interrupted multi-file feature publication without a consumer gate, doctor success with missing OCI slots, and README installation failure were confirmed from code paths or isolated probes.

No runtime code was changed and no OCI writes or real-bucket R10 acceptance were performed. The full suite reports **324 passed**, and `pyflakes lyra tests` passes; those green checks do not cover the adversarial cases below.

## High-priority findings

### H1 (P1) — Tracks in the same direction still share branch files, and context includes runs from other tracks

**Contract**: requirements R12 says each track independently owns its candidate YAMLs, lessons, and run attribution; different AIs in the same direction should evolve at their own pace.

**Implementation and reproduction**:

- `new_version()` writes candidates to `strategies/<direction>/<branch>.yaml`, without a track path. Duplicate detection also checks this direction-level file. Once track `alpha` creates `v02a`, track `beta` cannot create its own `v02a`; the global duplicate check rejects it.
- For each active branch, `render_context()` calls `_runs_for_branch(workspace, direction, branch)`. This lookup has no `track_id` parameter or filter. Although `run_meta.json` stores the track, the lookup returns all runs for that direction and branch across tracks.
- In an isolated temporary workspace, `alpha` created `strategies/trend/v02a.yaml`; `beta` was rejected when creating the same branch. After adding one run for each track with the same direction and branch, `_runs_for_branch()` returned both runs.

**Impact**: AIs cannot independently create candidates under the same branch identity within their own tracks. If a branch is used by multiple tracks, context and comparison can mix their evidence. The required “no mutual interference” property is not enforced by the storage layout and queries.

**Recommendation**: Implement the track-owned candidate files described by R12 and pass/filter `track_id` in single-track workflows such as context and compare. Cross-track synthesis should continue to read the research scope explicitly requested by the user and name its participating tracks; it must not leak into a single-track context implicitly. Define migration/compatibility for existing direction-level YAMLs, then add regression cases proving same-named branches can exist across tracks and runs never leak between them.

### H2 (P1) — `compare` does not use D3's `data_digest + feature_version` comparability rule

0009 D3 and §2.2 define comparability as matching `data_digest` and `feature_version`, with an incomparable marker at run level.

The runner uses `data_digest` in `run_id`, but does not write it to `metrics.json` or `manifest.json`; `metrics.json` also does not contain `feature_version`. `_runs_for_branch()` only carries `feature_snapshot_id` into workflow results, and `compare_siblings()` checks whether all non-empty snapshot IDs are identical and returns one overall `comparable` boolean. It neither compares the two fields defined by D3 nor marks individual runs.

Consequently, runs with the same feature snapshot but different underlying data identities can still be reported as `comparable=true`; runs with different `feature_version` are also not checked independently. The existing `test_d3_compare_marks_incomparable_across_generations` only covers different snapshot IDs, not identical snapshots with different data digests or versions.

**Recommendation**: Persist `data_digest` and `feature_version` in readable run identity artifacts. Have compare read and evaluate them within a track, marking each run/group. Legacy runs missing either field should be explicitly unknown/incomparable; a shared snapshot ID must not imply comparability.

### H3 (P1) — Feature publication is not an atomic generation switch, and runs do not enforce the generation gate

`run_features()` stages files first, but the publication phase prunes stale files, then deletes each old target and renames each new file one by one. It writes `_generation.json` only after all files have been replaced. If the publication loop fails or the process exits midway, the target directory can contain a mix of old and new files while the old manifest still describes the previous generation. `_write_generation()` also overwrites the manifest directly rather than atomically replacing it.

The existing `test_atomic_publish_failure_keeps_previous_generation` injects failure during the build phase, before publication starts; it does not cover a failed rename of the second or later file. A second gap is that `validate_generation()` is called at runtime only by `lyra doctor`: the `lyra features` command does not call it as D4 specifies, and `lyra run` does not validate before reading features. Even if an interrupted publish is detected, consumers can still read a mixed directory.

**Impact**: D4's guarantee that an interrupted publish preserves the previous complete generation and its fail-closed gate are not implemented. The generation digest in a run ID may describe the manifest while DuckDB reads mixed-generation files.

**Recommendation**: Publish immutable generation directories behind one atomic pointer/directory swap, or implement verifiable backup and rollback. Atomically replace the manifest last. Make `lyra run` fail closed before reading features, and inject failures during prune, replacement, and manifest publication in regression tests.

### H4 (P1) — Doctor returns exit 0 when three OCI slots are missing, contrary to D10's hard-failure rule

D10 lists a parseable config with all four OCI slots as a hard-failure condition. In the implementation, only a missing `data_par_url` fails through `oci_from_dict()`; missing `features_par_url`, `strategies_par_url`, or `runs_par_url` are warnings.

I ran `lyra doctor` with a temporary config containing only `data_par_url`. It returned **`DOCTOR OK: 0 failures, 4 warning(s)` and exit 0** (the fourth warning was the missing catalog). This is a reproduced acceptance-gate mismatch, not an inference.

**Impact**: Doctor reports success for a configuration that cannot perform all OCI sync/backup operations. This conflicts with D10, requirements R10's hard-failure rule for environment/configuration problems, and #110's “0 hard failures” claim.

**Recommendation**: Make the three missing slots hard failures as D10 specifies. If the product instead intends them to be optional at 0009, revise D10/R10 first and state what a successful doctor result means; the implementation must not silently downgrade the rule.

### H5 (P1) — README installation fails in a clean environment at the editable-install step

The README sequence creates a venv, installs `requirements.lock`, then runs:

```sh
.venv/bin/pip install -e . --no-deps --no-build-isolation
```

`pyproject.toml` uses the `setuptools.build_meta` backend and requires `setuptools>=68`; however, neither `requirements.lock` nor the package allowlist in `scripts/make_lock.sh` includes setuptools. I reproduced the README sequence in a temporary Python 3.12 venv: `pip install -r requirements.lock` succeeded, but the editable install above **failed with exit 2**, reporting `ModuleNotFoundError: No module named 'setuptools'`.

**Impact**: The documented clean-environment installation does not work. CI did not catch it because it runs tests directly from the checkout root without installing the Lyra package.

**Recommendation**: Add the build backend to the locked installation path, or enable pip build isolation and declare the build requirements correctly. CI should verify the documented installation sequence, not only run tests from the source tree.

## Medium-priority findings

### M1 (P2) — Doctor's Python policy and core dependency checks lag behind the declared support surface

`pyproject.toml` now pins `>=3.12,<3.13`, but doctor still uses `(3,11)` through `(3,13)` and prints `>=3.11,<3.13`; it therefore reports Python 3.11 as PASS. The hard-import list also omits NumPy (present in the lock and required at runtime, but not directly declared in pyproject) and TA-Lib (declared in pyproject). If either is unavailable, this check does not fail; a compile-smoke failure is only a warning.

**Recommendation**: Use one Python support range across doctor, pyproject, CI, and README. Check all actual core runtime imports as hard failures and add tests rejecting 3.11 and missing NumPy/TA-Lib.

### M2 (P2) — 0009 acceptance and stage records are not aligned with the final implementation

- All eight checkboxes in §4 of `0009-polish.md` and `.en.md` remain unchecked, including R10 sign-off, full-suite tests, and doctor.
- The 0009 row in HLD §8 still says **2026-11-11 and 323 tests**, while #110 records 2026-11-12 and 324 tests.
- The detailed #110 row in ACTION_LOG still says pyproject `>=3.11,<3.13` and CI `3.11+3.12`, unlike the current pyproject and workflow, which pin Python 3.12 only. The state summary has already been updated to 3.12.

**Impact**: Readers cannot trace the actual 0009 completion state from its acceptance checklist and central log; historical and final implementation claims are mixed together.

**Recommendation**: After resolving this review, refresh the 0009 checklist, HLD §8 row, and bilingual ACTION_LOG #110 status/revision note. If append-only history prevents rewriting #110, append a correction.

### M3 (P2) — Doctor's command name, installed smoke strategy, and operational hints do not match the CLI

- The real entry point is `lyra doctor`; `pyproject.toml` registers only `lyra`, not a standalone `lyra-doctor` executable. The 0009 decision and requirements R10 use `lyra-doctor`.
- 0009 §3a says compile smoke has a built-in RSI fallback. `_default_example_strategy()` actually only searches `strategies/examples/*/v01.yaml` under the repository root and raises if none is found; the exception becomes a warning. The strategies directory is not packaged with the Python module, so a non-checkout install is expected to keep this warning.
- Doctor's catalog warning tells the user to run `lyra build`, but `lyra --help` has no `build` command. The existing commands include `pull`, `clean`, `aggregate`, and `catalog`.

**Recommendation**: Standardize the official command name; package the smoke strategy or add the claimed real fallback; and make warnings point only to existing CLI commands.

### M4 (P2) — Failure to write the run identity sidecar does not fail the run, and workflow can then lose it

`lyra run` catches any `_write_run_meta()` exception, prints a warning, and still returns success. Workflow relies on direction/branch from `run_meta.json` when it exists; without it, legacy fallback requires an exact branch match against metrics `spec_id`. A formal strategy's spec ID is usually not its `vNN` branch name, so that run may not appear in context/compare.

**Recommendation**: Treat run identity as a required output of the strategy-search loop: fail the CLI if the sidecar cannot be written, or recover the same identity reliably from the manifest. Add sidecar write-failure and corruption tests.

## Verified items and evidence limits

- Full hypothesis snapshots and drift annotations are implemented in `create_track`/`render_context`; the counter identity token is included in run identity.
- `pytest -q`: **324 passed**; `pyflakes lyra tests` passes. This verifies the current test set, not the untested fault and identity combinations in H1–H5.
- Direct CLI checks confirmed the command is `lyra doctor`; neither `lyra build` nor a standalone `lyra-doctor` exists.
- No OCI writes or real-bucket acceptance were performed; no code/tests were changed. The interrupted-publication finding comes from the publication control flow and the current test injection point; I did not deliberately interrupt a publish in the real market-data directory.

## Recommended disposition order

Fix H1–H5 first, then address M1–M4 and refresh the bilingual acceptance record. Re-run the full suite, clean-environment installation, and doctor negative probes before moving to 0010. The green current suite does not waive these findings.
