# 0004 Compiler 与 0005 Trade Engine 联合对抗性审查（2026-11-08 批次 4）

> **范围**：针对 HLD §8 第 4 阶段（0004 YAML Compiler）与第 5 阶段（0005 Trade Engine），审查已实施的代码模块（`lyra/strategy_schema.py`、`lyra/compiler.py`、`lyra/trade_engine.py`、`lyra/cli.py`）、决策文档（`docs/decisions/0004-yaml-compiler.md` 与 `docs/decisions/0005-trade-engine.md`）以及二者之间的接口装配与时序契约。
>
> **方式**：静态代码路径追踪、数据流契约交叉推导、构造最小边界输入与 Python/DuckDB 实操验证。本报告为只读红队审查，记录缺陷、证据与最小复现，不直接修改实现或测试。

---

## 结论

0004 编译器与 0005 交易状态机各自在独立单体测试中表现良好（全仓 186 passed），并且在 past-only 窗口、强制 2% 止损、亏损方优先（stop before target）以及状态机方向隔离等基础不变量上落实了防护。

然而，对 0004 与 0005 进行端到端数据流与边界渗透审查时，发现了 **2 项 Critical（致命阻断）**、**3 项 Major（重大契约违背/静默失效）** 和 **3 项 Minor（边界偏差）** 缺陷：

1. **0004 产物无法直接驱动 0005**：`CompiledPlan.sql` 仅 SELECT 6 个信号与标识列，完全剥离了 `mid_o/mid_h/mid_l/mid_c` 价格列；而 `trade_engine.simulate()` 无条件强制索取 OHLC 列，二者直连即抛 `KeyError: 'mid_o'`，缺少端到端装配契约。
2. **融资天数覆盖参数 `trading_days: float` 架构设计失效**：`simulate()` 接收单个标量 `trading_days`，在多笔交易的回测中会将同一天数无差别赋予所有开闭仓；且调用方在 `simulate()` 运行前无法预知各笔交易的进出场时刻，导致 R4/O15 交易日融资在多交易场景下无法工作。
3. **特征与特征比较绕过类型校验**：批次 2 对 H1（STATE 序数 vs 布尔）的修复仅对常量分支生效（`if is_const`）；当右侧为特征列时完全缺失类型校验，导致 `close > psar_bullish` 产生 DuckDB `BinderException` 运行时崩溃，`sma_alignment_6_24 == psar_bullish` 在 DuckDB 中静默判定 `0 = FALSE` 为真。
4. **`_quote()` 真实报价列名硬编码拼接错误**：代码将前缀与传入的 `"mid_o"` 直接拼接生成 `"bid_mid_o"` / `"ask_mid_o"` 幽灵列，永远无法命中 0002 bronze/silver 标准列 `bid_o` / `ask_o`，真实点差报价被完全无视。
5. **`exit.feature` 白名单检查遗漏**：未对 `exit.feature` 子字典做键白名单限制，拼写错误（如 `whenn`）导致退出规则被静默丢弃并置换为 `FALSE AS exit_long`，无任何报错。

## 缺陷清单与证据

### Critical（致命）

#### C1 — 0004 `CompiledPlan.sql` 缺失 OHLC 价格列，直接接入 0005 `simulate()` 抛 `KeyError: 'mid_o'`

- **位置**：`lyra/compiler.py:290-298` 与 `lyra/trade_engine.py:114-118, 198, 213-215`
- **证据**：
  `compiler.py` 的 `_build_select` 生成的 SQL 为：
  ```sql
  SELECT "instrument" AS instrument, "time" AS time,
         <entry_long> AS entry_long, <entry_short> AS entry_short,
         <exit_long> AS exit_long, <exit_short> AS exit_short
  FROM "features_5m" ORDER BY instrument, time
  ```
  该 SQL 只投射了 6 列，未投射 `mid_o`, `mid_h`, `mid_l`, `mid_c`。
  但 `lyra/trade_engine.py:198` 与 `:213-215` 在执行开平仓与止损判定时，无条件读取 `bar["mid_o"]`、`bar["mid_l"]`、`bar["mid_h"]`。
  若直接将 DuckDB 执行 `plan.sql` 的结果（字典列表或 DataFrame）传入 `simulate(plan, rows)`，首根 K 线即崩溃于 `KeyError: 'mid_o'`。
- **影响**：0004 的编译产物与 0005 的消费入口契约脱节。现有单测中 `test_compiler.py` 只测 DuckDB 跑 SQL、`test_trade_engine.py` 只用手写合成带 OHLC 的 dict，没有任何一条测试跑通 `compile -> duckdb execute -> simulate` 的真实端到端链路。
- **最小复现**：
  ```python
  spec = parse_yaml(VALID_YAML, reg)
  plan = compile_strategy(spec, reg)
  rows = duckdb.connect().execute(plan.sql, plan.params).fetchdf().to_dict(orient="records")
  simulate(plan, rows)  # KeyError: 'mid_o'
  ```

#### C2 — `simulate()` 的 `trading_days: float | None` 标量设计无法支持多笔交易回测，且调用方无法前置感知

- **位置**：`lyra/trade_engine.py:106-111, 171` 与 `docs/decisions/0005-trade-engine.md:122, 131-136`
- **证据**：
  在 #84 的落地中，`simulate()` 增加参数 `trading_days: float | None = None`，并在 `_finish()` 中使用：
  `days = _day_count(position["time"], timestamp, trading_days)`。
  但 `simulate()` 面向的是单标的完整时间序列（例如 1 年或 5 年），通常产生数十至数百笔交易。将 `trading_days` 作为整个 `simulate()` 调用的单个标量参数传入，会导致该序列产生的所有交易被强制扣除**完全相同**的融资天数（无论该笔持仓 1 小时还是 3 周）。
  此外，0006 调用方在将 `bars` 传入 `simulate()` 之前，根本无法得知策略会在哪根 K 线进场、哪根 K 线出场（止盈止损由引擎内部撮合触发），因此调用方物理上无法在模拟前计算好每笔交易的交易日并传给 `simulate()`。
  若不传（保留默认 `None`），代码回退到 `(exit - entry).total_seconds() / 86400`（自然日），直接违反 R4 与已关闭的 O15（周末与节假日继续被扣费）。
- **影响**：R4/O15 的交易日融资规则在真实回测流程中处于死锁状态：传参则所有交易融资天数被单标量污染，不传则回退为自然日违例。
- **最小复现**：
  在一串包含两笔交易的序列中（交易 A 历时 1 个交易日，交易 B 历时 10 个交易日），传入 `trading_days=5`。两笔交易的 `cost_return` 均被强制按 5 天计算；交易 A 被多扣 4 天，交易 B 被少扣 5 天。

### Major（重大）

#### M1 — 特征与特征比较（feature-vs-feature）完全绕过类型检查，导致 DuckDB 运行时 BinderException 或语义错误

- **位置**：`lyra/strategy_schema.py:427-464`
- **证据**：
  在批次 2 处置 H1 时，对 STATE 序数与布尔值的类型检查只包裹在 `if is_const:` 分支内。
  当 RHS 是特征列时（`is_const = False`），`_parse_value_rhs` 仅返回 `(False, None, col)`，其类型 `_kind` 被完全丢弃，代码后续未对两侧列类型做任何兼容性判断。
  - **用例 A（DuckDB 运行时崩溃）**：策略写 `feature: close, op: gt, value: psar_bullish`（浮点数与布尔列做大小比较）。YAML 解析成功，SQL 编译出 `("mid_c" > "psar_bullish")`。DuckDB 执行时直接崩溃：`_duckdb.BinderException: Cannot compare values of type DOUBLE and type BOOLEAN - an explicit cast is required`。
  - **用例 B（布尔常量与数值比较）**：策略写 `feature: close, op: eq, value: true`。由于 `close` 的 `kind` 为 None/VALUE，跳过 `if left_kind is FeatureKind.STATE`，编译出 `("mid_c" = ?)` 绑定 `True`。DuckDB 将 `True` 转为 `1.0`，静默比较价格是否等于 1.0。
  - **用例 C（跨状态特征语义错误）**：策略写 `feature: sma_alignment_6_24, op: eq, value: psar_bullish`（序数状态 {-1,0,1} 比较布尔状态）。编译出 `("sma_alignment_6_24" = "psar_bullish")`。当均线走平为中性（0）且 PSAR 非多头（FALSE）时，DuckDB 判定 `0 = FALSE` 为 TRUE，错误开仓。
- **影响**：破坏了 0004 宣称的“validate 廉价快速失败”契约；合法通过 validate 的策略会在执行阶段因类型不兼容直接抛 SQL 异常，或者产生错误的信号语义。
- **最小复现**：
  ```python
  spec = parse_yaml("""
  version: 1
  id: type_err
  timeframe_minutes: 5
  direction: long
  entry:
    long:
      feature: close
      op: gt
      value: psar_bullish
  exit:
    stop_loss_pct: 0.02
  """, reg)
  plan = compile_strategy(spec, reg)  # 成功编译，毫无警告
  duckdb.connect().execute(plan.sql)  # 抛 _duckdb.BinderException
  ```

#### M2 — `_quote()` 生成幽灵列名 `"bid_mid_o"`，真实市场点差列被静默弃用

- **位置**：`lyra/trade_engine.py:97, 198, 213-215, 266`
- **证据**：
  `_quote` 实现如下：
  ```python
  def _quote(bar: Mapping[str, Any], direction: int, point: str, spread_bps: float | None) -> float:
      name = ("bid_" if direction == 1 else "ask_") + point
      if bar.get(name) is not None:
          return float(bar[name])
      base = float(bar[point])
      if spread_bps:
          return base * (1 - direction * spread_bps / 20000)
      return base
  ```
  在 `simulate()` 中调用时，传入的 `point` 为 `"mid_o"`, `"mid_l"`, `"mid_h"`, `"mid_c"`。
  字符串拼接生成的 `name` 变成了 `"bid_mid_o"` 与 `"ask_mid_o"`。
  然而在 0002 bronze/silver 数据集（见 `lyra/clean.py:33` 与 `lyra/oanda.py:57-60`）中，真实的买卖价列名为 `bid_o`, `ask_o`, `bid_h`, `ask_h`, `bid_l`, `ask_l`, `bid_c`, `ask_c`。
  由于 `bar.get("bid_mid_o")` 恒为 `None`，无论输入数据是否包含真实 bid/ask 报价，引擎**永远无法读取真实报价**，只能无条件走 `base = float(bar[point])` 并应用合成 `spread_bps`。
- **影响**：若回测使用带真实 bid/ask 的优质数据源，真实流动性与点差成本被完全丢弃，降级为粗糙的固定基点合成估算。
- **最小复现**：
  ```python
  bar = {"mid_o": 1.0, "bid_o": 0.9990, "ask_o": 1.0010}
  # direction=1 (想要 bid_o)
  quoted = _quote(bar, direction=1, point="mid_o", spread_bps=0)
  assert quoted == 1.0  # 本应得到 0.9990，实际得到 1.0
  ```

#### M3 — `exit.feature` 未作键白名单与类型校验，拼写错误导致平仓条件静默丢失

- **位置**：`lyra/strategy_schema.py:706-728`
- **证据**：
  在 `_normalize_exit_and_execution` 中：
  ```python
  legacy_when = None
  feature_block = exit_raw.get("feature")
  if isinstance(feature_block, dict) and "when" in feature_block:
      legacy_when = feature_block["when"]
  ```
  该分支在提取 `legacy_when` 时，没有对 `feature_block` 调用 `_reject_unknown_keys`。
  若用户编写时出现拼写错误（例如 `exit.feature.whenn: {feature: close, op: lt, value: open}`），`"when" in feature_block` 为 False，`legacy_when` 保持 `None`。
  函数既不报错也不告警，直接将 `exit_long` 和 `exit_short` 置为 None，并最终在 SQL 中编译为 `FALSE AS exit_long, FALSE AS exit_short`。
  同理，若用户输入 `exit.feature: "invalid_string"`，也直接被静默吞没。
- **影响**：违反决策 0004 严格 schema（fail-fast）承诺，用户的指标平仓条件被完全抹去，策略在无感知的情况下变成“永不主动平仓”。
- **最小复现**：
  ```yaml
  exit:
    stop_loss_pct: 0.02
    feature:
      whenn:
        feature: close
        op: lt
        value: open
  ```
  解析并通过校验，编译生成的 SQL 为 `FALSE AS exit_long`，平仓规则完全消失。

### Minor（次要）

#### m1 — 数据末端强制平仓（end_of_data）时间戳使用 bar 开盘时间而非收盘时间

- **位置**：`lyra/trade_engine.py:263-268`
- **证据**：
  ```python
  if position is not None and bars:
      last = bars[-1]
      raw_close = _quote(last, position["direction"], "mid_c", spread)
      _finish(last, raw_close, "end_of_data", last["time"], "bar_close")
  ```
  此处平仓价使用的是该 bar 的收盘价 `mid_c`，但传入的时间戳参数为 `last["time"]`（即最后一根 bar 的开盘时刻）。
  若某笔交易恰好在最后一根 bar 的开盘入场并在收盘被 end_of_data 强平，其 `entry_time == exit_time == last["time"]`，导致经历一整根 K 线持仓的实际耗时被计算为 0 秒，融资扣费为 0。
- **影响**：最后一根 K 线的持仓时间戳失真，与 `Trade.exit_time` 的文档定义（`bar open/close time of the exit fill`）在物理时间上偏差了 1 个 bar 跨度。

#### m2 — `simulate()` 缺乏标的唯一性检查（single-instrument assertion）

- **位置**：`lyra/trade_engine.py:106-269`
- **证据**：
  `simulate()` 假设调用方已按标的切分。若调用方不慎传入了多标的混合的 K 线序列（如按时间排序的全局 DataFrame），引擎不会报错，而是会在标的 A 的开仓状态下，被标的 B 的 exit 信号平仓，并生成一笔开仓价为 A、平仓价与标的名为 B 的怪异混合交易。
- **影响**：缺乏防御性断言；应在函数入口或首根 K 线记录 `instrument`，遇到异标的数据立即 fail-closed。

#### m3 — 开盘跳空触及止盈以 target 限价成交，保守估计剥离了开盘有利跳空收益

- **位置**：`lyra/trade_engine.py:228-234`, `docs/decisions/0005-trade-engine.md:144, 157`
- **证据**：
  当开盘跳空越过止盈线时（例如多头进场 100，止盈 102，次日直接高开在 105）：
  代码执行 `_finish(bar, target, "take_profit", bar["time"], "bar_open")`，强制按 102 结算，放弃了开盘集合竞价的 300 bps 溢价。
  相反，跳空跌破止损时（`stop_at_open`），代码却以 `opening` 真实开盘价全额吃下恶性跳空亏损。
  虽然这是忠实继承 Nova 的保守限价设计，但在真实交易所撮合中，处于价内的止盈单以开盘价成交（获得正向滑点/价格改善）。该不对称性在策略评估中对跳空型策略带来系统性惩罚，应在决策文档中明确标注为“极其保守的单边惩罚假设”。

## 已核对且符合预期的部分

- **时序与防未来数据**：`compiler.py` 的 SQL 生成严格限制为 `lag` 与 `ROWS BETWEEN N-1 PRECEDING AND CURRENT ROW`，没有任何 `lead`、未来 join 或全局排序前视。
- **强制 2% 止损不可推翻**：`strategy_schema.py` 严格校验 `stop_loss_pct` 只能为 `0.02`，不支持通过 YAML 关闭或放大止损。
- **同 Bar 止损止盈竞合**：`stop_inside` 优先于 `target_inside` 判定，严格满足 I4 不变量（亏损方优先）。
- **无反向翻转/加仓**：持仓期间忽略反向开仓信号，同一 Bar 平仓后禁止同 Bar 再次开仓，满足单标的一笔与无加仓约束。
- **确定性哈希**：`plan_hash` 将 SQL、参数、特征集与目录快照做哈希，不含运行期时间与进程状态，输出稳定可重现。

## 最小复现与回归脚本

可在项目虚拟环境中运行下述脚本一次性验证本文涉及的 4 项关键缺陷（C1、C2、M1、M2）：

```python
import duckdb
from lyra.features import core_registry
from lyra.strategy_schema import parse_yaml
from lyra.compiler import compile_strategy
from lyra.trade_engine import simulate, _quote

reg = core_registry()

# 1. 验证 C1: plan.sql 与 simulate() 字段脱节
yaml_c1 = """
version: 1
id: test_c1
timeframe_minutes: 5
direction: long
entry:
  long:
    feature: close
    op: gt
    value: open
exit:
  stop_loss_pct: 0.02
"""
plan = compile_strategy(parse_yaml(yaml_c1, reg), reg)
con = duckdb.connect()
con.execute("""
CREATE TABLE features_5m (
    instrument VARCHAR, time TIMESTAMP,
    mid_o DOUBLE, mid_h DOUBLE, mid_l DOUBLE, mid_c DOUBLE
);
INSERT INTO features_5m VALUES ('X', '2026-01-01 00:00:00', 1.0, 1.1, 0.9, 1.05);
""")
sql_rows = con.execute(plan.sql, plan.params).fetchdf().to_dict(orient="records")
try:
    simulate(plan, sql_rows)
except KeyError as e:
    print("[C1 验证成功] simulate 抛出预期的 KeyError:", e)

# 2. 验证 M1: feature-vs-feature 类型穿透
yaml_m1 = """
version: 1
id: test_m1
timeframe_minutes: 5
direction: long
entry:
  long:
    feature: close
    op: gt
    value: psar_bullish
exit:
  stop_loss_pct: 0.02
"""
plan_m1 = compile_strategy(parse_yaml(yaml_m1, reg), reg)
try:
    con.execute(plan_m1.sql)
except duckdb.BinderException as e:
    print("[M1 验证成功] DuckDB 抛出类型比较异常:", type(e).__name__)

# 3. 验证 M2: _quote 幽灵列
bar_m2 = {"mid_o": 1.0, "bid_o": 0.9990, "ask_o": 1.0010}
quoted = _quote(bar_m2, direction=1, point="mid_o", spread_bps=0)
assert quoted == 1.0, "M2 幽灵列应导致 fallback 到 1.0"
print("[M2 验证成功] _quote 成功忽略真实 bid_o 报价")
```

## 处置建议

1. **解决 C1（统一信号与行情数据流）**：
   - 修改 `_build_select`，在 SQL 输出中一并投影行情列：`"mid_o" AS mid_o, "mid_h" AS mid_h, "mid_l" AS mid_l, "mid_c" AS mid_c`（若存在 bid/ask 则一并带出）。
   - 使 `plan.sql` 执行后直接生成 `simulate()` 所需的完整 `bars` 结构，消除任何二次在内存中做慢速 Join 的需求。
2. **重构 C2（融资天数计算契约）**：
   - 移除 `simulate(plan, bars, trading_days=...)` 中的单标量参数。
   - 改为在 `Trade` 输出时仅保留 `entry_time`、`exit_time` 与 `bars_held`；在 0006 runner 阶段根据持仓区间日历批量或逐笔结算 `cost_return` 与 `net_return`；或者向 `simulate()` 注入交易日日历检查回调/集合。
3. **修复 M1（完善比较左/右侧类型检查）**：
   - 在 `_parse_expr` 中，当 RHS 为特征列时，同时获取其 `FeatureKind` 与 `unit`；
   - 严禁数值（VALUE）与布尔/事件（STATE/EVENT）做大小比对；
   - 严禁序数状态与布尔状态直接做相等比对；
   - 严禁布尔常量（true/false）用于数值类特征（VALUE）。
4. **修复 M2（修正 `_quote` 列名提取）**：
   - 在 `_quote` 中，若 `point.startswith("mid_")`，截取点名后缀 `p = point[4:]`（即 `o/h/l/c`）；
   - 正确拼接 `bid_{p}` 与 `ask_{p}`。
5. **修复 M3（`exit.feature` 严格白名单）**：
   - 校验 `exit.feature` 必须为 dict 且只允许存在 `when` 键；对内部表达式严格递归校验，拒绝未知字段。
