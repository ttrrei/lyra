# M3 与 O18 文档裁决独立检验 + 对抗性检验（2026-11-11 批次1）

> **English**: [Independent and Adversarial Review of M3 and O18 Documentation Rulings](./对抗性review-2026-11-11-批次1.en.md)

## 范围与结论

审查用户列出的 M3 终态拒绝、O18 深挖归档与关闭、0008 §3.1 双语同步，以及 `.gitignore` 的 `scratch/` 规则。对照 ACTION_LOG、HLD、requirements、0007/0008 决策稿、open-questions、上一批 0007 review，并对照仓外的 Lyra/Nova 数据产物与被忽略的 `scratch/barcov/one/*.json`。本轮仅审查并写报告，没有改代码、配置或裁决，也未运行测试套件。

**结论：用户裁决本身保持有效（M3 不实现；O18 以 Lyra bar 集为准），但当前文档包仍有阻止清晰签收的矛盾。** 找到 3 项高优先级问题和 4 项中优先级问题。核心数字 `179,550 + 4,359 = 183,909` 及 21 个标的逐项归因恒等式可复核；错误在于报告对 2019 输入、原始行数差额和“100% 聚合归因”的解释与数据及自身数字冲突。

严重度：**高**表示活动文案会让实施者误解已裁决能力，或让数据根因/数量结论不可信；**中**表示双语、证据边界或历史状态仍不够清楚。

## 高优先级发现

### H1 — M3 已拒绝，但活动设计文字仍保留 SDK fallback

**证据**

- 0007 D4 在最终拒绝注之前仍写 `auth_file` 可选；后面的终态注又明确说不实现，形成同一决策段内的自相矛盾。中英文版都有。
- 0007 的 B5 仍说只读 PAR 时改走 OCI SDK、这是 0007 最大实现不确定点；C1 仍写“必须走 OCI SDK 签名”，处置仍说 D3/D4 留有 SDK 出口。它们没有被标成已废弃的历史记录，中英文版都存在。
- 活动的 HLD §2.5、requirements R7 和 `config/config_example.yml` 仍把 `~/.lyra/credentials` / OCI auth 描述为可选路径；这与 HLD 依赖表及 M3 终态相反。
- 11-10 批次2 review 的原始验收总结仍写“13 accepted / 1 held / 0 rejected”，而 11-11 尾注写最终为“13 accepted / 1 rejected / 0 held”。尾注有日期，但旧总结没有标记为被取代。

**影响**：读者仍可能把 SDK 或 `auth_file` 当作 R10 失败时可启用的备援；示例配置会暗示填入凭证能生效。用户已裁决不实现此能力，R10 应只验 PAR 路径。

**建议**：将 D4 当前状态改为只支持 PAR；把 B5/C1 中的 SDK fallback 文字删除或明确标成“2026-11-11 前的历史假设，已由 M3 裁决取代”；同步 HLD、R7、config example。历史修订日志可保留，但需让后续终态清楚覆盖旧状态；上一批 review 的旧计数应标为裁决前快照。

### H2 — 2019 与 1m 行数归因无法通过当前数据复现

**独立复核**

- 对当前 Lyra catalog 执行只读查询：`bronze` 共 **48,846,896** 行，最早时间为 2020-01-01 UTC 窗口，`time < 2020-01-01T00:00:00Z` 为 **0** 行；`2026-10-23T21:00:00Z` 之后有 **258,445** 行。
- 当前 Nova 1m parquet 为 **48,588,451** 行。Lyra/Nova 总量差为 **258,445**，恰等于 Lyra cutoff 之后的 1m 行数。
- Lyra raw 子目录中确有 42 个 2019-11/12 CSV，共 **943,529** 行；这些行当前未进入 `bronze`。这与报告 §1.1“2019 行进入 bronze”不符。
- 报告 §1.2 写 bronze 比 Nova 多 **125,815** 行；按同段报出的 bronze 总量和当前 Nova parquet 总量，差额为 **258,445**，不是 125,815。报告所列 Nova 输入行数减去所列去重数，也不能推出其声称的 Lyra/Nova 差额。
- §3 把 4,359 根 1h 尾部 bar 归为“2026 尾部 + 2019 月文件”，但紧接着又说 2019 月文件未进入 1h。按报告自身的尾部定义和 per-symbol JSON，4,359 根全部是 Lyra 超过 Nova 截止时间的尾部，不能再包含 2019 贡献。

**影响**：同一份报告对 2019 数据是否进入 bronze、1m 总差额的大小以及 4,359 的构成给出互斥解释；因此“所有额外原始数据已解释”的说法目前不成立。

**建议**：以可复现 SQL 查询结果为准重写 §1.1–§1.2 与 §3；分别列明 raw CSV 存在、实际纳入 bronze、进入 1h 的行数/范围。保留 1h 归因恒等式，但删掉不能成立的 2019 归因，并解释原 `125,815` 计算口径或更正。

### H3 — “差异 100% 来自聚合规则”与报告的 2.4% 尾部不一致

报告自身的 21 行表格与 JSON 可复核：

- Lyra 1h 总数 **838,272**，Nova **654,363**，差额 **183,909**。
- partial 小时 **179,550**；Lyra-only 1h 尾部 **4,359**；逐标的均满足 `Δ = partial + tail`，**21/21** 无残差；两侧 shared-window 1m 行数比较也为 **21/21 相等**。
- `179,550 / 183,909 = 97.63%`，报告四舍五入为 97.6% 正确；其余 **2.37%** 是时间窗口差异，不是聚合规则。

但报告 TL;DR、0008 migration 英文 §3.1、open-questions 的归纳句以及 HLD/ACTION_LOG 总结多处写“差异 100% 来自聚合规则”。open-questions 同时又写了“过滤器 + 数据窗口尾部”，这些口径彼此不一致。

**影响**：审计读者会把时间窗口差异误当成聚合行为；“重拉 raw 无需”与“必须先对齐窗口”也被混为一谈。

**建议**：统一写成“总差额 183,909 = 179,550（97.6%，过滤 partial）+ 4,359（2.4%，窗口尾部）”；单独说明本地时区展示解释的是 21/24 根/日现象，不是 bar 总差额的第三个数值来源。

## 中优先级发现

### M1 — 中文迁移稿仍保留 O18 已关闭前的裁决状态

`docs/decisions/0008-migration-and-regression.md` §3.1 仍称 raw 来源未确认、等待 data owner 裁决，并重复“Lyra 21 根/日、Nova 24 根/日、SPX 每周 115 根”等旧叙述；同一节结论段却称 O18 已关闭。英文 §3.1 已替换为 SHA256、partial 过滤和最终裁决说明。默认中文文档与英文版不是相同裁决。

**建议**：将中文 §3.1 数据层段同步到英文当前裁决；旧结论仅保留在带日期的历史记录中，并标明已被 O18 深挖取代。

### M2 — O18 归档报告缺少英文配对

存在 `docs/decisions/0008-bar-coverage-analysis.md`，但没有 `0008-bar-coverage-analysis.en.md`。这违反项目“每份文档中英成对”的约定，也使英文 §3.1 指向的关键计算报告无法在英文文档链中完整审阅。

**建议**：补齐完整英文配对，并保持数字、范围、因果归属与中文版本逐项一致。

### M3 — “raw 无整点小时缺失”与“更贴近共识”超出当前证据

我核实了报告声称的 21/21 原始 CSV SHA256 一致；也从 JSON 检查了 43,103 个标的-日期观测，未发现 Lyra 当日 bar 数小于 Nova。这能支持“两边输入相同”和“报告窗口内 UTC 逐日 Lyra 不少于 Nova”。但同一批 raw 字节相等不能证明两边都没有共同缺失的市场小时；报告也未给出市场开放日历或外部可用性基准。FX、指数等“共识每日报价小时数”表同样没有标注来源或可复核规则。

**建议**：将“raw 不缺整点小时”收窄为“两侧未发现相互差异的 raw 小时”；将“更接近共识”标为项目内观察/判断，或补充逐类别的基准来源与算法。用户的“以 Lyra 为准”裁决无需依赖这个更强的外部完整性主张。

### M4 — `scratch/` 归档可用，但复核材料不随仓库提供

`.gitignore` 的 `scratch/` 规则已生效，所指计算 JSON 和脚本不会进入 Git；这符合临时产物不进核心仓的边界。代价是报告引用的 JSON、脚本与抽样明细无法由仓库读者检视，且报告没有英文配对。

**建议**：在报告中保留完整查询/字段定义或生成脚本的稳定归档方式；不要把临时 scratch 输出描述为仓库内永久可复现证据。无需撤销 `scratch/` 忽略规则。

## 检查通过项与边界

- **M3 用户裁决本身明确**：拒绝 SDK fallback；R10 走 PAR。旧修订记录中出现“held”是当时状态，若日期和后续覆盖关系清楚，作为历史记录可以保留。
- **核心 bar 归因算术成立**：21 个标的的 `lyra_1h = nova_1h + partial + tail` 恒等式全部成立；179,550 + 4,359 = 183,909；partial 占 97.6%。
- **Raw SHA256 复核通过**：21/21 根目录逐标的 CSV 在 Nova 与 Lyra 两侧相同；`scratch/` 已被 Git ignore。
- **时区断言的适用范围**：本地 JSON 支持 43,103 个标的-日期中 Lyra 日 bar 数均不低于 Nova；这只是所含数据窗口内的比较，不证明共同 raw 覆盖完整。
- 没有重跑全套测试：本轮目标是文档与已有数据证据的对抗性核验，不涉及程序改动。

## 处置建议

先处理 H1–H3 与 M1–M2，再把修订后的中英文文档作为 0007 R10 / 0008 签收材料。M3–M4 是证据范围和归档透明度改进；不推翻用户关于 Lyra bar 集的裁决，也不要求重新下载 raw 数据。
