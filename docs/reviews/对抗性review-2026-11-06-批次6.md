## 关键修正细节

### A1（本批次最核心：防"看似成功"）

三层验证的**必要性**在于：Parquet 是"追加 row-group + 末尾写 footer"的格式。
一次中断最可能留下的坏状态是——**footer 已写、但前面某个 row-group 的
page 数据损坏 / 缺页**。这种情况 `SELECT COUNT(*)`（走 footer 元数据）**不会
报错**，会返回"对"的行数；只有真正逐 row-group 解压时才暴露。
所以"footer 对 + COUNT 对"**不足以**证明数据没坏——必须做
**全 row-group 解压扫描**（每 row-group 触发 page 解码）。
实测：三份文件共 395 + 82 + 7 = 484 个 row-group **全部**成功解码、
扫到行数与 footer 完全一致 → **无静默损坏**。
raw 层再补一刀：163/163 zip 与远端 PAR 逐对象 **md5 + size 双比对全等**
（md5 比对排除了"size 相同但内容不同"的极端情形）。

### A2 + A3（用户诉求落地）

用户明确要"DuckDB 作为 metadata / external-table catalog"。落地的关键是
**分清"数据"与"元数据"**：

* **数据**：bronze / 5m / 1h 的 **Parquet 文件**（I18 单一事实来源，
  0007 push 的对象）。
* **元数据**：`catalog.duckdb`（274 KB），只存 3 条
  `CREATE VIEW ... AS SELECT * FROM read_parquet('…')`。

下游（0003 feature builder / 0005 trade engine）查询时 `SELECT ... FROM bronze`
即可——**稳定命名入口**，不必记路径、不必 re-glob、列序由 Parquet 文件本身
决定（I18）。catalog 坏了删掉 `upsert_views` 重建即可，**零数据风险**。
这正是用户要的"高效又好管理好扩展"形态。

### A6（诚实标注效率上界）

A2/A3 不是"零内存"魔法：VIEW 消除了 bronze 全表拷贝，但 aggregate 的
**分组工作集**（`time_bucket` 哈希表 + `ARRAY_AGG` 排序缓冲）在 48M 行下
实测峰值 ≈9.5 GB。这是 DuckDB 聚合的固有形态，**不是 bug、也不是流式可消除的**
（除非改成纯外部聚合 / 分片）。文档必须如实写，否则 0003 在更大 feature 面
上会误以为"内存免费"。

## 结论

本批次回答了两个"看起来成功 ≠ 真的成功"的边界问题：

1. **完整性**——前面的系统中断**没有**留下截断 / page 损坏 / 静默失败
   （三层验证：footer + 全 row-group 解压 + raw md5 全过）。
2. **高效性**——读路径已统一为 DuckDB **外部表 / 视图**（A2 消除 bronze
   全表拷贝；A3 建立 catalog 命名入口）；同时**诚实标注** aggregate 分组
   工作集在 48M 行下仍约需 ~10 GB 峰值（A6），避免 0003 误判"内存免费"。

0002 在真实数据上**可复现跑通 + 数据完整 + 读写走 DuckDB 高效形态**三项
均满足，可进入 commit。遗留一项**非阻塞**：aggregate 峰值内存 ~10 GB
（A6）已在文档如实标注，0003 设计大 feature 面时需据此规划。
