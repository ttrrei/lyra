### 缺陷 1：【严重跨平台故障】路径安全校验正则阻断 Windows 路径（直接违背 R8 可移植性承诺）

* **涉及文件**：[`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L36) (`_quote`)、[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L43) (`_quote`)。
* **代码现实**：
  ```python
  # lyra/aggregate.py
  def _quote(path: Path) -> str:
      if not re.match(r"^[\w\s/.\-]+$", str(path)):
          raise ValueError(f"unsafe path for aggregate: {path!r}")
      return str(path)

  # lyra/clean.py
  def _quote(path: Path) -> str:
      s = str(path)
      if not re.match(r"^[\w\s/.\-*]+$", s) or s.startswith("-"):
          raise CleanInputError(f"unsafe path for clean: {path!r}")
      return s
  ```
* **攻击场景与破坏性**：
  * 在 Windows 环境下，`Path.resolve()` 输出的路径必然包含驱动器盘符冒号 `:` 以及 Windows 分隔符 `\`（如 `C:\Users\run\...` 或 `C:/Users/run/...`）。
  * 现有的正则表达式 `^[\w\s/.\-]+$` 和 `^[\w\s/.\-*]+$` **严厉排除了冒号 `:` 与反斜杠 `\`**！
  * 当任何 Windows 用户执行 `lyra pull`、`lyra clean` 或 `lyra aggregate` 时，程序将在第一步直接抛出 `CleanInputError` 或 `ValueError` 崩溃！
  * 这直接违背了 [`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L149) R8 的明确规定：“**可移植**：POSIX + Windows；不依赖系统包”。
* **判定**：**严重缺陷 (Major)**。
* **处置建议**：统一重构路径转义，将单引号进行标准 SQL 转义（`s.replace("'", "''")`），正则放宽对 Windows 盘符 `:` 与分隔符 `\` 的合法识别，并在 CI/测试中增加 Windows 风格路径的回归测试。

### 缺陷 2：【架构死锁与崩溃风险】Catalog 缺乏并发锁防御，承诺的 "Best-effort" 在代码中裸奔

* **涉及文件**：[`lyra/pipeline.py`](file:///home/ubuntu/work/lyra/lyra/pipeline.py#L149-L152)、[`lyra/catalog.py`](file:///home/ubuntu/work/lyra/lyra/catalog.py#L64)。
* **代码现实**：
  在 `pipeline.py` 中写道：
  ```python
  # 5) register the DuckDB catalog (metadata layer over the Parquet files)
  #    so 0003+ query stable named views instead of re-opening globs.
  #    Best-effort: a catalog failure must not fail the data pipeline.
  from .catalog import upsert_views
  upsert_views(data_root)
  ```
  在 `catalog.py` 中：
  ```python
  con = duckdb.connect(str(self.path))
  ```
* **攻击场景与破坏性**：
  * DuckDB 文件数据库是**单进程排他写锁（Exclusive File Lock）**机制。
  * `pipeline.py` 注释声称“*Best-effort: a catalog failure must not fail the data pipeline*”，但代码中对 `upsert_views` **没有任何 `try...except` 保护**！
  * 若下游进程（如 0003 特征计算后台任务、Jupyter 交互分析、或者未释放连接的 Python 终端）正持有 `catalog.duckdb` 连接，此时运行 `lyra pull`，在漫长 15 分钟完成 12GB 下载与清洗聚合后，将在最后一行被 DuckDB 的 `IOException: Could not set lock on file` 炸崩！
  * 导致用户产生错觉以为全流程失败，违反了“catalog 仅是元数据，不应阻断核心数据落地”的架构契约。
* **判定**：**严重缺陷 (Major)**。
* **处置建议**：
  1. `pipeline.py` 必须对 `upsert_views` 加包裹 `try...except Exception as exc:`，失败时仅发出警告而不抛出异常中断 pipeline；
  2. `catalog.py` 在连接失败或遇到锁冲突时提供友好提示，并考虑只读尝试。

### 缺陷 3：【内存失控风险】未对接 `config.yml` 的 `databackend` 内存限制（小内存机必遭 OOM Kill）

* **涉及文件**：[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L94, #L157)、[`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L127)、[`config/config_example.yml`](file:///home/ubuntu/work/lyra/config/config_example.yml#L36-L39)。
* **代码现实**：
  * `config_example.yml` 明确定义了：
    ```yaml
    databackend:
      memory_limit: "1GB"
      threads: 2
      # spills go to local.tmp
    ```
  * 但在 `clean.py`、`aggregate.py`、`pipeline.py` 中，全部硬编码调用 `duckdb.connect(":memory:")`，**根本没有传递任何 `memory_limit` 或 `temp_directory` 参数**！
  * 批次 06 的实测数据已证实：aggregate 的分组工作集峰值高达 **9.5 GB**！
* **攻击场景与破坏性**：
  * DuckDB 默认策略是抢占宿主机 80% 的物理内存。
  * Lyra 的核心定位（R0）是“**小 AI 预算与业余时间**”，用户极可能在 4GB~8GB 内存的云主机、轻量虚拟机或 Docker 容器中运行。
  * 一旦在 4GB~8GB 机器上跑真实数据，因未设置 `max_memory` 和磁盘换页 `temp_directory`，Linux 内核的 OOM Killer 会直接发送 `SIGKILL (Kill -9)` 暴毙中断进程！用户在 `config.yml` 中配置的 `memory_limit: "1GB"` 实际上完全被代码无视。
* **判定**：**中度缺陷 (Moderate)**。
* **处置建议**：在 `clean.py` 和 `aggregate.py` 的 `duckdb.connect` 中读取 `config.yml` 的 `databackend.memory_limit` 和 `local.tmp`，执行 `SET max_memory='...'; SET temp_directory='...'`，让 DuckDB 溢出时安全下刷磁盘换页。

### 缺陷 6：【防呆鲁棒性盲区】`_validate_1m` 对稀疏标的（Sparse Data）误判违规且报错不透明

* **涉及文件**：[`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L42-L70)。
* **代码现实**：
  ```sql
  WITH g AS (
      SELECT instrument,
             EXTRACT(EPOCH FROM (time - LAG(time) OVER (PARTITION BY instrument ORDER BY time))) AS gap_s
      FROM bronze
  ),
  mins AS (
      SELECT MIN(gap_s) AS min_gap_s FROM g WHERE gap_s IS NOT NULL GROUP BY instrument
  )
  SELECT COUNT(*) FROM mins WHERE min_gap_s < 59 OR min_gap_s > 61
  ```
* **攻击场景与破坏性**：
  1. **冷门/节假日抽样数据误杀**：如果用户测试或拉取的标的中包含一个交易极不活跃的冷门品种，或者只有单日切片数据，其历史上的最小两根 bar 间隔为 2 分钟（120 秒），`min_gap_s` 将等于 120。由于 `120 > 61`，`_validate_1m` 会误将该合法 1m 标的判为违规，直接抛出 `GranularityError` 拒绝整个 12GB 数据集的聚合！
  2. **诊断极其晦涩**：报错信息仅为 `I22 violation: 1 instrument(s) are not 1-minute resolution`。在 21 个标的、4800 万行数据中，用户根本不知道是哪一个标的被误拒、其 `min_gap_s` 到底是多少。
* **判定**：**中度缺陷 (Moderate)**。
* **处置建议**：
  1. 报错信息增加具体违规标的列表及其实测 `min_gap_s`；
  2. 考虑将判据放宽为允许极值接近 60s 的倍数，或仅拒绝整体分布为 5m/1h 的标的。

### 缺陷 7：【边界时区漂移】空表落盘使用 naive timestamp，与非空表 TIMESTAMPTZ 产生 Schema 漂移

* **涉及文件**：[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L147-L154)、[`lyra/pipeline.py`](file:///home/ubuntu/work/lyra/lyra/pipeline.py#L56-L62)。
* **代码现实**：
  * 在真实非空数据下，DuckDB 写入 Parquet 的 `time` 列是 `TIMESTAMPTZ(UTC)`（带时区属性）；
  * 但当 `clean_csv_to_bronze_parquet` 或 `_write_parquet` 遇到 0 行空输入时，回退的 PyArrow 代码构造了：
    ```python
    pa.field("time", pa.timestamp("us"))  # 缺少 tz="UTC" 参数！
    ```
* **破坏性**：空数据集输出的 Parquet 是 naive `timestamp[us]`，真实数据输出的是 `timestamp[us, tz=UTC]`。下游工具或 DuckDB 在联合读取或执行严格 Schema 校验时会触发类型不匹配错误，违背 I18“Schema 绝对稳定”承诺。
* **判定**：**轻度缺陷 (Minor)**。
* **处置建议**：在 `clean.py` 和 `pipeline.py` 的空表分支中，统一使用 `pa.timestamp("us", tz="UTC")`。

### 缺陷 8：【视图跨工作目录失效】`Catalog.upsert` 嵌入相对路径导致切换目录后查询失败

* **涉及文件**：[`lyra/catalog.py`](file:///home/ubuntu/work/lyra/lyra/catalog.py#L62-L78)。
* **代码现实**：
  ```python
  root = Path(data_root)
  ...
  parquet = root / sub
  con.execute(f"CREATE OR REPLACE VIEW {view_name} AS SELECT * FROM read_parquet('{parquet}')")
  ```
* **破坏性**：
  * 若调用方传入相对路径（如 `--data-root data`），写入 DuckDB 视图的语句为 `read_parquet('data/all_data/all_data.parquet')`。
  * 当下游（如 0003 测试或外部脚本）在其他子目录打开 `catalog.duckdb` 并执行 `SELECT * FROM bronze` 时，DuckDB 会基于当前工作目录寻找 `data/...`，必然抛出 `No such file or directory`。
* **判定**：**轻度缺陷 (Minor)**。
* **处置建议**：强制执行 `root = Path(data_root).resolve()`，确保视图内嵌的 Parquet 路径绝对化。

### 缺陷 9：【解压无上限防御】`pull.py` 缺少解压炸弹（Zip Bomb）大小拦截

* **涉及文件**：[`lyra/pull.py`](file:///home/ubuntu/work/lyra/lyra/pull.py#L74-L88)。
* **代码现实**：
  `extract_zips_to_csv` 仅校验了 `archive.testzip()`（仅校验 CRC 校验和），直接通过 `while True: chunk = src.read(...)` 流式落盘。
* **破坏性**：没有对 `info.file_size` 进行阈值拦截。若远程恶意或损坏的对象包含解压炸弹（几十 KB 解压出上百 GB），将导致本地存储被瞬间写爆（DoS）。
* **判定**：**轻度缺陷 (Minor)**。
* **处置建议**：对单 member 的解压后大小 `info.file_size` 增加安全上限拦截（如单个 CSV 不应超过 2GB）。
