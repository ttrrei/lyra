# 0003 Feature Builder 对抗性自检（2026-11-08 批次 1）

> **范围**：按 `docs/hld.md` §8 第 3 阶段检查 0003 v1.3 决策与已落地实现。审查 `lyra/features.py`、`lyra/registry.py`、`lyra/indicators.py`、`lyra/catalog.py`、feature CLI、对应测试源码、`docs/decisions/0003-feature-builder.md`、HLD 与 requirements。
>
> **审查方式**：静态追踪代码路径、接口契约、元数据与测试覆盖。**本轮没有运行测试**；104 项通过等状态仅引用 ACTION_LOG #65 的既有记录，不作为本轮复测结果。

## 结论

0003 的主计算路径边界清晰：聚合层按标的读取、在 Python/NumPy/TA-Lib 侧计算、特征宽表含输入列，并逐标的写 Parquet。此前 ACTION_LOG 记录的测试和真实数据 E2E 结果为收口提供了证据，但本轮发现 **4 项高优先级缺陷**，其中两项直接影响本地写入边界与特征产物可追溯性；另有若干注册表、Catalog 和文档/测试覆盖缺口。**建议在 0003 正式签收及进入 0004 前先处置高优先级项，并复核相关回归测试。**本报告只记录审查结果，不代表这些问题已修复。

优先级：**高**表示会破坏安全边界、已声明接口或产物一致性；**中**表示可能使固定参数、元数据、下游消费或回归门禁偏离已定约定。

## 高优先级发现

### H1 — `instrument` 未验证并直接拼入输出路径

- **证据**：`list_instruments()` 从聚合数据读出标的值，`clean` 未发现针对 `instrument` 的路径字符校验；`feature_path()` 将该值直接插入 `Path(data_root) / "features" / layer / f"{instrument}.parquet"`（`lyra/features.py:775-785`）。
- **影响**：带有 `../`、路径分隔符或 Windows 分隔符的输入值可使输出离开预期的 feature 子目录，甚至越过 data root。数据通常来自受控 OCI，但这一写路径边界没有在代码中落实。
- **建议**：在数据入口和 `feature_path()` 两层拒绝路径分隔符、`.`/`..` 等路径组件，并在写入前检查解析后的目标仍位于对应 layer 目录内。保留合法 instrument 命名的具体字符集需与 0002 数据合约一致。

### H2 — alpha compute 的公开签名与运行时调用不一致

- **证据**：决策文档 §3.1 写明 alpha `compute` 接收 `(mid_o, mid_h, mid_l, mid_c, volume, time, *extra)`，并可返回一维数组或 `{col: array}`；实现却在 `compute_features()` 中固定调用 `spec.compute(ctx, spec)`，随后只接受单个 `np.ndarray` 且形状必须为 `(ctx.n,)`（`lyra/features.py:572-580`）。现有 alpha fixture 使用的是运行时签名，和文档签名相反。
- **影响**：按已发布契约编写的 alpha 特征会在执行时失败；文档承诺的多列返回也无法工作。R3.2 的扩展点因此没有唯一、可依赖的接口契约。
- **建议**：先选定唯一接口并同步文档、类型/校验和 fixture。若保留 `(ctx, spec) -> ndarray`，需明确 alpha 如何注册多列特征（或删除该承诺）；若保留原始数组签名及多列返回，则实现适配和列名/注册规则。

### H3 — alpha 实现版本没有进入 Parquet 版本标识

- **证据**：决策文档 §3.1 说 alpha 语义版本由模块 docstring 的版本标签承担；实现的 `feature_version_string()` 只散列注册名、`params` 和 `warmup_bars`，再加 core `FEATURE_VERSION` 与 Python/NumPy 版本（`lyra/features.py:584-599`）。loader 不读取或校验 alpha 的版本标签，元数据也不记录 alpha 源码摘要。
- **影响**：保持相同注册名、参数和 warm-up 的 alpha 代码改变后，版本标识可以不变。不同语义的 feature Parquet 因而无法仅凭既有版本元数据区分，削弱可复现与后续 run provenance。OCI 同路径不可变只能约束远端文件覆盖，不能令当前本地产物标识出其所用实现。
- **建议**：让 alpha 版本标识成为强制、可解析且写入 Parquet 元数据的注册字段，或将实际加载的 alpha 模块内容摘要纳入版本标识；同时将其纳入文档和回归测试。

### H4 — 多标的重算不是原子发布，失败会留下混合版本

- **证据**：`run_features()` 对标的逐个计算并立即覆盖正式路径，循环完成前没有 staging/publish 屏障或全量版本一致性校验（`lyra/features.py:852-861`）。Catalog 的 `features_5m` / `features_1h` 视图使用该目录下全部 Parquet 文件的 glob（`lyra/catalog.py:92-119`）。
- **影响**：在某标的计算或写盘失败时，前面已覆盖的文件是本轮版本，后面的文件仍是旧版本。Catalog 随后仍可读到一组混合版本的文件；若列结构变更，还可能因 glob schema 不一致而在下游报错。此时命令失败并不等于输出目录保持上一个完整状态。
- **建议**：先将整轮结果写入隔离的 generation/staging 位置，全部成功并验证版本与 schema 后再切换可见版本；或提供 manifest/发布标记并让 Catalog/下游只消费已完整发布且版本一致的一组文件。

## 中优先级发现

### M1 — 注册参数是可变字典，固定参数约定可被运行时绕过

`FeatureSpec` 是 `frozen=True`，但 `Registry.register()` 保存普通 `dict`，并经 `get()` 暴露；调用方可直接改 `reg.get("rsi_24").params["n"]`。计算闭包会读取该映射，因此无需改注册定义即可更改实际参数，并可能令 `window_params` 与实际参数分离（`lyra/registry.py:46-71, 109-119`）。建议在注册时深度冻结参数，或避免暴露可变内部状态；增加“尝试修改后被拒绝/不影响计算”的测试。

### M2 — `load_from()` 复制 core 注册表时丢弃 `self_implemented`

复制 core spec 的 `out.register(...)` 没有传递 `self_implemented=spec.self_implemented`（`lyra/features.py:635-645`）。标准 CLI 总是先调用 `load_from()`，所以 HA 在实际 feature 命令所用 registry 中失去 K7 的 `True` 标记；当前 K7 测试直接检查 `build_registry()`，没有覆盖 loader 后的 registry。建议复制该字段并在 `load_from()` 路径断言 HA 标记保持。

### M3 — 版本串未包含 timeframe，且实现与记录的数值栈字段不一致

决策文档 §3.1 与 HLD §2.2 声明版本标识包含 timeframe 及 Python/NumPy/pandas；实现的 `feature_version_string(reg)` 不接收 timeframe，实际只写入 Python 与 NumPy。5m 和 60m 对同一 registry 会得到相同 `version_string`，虽然另有独立的 `input_minutes` 元数据。建议将 timeframe 纳入版本串，或修订契约说明版本串与 timeframe 分字段；并明确 pandas 是否属于产物计算栈（目前运行时 feature builder 未使用 pandas）。

### M4 — Catalog 查询入口隐藏了 features 视图

`upsert_feature_views()` 创建 `features_5m` / `features_1h`，但 `Catalog.views()` 的白名单只含 `_LAYERS`（bronze、ohlcv_5m、ohlcv_1h）；因此 `lyra catalog` 不会展示刚创建的 feature views。若把它作为人工检查 Catalog 完整性的入口，会给出不完整结果。建议将 features views 纳入列举和刷新流程，并覆盖命令行为。

### M5 — D5 测试没有验证文档承诺的内存上限

`test_per_instrument_streaming` 只调用一次 `build_instrument()`，断言返回行数和列数；它没有测量峰值内存、验证整个多标的循环逐个写后释放，也没有 `<300MB` 断言（`tests/test_features.py` 对应测试段）。实现的 `run_features()` 静态上确实逐标的处理并 `del built`，但当前测试不是能捕捉该控制律回归的内存门禁。建议调整测试或收窄决策文档对该测试的描述。

### M6 — HLD 对 0003 状态及输出路径仍与当前实现/决策文档冲突

- HLD §8 第 3 行仍写“v0.1 骨架、借鉴扫描中”，与 0003 v1.3 已实施及 ACTION_LOG #65 的状态相矛盾。
- HLD §2.2/§3 使用 `data/features/<minutes>m/...`（例如 `features/5m`），而 0003 决策和代码使用 `data/features/ohlcv_5m/...`、`data/features/ohlcv_1h/...`。

建议在本轮 review 处置后同步 HLD 中英版；具体输出路径以用户批准的 0003 合约为准，避免给 0007/0004 留下两种路径口径。

## 已核对的边界与本轮限制

- 0003 仍以 5m/1h 聚合视图为输入；本轮未发现它越界实现交易执行或组合收益。
- `run_features()` 主循环可见地按标的读取、计算、写入；本轮指出的是失败后的发布一致性和测试证明不足，不是全标的一次性载入。
- 本轮没有复跑 ACTION_LOG #65 所述 104 项测试、pyflakes 或真实数据 E2E；上述通过状态只作为历史记录引用。
- 0003 §5b A5 的 OHLC 波动率、Connors RSI、截面特征缓做冲突仍待用户裁决；本轮不替用户改变该范围决策。

## 处置建议

先处理 H1–H4，再处理 M1–M6 或由用户明确接受其边界；之后针对修复项补回归验证、同步 HLD/双语决策文档，并重新确认 0003 的签收状态。完成前不建议把当前产物版本标识视为 alpha 代码的完整 provenance，也不建议在发生部分失败后直接消费 feature Catalog。
