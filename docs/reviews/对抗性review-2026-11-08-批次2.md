# 0004 YAML Compiler 对抗性自检（2026-11-08 批次 2）

> **范围**：针对 HLD §8 第 4 阶段，审查 0004 YAML schema、AST、SQL compiler、CLI、测试与决策文档。重点检查策略语义是否被静默改变、schema 是否 fail-fast、past-only 与参数绑定边界，以及编译计划标识。
>
> **方式**：静态追踪代码，构造最小 YAML 输入复现边界行为，并运行 0004 专项测试及全仓测试。本报告是对 #74 实施结果的独立对抗性复核；不修改实现，也不代表所列问题已处置。

## 结论

核心编译路径的时序设计有可验证基础：0004 专项测试通过，现有断言覆盖 past-only 窗口、NULL gate、after_event 的 exact-age、参数数量与 SQL 占位符一致，以及强制 2% stop。静态检查也未发现 SQL 常量插值或前视算子。

但本次复现了 **4 项高优先级问题**：STATE 与布尔值的类型语义混淆；tracked example 中 exit.take_profit_pct 被静默丢弃；exit 层的成本和持仓限制字段绕过验证；未知字段被静默忽略。另有 4 项中优先级问题涉及 YAML alias、错误归一化、元数据类型及 plan_hash 定义。前四项可能令通过 validate 的策略与作者写下的策略含义不同，建议修复并加回归后再将 0004 视为完成签收。

优先级含义：**高**表示已复现策略语义、执行元数据或 fail-fast 契约被破坏；**中**表示健壮性、审计字段或产物身份存在缺口，影响取决于调用方式或待明确的 hash 契约。

## 高优先级发现

### H1 — STATE 混合布尔和序数状态，比较两侧没有类型校验

- **证据**：0003 将 sma_alignment_6_24 注册为 STATE，数值取值是 -1 / 0 / +1（lyra/features.py:278-285, 365-371）。schema 对 STATE/EVENT 只限制运算符为 eq/ne，却未校验常量或右侧 feature 类型（lyra/strategy_schema.py:333-378）。`sma_alignment_6_24 == false` 被接受并编译；DuckDB 将 false 与数值 0 比较为相等，因此匹配的是“中性”状态，而不是下行状态 -1。反过来，布尔 feature 与数值状态 feature 的比较也被接受。现有 VALID_NESTED fixture 使用 true/false，但测试只编译，没有对实际状态值做 truth table（tests/_compiler_fixtures.py:112-144；tests/test_compiler.py:270-279, 447-454）。
- **影响**：策略作者可能以自然语言语义理解 false 为“不成立/下行”，数据库实际却将其解释为数值零。schema 既不能保证 feature-vs-feature 类型兼容，也不能保证布尔常量适用于 STATE。此问题改变信号含义，不只是报错格式。
- **建议**：为布尔状态与有限枚举/序数状态提供可判别的类型或值域；校验常量及右侧 feature 与左侧兼容。针对 -1、0、+1 和 true/false 加 DuckDB truth-table 测试，明确并拒绝歧义输入。

### H2 — exit.take_profit_pct 被接受但不会进入 CompiledPlan

- **证据**：tracked example 把 take_profit_pct 写在 exit 下（strategies/examples/momentum_breakout/v01.yaml:21-24），0004 决策也把它列为 exit 元数据字段（docs/decisions/0004-yaml-compiler.md §3.1）。实现只在 execution block 中解析 take_profit_pct（lyra/strategy_schema.py:464-508）；exit 归一化只复制 stop、成本和 max_holding/time_bars，没有复制 take_profit_pct（同文件:649-682）。最小输入中 exit.take_profit_pct=0.03 或 0.06 均可通过 parse，但生成的 CompiledPlan.take_profit_pct 为 None。
- **影响**：策略文件看似配置止盈，编译结果却没有止盈值；validate 仍报告有效。后续 0005 若仅消费 CompiledPlan，将按“无 take profit”运行。该丢失难以从 CLI 的 VALID 状态发现。
- **建议**：将 exit 与 execution 的兼容字段统一规范化，再经同一个 ExecutionMeta 校验；对 tracked-example 字段增加断言，确认 0.06 原样进入 CompiledPlan，并定义两处同时出现时的优先级/冲突规则。

### H3 — exit 层成本和 max_holding_bars 绕过范围校验

- **证据**：execution 层由 _parse_execution 校验非负成本与正整数 max_holding_bars（lyra/strategy_schema.py:464-508）。exit 层随后通过 _replace 直接覆盖 ExecutionMeta，未复用这些验证（同文件:664-682）。复现确认 exit.spread_bps=-50 与 exit.max_holding_bars=0 均被接受；当 execution.max_holding_bars 已设置时，exit.time_bars=0 也会因只在空值时检查而被静默忽略。
- **影响**：同一字段放在两个文档允许的位置会得到不同的校验；负成本或零持仓时限可进入 CompiledPlan，造成后续执行与成本报告失真。无效兼容别名还会被规范值遮蔽，降低审计可靠性。
- **建议**：先把所有兼容位置规范化为一个执行元数据对象，再统一执行类型、范围、正值和重复字段冲突校验。所有被接受的别名都应有等价测试和无效值测试。

### H4 — 未知 YAML 字段被忽略，拼写错误会静默改变策略

- **证据**：决策文档要求 strict schema 对未知 key fail-fast（0004-yaml-compiler.md §3.1）。当前 _validate_doc 读取已知字段但没有检查根级未知 key；execution parser 同样没有拒绝额外 key（lyra/strategy_schema.py:592-682、464-508）。复现中顶层 unknown 字段及 execution.commission_bps_round_trip_typo: 100 均通过，后者不会进入 CompiledPlan。
- **影响**：用户以为策略使用了特定成本或控制字段，实际上该字段被忽略，validate 仍成功。成本被遗漏会直接改变后续净收益计算；策略审阅者也无法从成功状态区分有效字段与拼写错误。
- **建议**：按每个 mapping 层维护允许键集合；不认识的字段统一报带 YAML 路径的 SchemaError。给根层、entry/exit、execution、组合算子和 temporal 节点分别加未知键回归测试。

## 中优先级发现

### M1 — YAML alias 未按决策拒绝，递归 alias 导致 RecursionError

决策文档要求拒绝递归 alias（§3.1），但 _SafeLoader 只处理重复键，没有禁用 alias（lyra/strategy_schema.py:247-268）。`extra: &loop [*loop]` 可加载成循环对象，之后 _reject_nan_inf 递归遍历时抛出裸 RecursionError（同文件:558-568），不是 SchemaError。若策略文件被自动批量验证，单个输入可输出非受控异常并中断调用方。建议检测对象图循环并按契约拒绝 alias/递归结构，错误应包含文件与 YAML 路径。

### M2 — 多种错误结构抛裸 Python 异常；CLI 只把 parse 阶段的 SchemaError 转成 INVALID

exit: oops 会在 dict(exit_raw) 抛 ValueError；after_event: [] 会在访问 ae.keys() 抛 AttributeError（strategy_schema.py:411-426, 511-520）。此外 validate/compile 只捕获 parse_strategy 的 SchemaError，而 compile_strategy 在 try 块外调用（cli.py:252-258, 281-287）；编译阶段的 SchemaError 同样不会走统一的 INVALID 输出。当前活动 Python 缺少 typer，因此 CLI 行为未动态执行，此项依据调用路径静态确认。建议入口处先校验 mapping/list 结构，并在命令层统一捕获预期的 Lyra 错误，避免 traceback 取代用户可修复的字段诊断。

### M3 — 部分 schema 元数据未做精确类型校验

timeframe_minutes: 60.0 会通过集合/字典键匹配，因为 Python 中 60.0 与 60 相等；direction 可接受 list；parents: v01 会被 tuple(...) 拆成字符序列（strategy_schema.py:606-626, 684-714）。这些值主要影响方向归属、血缘记录与可读诊断，但会污染 AI context/审计元数据，并可能使下游依赖方向字符串的代码遇到异型值。建议对 timeframe 使用非 bool 的整数检查，并明确校验 direction、parents、inherited、driven_by_lesson 的字符串/列表形状。

### M4 — plan_hash 忽略执行元数据与 feature snapshot，身份语义需收窄或补全

_plan_hash 只纳入 SQL、SQL 参数、feature 名、schema/compiler 版本（compiler.py:313-319）；调用时未传入 stop/take-profit/cost/max-holding，也未包含 CompiledPlan 上的 feature_catalog_snapshot（同文件:327-367）。复现中只有 take_profit_pct 不同的两个计划具有相同 plan_hash。若它是 SQL 编译指纹，这是合理但命名/文档需明确；若被当作完整策略计划或运行产物身份，则会让不同的执行语义/feature snapshot 共用一个标识。建议定义边界：保留 sql_hash 并另设 execution/provenance fingerprint，或把完整计划字段纳入 plan_hash。

## 已核对且未发现问题的部分

- 0004 专项测试中的时序边界、NULL gate、after_event exact-age 与 SQL 参数数量不变式全部通过。
- 代码生成使用已注册列/白名单列与标识符引用，常量以绑定参数传入；本轮未发现 lead 或前视 join。
- 强制 2% stop 的 execution 与 exit 两条路径在现有专项测试中均有覆盖；本轮未复现可放宽 stop 的路径。
- compile_strategy 对同一策略输入的 SQL/参数保持确定性；tracks、AI 身份与 VectorBT 没有混入 SQL 编译输入，符合已裁定边界。
- O16 的 332 策略 feature 缺口是既有、独立的兼容问题；本报告不把它重复计作 0004 schema/compiler 缺陷。

## 反向自检：避免过度定性

1. 对 H1，问题不是说 false 必然代表“下行”，而是注册值域为 -1/0/+1、schema 却接受布尔常量并让 DuckDB 把 false 等同于 0；语义未定义且确实会匹配中性行，因此应修类型边界，而非假设唯一作者意图。
2. 对 H2，止盈字段如果放在 execution 下可以解析；缺陷具体是决策与 tracked example 支持的 exit 位置会被静默丢弃。
3. 对 M4，若 plan_hash 的正式定义仅为 SQL 计划摘要，同 hash 本身并非 bug；报告将其作为契约歧义，未要求必然改变 hash 算法。
4. 全仓测试失败是缺少 requests 的解释器环境问题；没有把这 8 项报告为产品缺陷。
5. 当前专项测试通过并不推翻边界复现；它们说明已覆盖的时序与安全检查有效，也显示 schema 负例和执行元数据兼容形状缺少测试。

## 处置建议

接受 0004 之前先修复 H1–H4，并为每项加入最小回归；同时处置 M1–M3 的契约与错误归一化，明确 M4 的 hash 范围。修复后重跑专项测试和全仓测试（在包含项目依赖的解释器中），再单独确认 CLI 输出。报告只提交审查结论，不包含实现改动。
