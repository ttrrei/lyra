## 1. Core Defect & Vulnerability Analysis

### Defect 1: [Major Cross-Platform Failure] Path security regex rejects valid Windows paths (violates R8 portability)

* **Affected Files**: [`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L36) (`_quote`), [`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L43) (`_quote`).
* **Code Reality**:
  ```python
  # lyra/aggregate.py
  def _quote(path: Path) -> str:
      if not re.match(r"^[\w\s/.\-]+$", str(path)):
          raise ValueError(f"unsafe path for aggregate: {path!r}")
      return str(path)

  # lyra/clean.py
  def _quote(path: Path) -> str:
      s = str(path)
      if not re.match(r"^[\w\s/.\-*]+$", s) or s.startswith("-"):
          raise CleanInputError(f"unsafe path for clean: {path!r}")
      return s
  ```
* **Attack Scenario & Impact**:
  * On Windows, `Path.resolve()` outputs drive letters with colons `:` and backslashes `\` (e.g., `C:\Users\run\...` or `C:/Users/run/...`).
  * The current regexes `^[\w\s/.\-]+$` and `^[\w\s/.\-*]+$` strictly exclude colons `:` and backslashes `\`.
  * Whenever a Windows user runs `lyra pull`, `lyra clean`, or `lyra aggregate`, execution crashes immediately with `CleanInputError` or `ValueError`!
  * This directly contradicts [`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L149) R8: "**Portable**: POSIX + Windows; no system package dependencies".
* **Severity**: **Major**.
* **Remediation**: Use standard SQL string literal escaping (`s.replace("'", "''")`), relax path regexes to permit colons `:` and backslashes `\`, and add Windows-style path tests.

### Defect 2: [Architectural Deadlock & Crash Risk] Catalog lacks concurrency lock handling; promised "Best-effort" unhandled

* **Affected Files**: [`lyra/pipeline.py`](file:///home/ubuntu/work/lyra/lyra/pipeline.py#L149-L152), [`lyra/catalog.py`](file:///home/ubuntu/work/lyra/lyra/catalog.py#L64).
* **Code Reality**:
  In `pipeline.py`:
  ```python
  # 5) register the DuckDB catalog (metadata layer over the Parquet files)
  #    so 0003+ query stable named views instead of re-opening globs.
  #    Best-effort: a catalog failure must not fail the data pipeline.
  from .catalog import upsert_views
  upsert_views(data_root)
  ```
  In `catalog.py`:
  ```python
  con = duckdb.connect(str(self.path))
  ```
* **Attack Scenario & Impact**:
  * DuckDB databases use an exclusive file lock for write connections.
  * `pipeline.py` claims in comments that catalog registration is "Best-effort", but calls `upsert_views` **without any `try...except` block**!
  * If a downstream process (such as 0003 feature extraction, a Jupyter notebook, or an interactive Python session) holds a connection to `catalog.duckdb`, running `lyra pull` will abort on the very last line with `duckdb.IOException: Could not set lock on file` after 15 minutes of downloading and aggregating 12 GB of data!
  * This violates the principle that metadata catalog failures must never abort successful raw and bronze data sync.
* **Severity**: **Major**.
* **Remediation**: Wrap `upsert_views` in `pipeline.py` with `try...except Exception:` emitting a warning without aborting the pull; handle lock contention gracefully.

### Defect 3: [Unbounded Memory Risk] `databackend` memory limits in `config.yml` completely ignored (OOM kill on low-spec machines)

* **Affected Files**: [`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L94, #L157), [`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L127), [`config/config_example.yml`](file:///home/ubuntu/work/lyra/config/config_example.yml#L36-L39).
* **Code Reality**:
  * `config_example.yml` specifies:
    ```yaml
    databackend:
      memory_limit: "1GB"
      threads: 2
      # spills go to local.tmp
    ```
  * However, `clean.py`, `aggregate.py`, and `pipeline.py` hard-code `duckdb.connect(":memory:")` without setting `max_memory` or `temp_directory`!
  * Batch 06 real-data metrics proved that aggregate peak working set reaches **9.5 GB**!
* **Attack Scenario & Impact**:
  * DuckDB defaults to claiming 80% of host RAM.
  * Lyra is explicitly targeted at "small AI budgets and spare time" (R0). Users are likely to deploy on 4 GB or 8 GB cloud instances or virtual environments.
  * Running `lyra pull` on a 4 GB–8 GB machine without DuckDB spill configuration will cause the Linux kernel OOM Killer to terminate the process with `SIGKILL (Kill -9)`. The user-specified `memory_limit: "1GB"` is ignored.
* **Severity**: **Moderate**.
* **Remediation**: Pass `databackend.memory_limit` and `local.tmp` into DuckDB connections, setting `SET max_memory='...'; SET temp_directory='...'` to enable disk spilling.

### Defect 6: [Granularity Check Vulnerability] `_validate_1m` false-positive on sparse instruments with opaque error

* **Affected Files**: [`lyra/aggregate.py`](file:///home/ubuntu/work/lyra/lyra/aggregate.py#L42-L70).
* **Code Reality**:
  ```sql
  WITH g AS (
      SELECT instrument,
             EXTRACT(EPOCH FROM (time - LAG(time) OVER (PARTITION BY instrument ORDER BY time))) AS gap_s
      FROM bronze
  ),
  mins AS (
      SELECT MIN(gap_s) AS min_gap_s FROM g WHERE gap_s IS NOT NULL GROUP BY instrument
  )
  SELECT COUNT(*) FROM mins WHERE min_gap_s < 59 OR min_gap_s > 61
  ```
* **Attack Scenario & Impact**:
  1. **Sparse / Holiday data rejection**: If pulled data contains an illiquid instrument or a short test sample where the closest two bars are 2 minutes apart (120s), `min_gap_s == 120`. Because `120 > 61`, `_validate_1m` rejects the entire 12 GB dataset with `GranularityError`!
  2. **Opaque diagnosis**: The error message only states `I22 violation: 1 instrument(s) are not 1-minute resolution`, offering no detail on which symbol failed or what its `min_gap_s` was.
* **Severity**: **Moderate**.
* **Remediation**: Include the offending instrument names and their measured `min_gap_s` in the exception message.

### Defect 7: [Schema Timezone Drift] Empty bronze writes naive timestamp instead of TIMESTAMPTZ

* **Affected Files**: [`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L147-L154), [`lyra/pipeline.py`](file:///home/ubuntu/work/lyra/lyra/pipeline.py#L56-L62).
* **Code Reality**:
  * For non-empty data, DuckDB writes `TIMESTAMPTZ(UTC)` into Parquet.
  * For empty zero-row inputs, fallback PyArrow code writes:
    ```python
    pa.field("time", pa.timestamp("us"))  # missing tz="UTC"!
    ```
* **Impact**: An empty dataset produces `timestamp[us]`, while real data produces `timestamp[us, tz=UTC]`. This causes schema drift when reading or concatenating, violating I18.
* **Severity**: **Minor**.
* **Remediation**: Use `pa.timestamp("us", tz="UTC")` consistently in empty-table fallbacks.

### Defect 8: [Cross-Directory Path Breakage] `Catalog.upsert` embeds relative paths into persistent views

* **Affected Files**: [`lyra/catalog.py`](file:///home/ubuntu/work/lyra/lyra/catalog.py#L62-L78).
* **Code Reality**:
  ```python
  root = Path(data_root)
  ...
  parquet = root / sub
  con.execute(f"CREATE OR REPLACE VIEW {view_name} AS SELECT * FROM read_parquet('{parquet}')")
  ```
* **Impact**: If `data_root` is passed as a relative path (`data`), DuckDB embeds `'data/all_data/all_data.parquet'`. When downstream processes access `catalog.duckdb` from another directory, queries fail with `No such file or directory`.
* **Severity**: **Minor**.
* **Remediation**: Enforce `root = Path(data_root).resolve()` to ensure persistent views store absolute file paths.

---

### Defect 9: [Missing Decompression Bounds] `pull.py` lacks zip bomb defense

* **Affected Files**: [`lyra/pull.py`](file:///home/ubuntu/work/lyra/lyra/pull.py#L74-L88).
* **Code Reality**: `extract_zips_to_csv` checks `archive.testzip()` for CRC integrity, then streams decompression without inspecting `info.file_size`.
* **Impact**: A corrupt or malicious archive expanding to hundreds of gigabytes would fill the local disk (DoS).
* **Severity**: **Minor**.
* **Remediation**: Add a maximum single-file uncompressed size threshold (e.g. 2 GB) before extracting.
