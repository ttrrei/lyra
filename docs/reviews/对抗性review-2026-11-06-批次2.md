### 漏洞 1：【致命架构死锁】B9 / I17 OCI 全局不可变规则导致方向迭代（`hypothesis.md` / `lessons.md`）上传崩溃

* **涉及文件**：[`docs/proposals/oci-alpha-layout.md`](file:///home/ubuntu/work/lyra/docs/proposals/oci-alpha-layout.md#L427) (B9)、[`docs/decisions/0001-repo-and-oci-split.md`](file:///home/ubuntu/work/lyra/docs/decisions/0001-repo-and-oci-split.md#L82) (I17)、[`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L201) (R12)。
* **漏洞描述**：
  * 规则 B9 与不变量 I17 规定：“**OCI 上的文件不可变（同 path 同 sha256 幂等；不同 sha256 报错）**”，且 0001 的测试清单明确包含 `test_push_rejects_sha_mismatch`。
  * 与此同时，R12 明确定义方向目录内的 `hypothesis.md` 包含状态迁移（active/paused/killed）与修改历史（只增不删）；`lessons.md` 是追加式日志（每个版本一段）；`index/*.json` 随着新策略/运行产生而动态重建更新。
* **冲突死锁场景**：
  * 初始阶段：用户或 AI 推送 `trend_continuation` 方向的首版 `v01`，此时 `lessons.md` 上传至 OCI，产生哈希 $H_1$。
  * 迭代阶段：基于 `v01` 的运行诊断，AI 或用户向本地 `lessons.md` 追加了 `v02a` 的诊断教训，文件哈希变为 $H_2$。此时执行 `lyra push-direction trend_continuation`。
  * 致命冲突爆发：OCI 远端路径 `.../trend_continuation/lessons.md` 已存在，但哈希 $H_2 \neq H_1$。按照规则 B9 和 I17 的无差别拦截，`push` 操作将被作为“数据漂移错误”直接拒绝！导致方向演进历史根本无法同步至 OCI！
* **红队判定**：**致命漏洞 (Critical)**。B9 和 I17 制定时过于一刀切，混淆了“不可变数据（Data/Runs/vNN.yaml）”与“可追加元数据（Hypothesis/Lessons/Index）”。
* **修复方案**：
  必须在 B9 和 I17 中引入明确的分级约束：
  1. **严格不可变路径（Immutable）**：`data/**`、`runs/**`、`strategies/**/v*.yaml`、`alpha/features/*.py`（代码与数据严格不可篡改）。
  2. **允许追加更新路径（Append-only / Mutable Metadata）**：`strategies/**/hypothesis.md`、`strategies/**/lessons.md`、`index/*.json`（允许在内容为超集或版本向前推进时覆盖更新）。

### 漏洞 2：【概念冲突与 AI 幻觉隐患】“改造参数”表述与 I8 / R2“特征参数锁死（Fixed Params）”直接矛盾

* **涉及文件**：[`docs/ACTION_LOG.md`](file:///home/ubuntu/work/lyra/docs/ACTION_LOG.md#L49) (#22, #49)、[`docs/proposals/oci-alpha-layout.md`](file:///home/ubuntu/work/lyra/docs/proposals/oci-alpha-layout.md#L215) (§2.3)、[`AGENTS.md`](file:///home/ubuntu/work/lyra/AGENTS.md#L11) (Non-negotiables)、[`docs/hld.md`](file:///home/ubuntu/work/lyra/docs/hld.md#L199) (I8)。
* **漏洞描述**：
  * 在 `ACTION_LOG.md` 条目 #22 与 R12 演进决策中写道：“交叉/变异完全交给找策略的 AI：取什么、怎么合成（整块 / 逐参数 / **改造参数**）全由 AI 自由决定，框架不限制粒度”。
  * 但在 `AGENTS.md` 铁律与 `hld.md` 不变量 I8 中严正声明：“**Feature parameters are fixed. New features are registered, not re-parameterized. No parameter sweeps.**（特征参数在注册时定死，不做扫描）”。
* **潜在风险**：
  * 在“AI 是一等写作者”的前提下，AI 上下文包若包含“可自由改造参数”的字眼，极易导致 LLM 产生幻觉，尝试去修改已注册特征的底层参数（例如在 YAML 中将 `sma_alignment_6_24` 随意改成 `sma_alignment_7_25`，或将 `rsi_14` 改成 `rsi_17`）。
  * 这种 YAML 一旦被 AI 生成，将在 `lyra validate` 阶段因找不到注册特征而全部报错崩塌，造成大量上下文与算力浪费。
* **红队判定**：**严重隐患 (Major)**。文字表述存在致命模糊性。
* **修复方案**：
  在 R12、`ACTION_LOG` 和提案中做出显式区分：AI 的变异与“改造”能力**严格限定于策略层阈值与时间算子参数**（如 `held_for.bars`、`within.bars`、比较操作符、常数阈值）；**严禁改动任何特征注册名及已注册特征的参数（固守 I8）**。

### 漏洞 3：【版本树生命周期缺陷】跨代交叉语义空白、命名碰撞与无限分支规避杀灭

* **涉及文件**：[`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L207) (R12)、[`docs/proposals/oci-alpha-layout.md`](file:///home/ubuntu/work/lyra/docs/proposals/oci-alpha-layout.md#L219) (§2.3)。
* **漏洞描述**：
  * **缺陷 3.1（跨代交叉未定义）**：规则规定版本命名为 `v<代数><分支后缀>`。在遗传迭代中，不同代数的分支发生交叉（如父本 1 为高胜率基线 `v02a`，父本 2 为最新突破分支 `v04b`）是常规操作。然而当前文档完全没有定义：跨代交叉产生的新分支应该算作哪一代？（是算第 3 代、第 4 代还是第 5 代？）
  * **缺陷 3.2（同父母多变异命名碰撞）**：若 AI 对同一对父本 `v03a` 和 `v03b` 探索了两种不同的交叉融合方案（例如方案一融合入场，方案二融合出场），按当前规范都会生成 `v04ab.yaml`，发生同名覆盖。
  * **缺陷 3.3（无限分支规避 Kill Criteria）**：R12 规定“单分支失败 = prune；kill criteria 作用于所有活跃分支连续 N 轮失败”。但由于框架**没有对单方向并发活跃分支总数设定上限（Active Branch Cap）**，自动化 AI 可以在旧分支濒临失败时，通过源源不断分叉出 `v02c`, `v02d`, `v02e`... 来无限规避触发 kill criteria，导致该方向沦为永久占用算力的僵尸任务。
* **红队判定**：**中度缺陷 (Moderate)**。演进机制缺乏工程严密性。
* **修复方案**：
  1. 明确跨代交叉的代数定义为 $\max(\text{parent generations}) + 1$。
  2. 命名规则允许增加序号或变异后缀（如 `v05ab_1.yaml`，或由 hash 衍生）。
  3. 设定每个方向的**最大并发活跃分支数上限**（如建议不超过 3~4 个分支），超额必须显式 prune，防止搜索空间无序膨胀。

### 漏洞 4：【执行引擎接口黑洞】SQL 稀疏信号与 2% 盘中不利止损计算的架构断层

* **涉及文件**：[`docs/hld.md`](file:///home/ubuntu/work/lyra/docs/hld.md#L97) (§2.3, §2.4)、[`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L78) (R4)。
* **漏洞描述**：
  * HLD 规定：`compiler` 组件将 YAML 转换为 DuckDB SQL；`run` 组件执行 SQL，并按 bar 运行 Trade state machine。
  * 不变量 I3 严格规定：持仓期间只要价格触及不利价差 2%，立即在下一根开盘前触发平仓。
  * **断层盲区**：如果 SQL 编译器仅按条件过滤输出“信号触发行（`signal == True`）”，那么在开仓到平仓之间的数十或数百根持有 bar 期间，Trade state machine 根本拿不到逐根 bar 的 High/Low 极值！没有极值数据，Trade engine 根本无法判断盘中是否曾击穿 2% 止损线！
* **红队判定**：**中度缺陷 (Moderate)**。直接关系到即将编写的 `0004` 与 `0005` 决策文档的技术接口可行性。
* **修复方案**：
  在 HLD 和未来 `0004/0005` 中明确数据流接口方案：
  * **方案 A（全量流式回放）**：SQL 仅负责在 Parquet 宽表上计算并标记特征谓词（输出全量序列或带信号掩码的宽表），Python Trade engine 流式扫描并维护订单状态。
  * **方案 B（窗口下推）**：SQL 计算出信号后，通过窗口关联（如 `lead` 在回测验证中通常禁止，但可以在 SQL 外围使用范围关联）拉取持有区间极值。
  * *推荐方案 A*，保持 DuckDB 处理纯分析、Python 处理状态机的职责纯粹性。

### 漏洞 5：【OCI 本地镜像边界遗漏】B13 规范了数据与策略镜像，但遗漏了自定义特征 `alpha/` 的落地规范

* **涉及文件**：[`docs/proposals/oci-alpha-layout.md`](file:///home/ubuntu/work/lyra/docs/proposals/oci-alpha-layout.md#L429) (B13)、[`config/config_example.yml`](file:///home/ubuntu/work/lyra/config/config_example.yml#L13)。
* **漏洞描述**：
  * B13 提出：“OCI 镜像（`data/` `strategies/` `runs/`）默认解析到仓库外（`~/.lyra/<workspace>/…`）”。
  * 然而根据 OCI 布局方案，OCI 上还有 `alpha/features/*.py`（闭源特征、契约卡、测试）。
  * 在 [`config_example.yml`](file:///home/ubuntu/work/lyra/config/config_example.yml#L27) 中，只提供了 `features.extend_from` 路径，而在 `local:` 段中只列出了 `data`、`strategies`、`runs`、`tmp`，根本没有 `alpha` 目录项！
  * 如果用户运行 `lyra pull` 同步 alpha 特征，或者本地开发自定义特征时，由于缺少像 `local.strategies` 一样的规范约束，极易直接在 Git 工作区根目录下创建 `./alpha/`，从而立刻引发 B1 违规与泄露风险。
* **红队判定**：**中度缺陷 (Moderate)**。边界隔离设计遗漏了闭源特征。
* **修复方案**：
  在 `config_example.yml` 的 `local:` 段补齐 `alpha: "alpha"` 配置，并更新 B13 的文字说明，将 `alpha/` 明确纳入“默认位于仓库外部 `~/.lyra/<workspace>/alpha/`”的防呆体系中。

### 漏洞 6：【标的定义与时间成本模糊】21 标的池缺少标准化定义，跨周末隔夜融资成本（Financing）未定

* **涉及文件**：[`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L91) (R1, R4, R8)、[`config/config_example.yml`](file:///home/ubuntu/work/lyra/config/config_example.yml#L33)。
* **漏洞描述**：
  * R1 声明覆盖 forex / precious metals / crude oil / equity indices，R8 声称验证“21 标的 H1 全量 run”。但全库没有任何一份文档给出这 21 个标的的权威清单与代码标识规范（例如黄金是 `XAU_USD` 还是 `GOLD`？原油是 `BCO_USD` 还是 `WTICO_USD`？）。
  * 成本模型定义了 `financing_per_day: 0.0001`（fraction per elapsed day）。真实外汇/CFD 跨周末持仓会产生 3 天隔夜利息。文档未明确“elapsed day”是物理时间戳相减折算日历天（`exit_time - entry_time`），还是交易日（bar 数换算）。若定义模糊，回测收益在跨周末时将出现口径漂移，违背 R8（同一输入确证相同输出）。
* **红队判定**：**轻度缺陷 (Minor)**。口径不确定性影响回测复现。
* **修复方案**：
  在 HLD 或 Requirements 中显式枚举 21 标的标准代码表；明确隔夜利息计算严格以 UTC 时间戳差值的物理日历日（含周末）为准。
