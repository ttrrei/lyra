# 0004 Compiler and 0005 Trade Engine Joint Adversarial Review (2026-11-08 Batch 4)

> **Scope**: Review the implemented code modules (`lyra/strategy_schema.py`, `lyra/compiler.py`, `lyra/trade_engine.py`, `lyra/cli.py`), decision records (`docs/decisions/0004-yaml-compiler.md` and `docs/decisions/0005-trade-engine.md`), and their interface assembly and temporal contracts for HLD §8 Stage 4 (0004 YAML Compiler) and Stage 5 (0005 Trade Engine).
>
> **Method**: Static code path analysis, dataflow cross-verification, edge-case input synthesis, and empirical validation in Python and DuckDB. This report is a read-only red-team review detailing defects, evidence, and minimal reproductions without directly modifying production code or tests.

---

## Conclusion

Both the 0004 compiler and the 0005 trade state machine perform adequately in isolation within their unit test suites (186 passed overall), successfully maintaining baseline invariants such as past-only windowing, mandatory 2% stops, loss-priority resolution (`stop_inside` before `target_inside`), and trade direction isolation.

However, an adversarial end-to-end audit across the boundary between 0004 and 0005 uncovered **2 Critical (blocking)**, **3 Major (contract violation / silent failure)**, and **3 Minor (boundary discrepancy)** defects:

1. **0004 compiled plans cannot drive 0005 trade engine directly**: `CompiledPlan.sql` only selects 6 signal and identity columns, omitting the `mid_o/mid_h/mid_l/mid_c` price columns. Meanwhile, `trade_engine.simulate()` unconditionally dereferences OHLC columns, causing an immediate `KeyError: 'mid_o'` and revealing an unintegrated contract gap.
2. **Financing override parameter `trading_days: float` is architecturally defective**: `simulate()` accepts a single scalar `trading_days`, which applies the exact same duration to all trades in a multi-trade simulation. Furthermore, the caller cannot know the entry/exit timestamps before `simulate()` executes, making R4/O15 trading-day financing unusable for multi-trade runs.
3. **Cross-feature comparisons bypass type validation**: The batch 2 fix for H1 (STATE ordinal vs boolean) only applied to constant literals (`if is_const`). When comparing two columns, type checking is bypassed entirely, allowing comparisons like `close > psar_bullish` to crash DuckDB with `BinderException` at runtime, while `sma_alignment_6_24 == psar_bullish` silently treats `0 = FALSE` as TRUE.
4. **`_quote()` constructs invalid ghost column names (`bid_mid_o`)**: String concatenation combines `"bid_"` with `"mid_o"` to look for `"bid_mid_o"`, which never matches the 0002 standard columns `bid_o` / `ask_o`, silently ignoring real market quote spreads.
5. **Missing schema whitelist in `exit.feature`**: Typos in `exit.feature` (e.g. `whenn`) are silently accepted, causing exit rules to be discarded and replaced with `FALSE AS exit_long` without any warning or error.

## Defect Inventory & Evidence

### Critical

#### C1 — 0004 `CompiledPlan.sql` omits OHLC price columns, causing `KeyError: 'mid_o'` when fed into 0005 `simulate()`

- **File & Line**: `lyra/compiler.py:290-298` vs `lyra/trade_engine.py:114-118, 198, 213-215`
- **Evidence**:
  `compiler.py`'s `_build_select` generates:
  ```sql
  SELECT "instrument" AS instrument, "time" AS time,
         <entry_long> AS entry_long, <entry_short> AS entry_short,
         <exit_long> AS exit_long, <exit_short> AS exit_short
  FROM "features_5m" ORDER BY instrument, time
  ```
  This query projects only 6 columns and completely leaves out `mid_o`, `mid_h`, `mid_l`, `mid_c`.
  In contrast, `lyra/trade_engine.py:198` and `:213-215` unconditionally read `bar["mid_o"]`, `bar["mid_l"]`, and `bar["mid_h"]`.
  Passing the DuckDB query output of `plan.sql` directly into `simulate(plan, rows)` crashes immediately on the first bar with `KeyError: 'mid_o'`.
- **Impact**: The output of 0004 is disconnected from the input requirements of 0005. Existing tests in `test_compiler.py` only verify SQL execution in DuckDB, while `test_trade_engine.py` only uses mock synthetic dictionaries. There is zero end-to-end integration coverage connecting `compile -> duckdb execute -> simulate`.
- **Minimal Reproduction**:
  ```python
  spec = parse_yaml(VALID_YAML, reg)
  plan = compile_strategy(spec, reg)
  rows = duckdb.connect().execute(plan.sql, plan.params).fetchdf().to_dict(orient="records")
  simulate(plan, rows)  # KeyError: 'mid_o'
  ```

#### C2 — Scalar `trading_days: float | None` parameter cannot support multi-trade simulations and cannot be known in advance

- **File & Line**: `lyra/trade_engine.py:106-111, 171` vs `docs/decisions/0005-trade-engine.md:122, 131-136`
- **Evidence**:
  Commit #84 introduced `simulate(plan, bars, *, trading_days: float | None = None)`, evaluated inside `_finish()` as:
  `days = _day_count(position["time"], timestamp, trading_days)`.
  However, `simulate()` processes a full bar sequence for an instrument (e.g., 1 to 5 years), typically generating dozens to hundreds of distinct trades. Accepting a single scalar `trading_days` forces every single trade in that run to be billed for the exact same duration, whether a trade lasted 1 hour or 3 weeks.
  Moreover, the caller (the 0006 runner) cannot know when trades will enter or exit before `simulate()` executes, making it physically impossible for the caller to provide precomputed trading-day counts ahead of time.
  Leaving `trading_days=None` falls back to `(exit - entry).total_seconds() / 86400` (natural days), directly violating R4 and closed decision O15 by charging financing across weekends and market holidays.
- **Impact**: The R4/O15 trading-day financing requirement is in a deadlocked state: passing the override corrupts multi-trade financing with a single uniform scalar, while omitting it violates R4/O15 by charging weekend financing.
- **Minimal Reproduction**:
  In a bar series containing two trades (Trade A held for 1 trading day, Trade B held for 10 trading days), pass `trading_days=5`. Both trades receive identical 5-day financing charges, overcharging Trade A by 4 days and undercharging Trade B by 5 days.

### Major

#### M1 — Feature-vs-feature comparisons bypass type checking, causing runtime DuckDB `BinderException` or silent logic bugs

- **File & Line**: `lyra/strategy_schema.py:427-464`
- **Evidence**:
  The batch 2 resolution for H1 only guarded literal constants (`if is_const:`).
  When the RHS is a feature column (`is_const = False`), `_parse_value_rhs` returns `(False, None, col)`, discarding `_kind` with no subsequent type compatibility check between left and right columns.
  - **Case A (DuckDB Runtime Crash)**: A strategy specifies `feature: close, op: gt, value: psar_bullish` (double price vs boolean). YAML parsing succeeds, and SQL codegen emits `("mid_c" > "psar_bullish")`. DuckDB execution fails immediately: `_duckdb.BinderException: Cannot compare values of type DOUBLE and type BOOLEAN - an explicit cast is required`.
  - **Case B (Boolean Literal vs Numeric Column)**: A strategy specifies `feature: close, op: eq, value: true`. Because `close` has no `STATE` kind, it bypasses the `left_kind is STATE` guard and binds `True` as a query parameter. DuckDB casts `True` to `1.0`, silently checking whether the asset price equals 1.0.
  - **Case C (Ordinal vs Boolean State Inconsistency)**: A strategy specifies `feature: sma_alignment_6_24, op: eq, value: psar_bullish` (ordinal state {-1,0,1} vs boolean state). The generated SQL is `("sma_alignment_6_24" = "psar_bullish")`. When SMA alignment is neutral (0) and PSAR is not bullish (FALSE), DuckDB evaluates `0 = FALSE` as TRUE, generating a false-positive entry signal.
- **Impact**: Violates 0004's fail-fast validation promise. Validated strategies crash during backtesting execution or trade on corrupted signals.
- **Minimal Reproduction**:
  ```python
  spec = parse_yaml("""
  version: 1
  id: type_err
  timeframe_minutes: 5
  direction: long
  entry:
    long:
      feature: close
      op: gt
      value: psar_bullish
  exit:
    stop_loss_pct: 0.02
  """, reg)
  plan = compile_strategy(spec, reg)  # Succeeds without error
  duckdb.connect().execute(plan.sql)  # Raises _duckdb.BinderException
  ```

#### M2 — `_quote()` generates nonexistent column names (`"bid_mid_o"`), silently ignoring real quote data

- **File & Line**: `lyra/trade_engine.py:97, 198, 213-215, 266`
- **Evidence**:
  `_quote()` constructs column names as:
  `name = ("bid_" if direction == 1 else "ask_") + point`
  Calls from `simulate()` pass `point="mid_o"`, `point="mid_l"`, `point="mid_h"`, and `point="mid_c"`.
  This evaluates `name` to `"bid_mid_o"` and `"ask_mid_o"`.
  However, in 0002 bronze/silver schemas (`lyra/clean.py:33`, `lyra/oanda.py:57-60`), the actual column names are `bid_o`, `ask_o`, `bid_h`, `ask_h`, `bid_l`, `ask_l`, `bid_c`, `ask_c`.
  Because `bar.get("bid_mid_o")` is always `None`, `_quote()` will NEVER read real bid/ask quotes from input bars, always falling back to `base = float(bar[point])` with synthetic `spread_bps`.
- **Impact**: When running backtests against high-quality datasets that provide true bid/ask quotes, real market spread information is entirely ignored and degraded to fixed-basis synthetic spread estimation.
- **Minimal Reproduction**:
  ```python
  bar = {"mid_o": 1.0, "bid_o": 0.9990, "ask_o": 1.0010}
  quoted = _quote(bar, direction=1, point="mid_o", spread_bps=0)
  assert quoted == 1.0  # Returns 1.0 instead of 0.9990
  ```

#### M3 — `exit.feature` lacks strict key validation, silently dropping misspelled exit conditions into `FALSE AS exit_long`

- **File & Line**: `lyra/strategy_schema.py:706-728`
- **Evidence**:
  In `_normalize_exit_and_execution`:
  ```python
  legacy_when = None
  feature_block = exit_raw.get("feature")
  if isinstance(feature_block, dict) and "when" in feature_block:
      legacy_when = feature_block["when"]
  ```
  `_reject_unknown_keys` is never called on `feature_block`.
  If a user has a typo (e.g. `exit.feature.whenn: {feature: close, op: lt, value: open}`), `"when" in feature_block` evaluates to False, and `legacy_when` remains `None`.
  No error or warning is emitted; `exit_long` and `exit_short` become `None` and compile down to `FALSE AS exit_long, FALSE AS exit_short`.
  Similarly, passing `exit.feature: "invalid_string"` is silently swallowed.
- **Impact**: Violates strict fail-fast schema guarantees. A strategy's indicator exit condition is completely stripped without notice, leaving the strategy unable to exit except by stop-loss or end-of-data.
- **Minimal Reproduction**:
  ```yaml
  exit:
    stop_loss_pct: 0.02
    feature:
      whenn:
        feature: close
        op: lt
        value: open
  ```
  Validates without error, compiling into `FALSE AS exit_long`.

### Minor

#### m1 — End-of-data liquidation timestamp uses bar open time instead of bar close time

- **File & Line**: `lyra/trade_engine.py:263-268`
- **Evidence**:
  End-of-data liquidation uses the last bar's close price `mid_c`, but passes `last["time"]` (the bar's open timestamp) as the exit time.
  If a trade entered on the final bar's open and is liquidated at the final bar's close, `entry_time == exit_time == last["time"]`, yielding `days = 0.0` and zero financing, despite holding across the full bar duration.
- **Impact**: Distorts the final bar's holding duration and diverges from `Trade.exit_time` documentation.

#### m2 — `simulate()` lacks single-instrument assertion

- **File & Line**: `lyra/trade_engine.py:106-269`
- **Evidence**:
  `simulate()` assumes the caller has partitioned the input by instrument. If an unpartitioned stream with interleaved instruments is provided, a position opened on EUR_USD can be closed by an exit signal on GBP_USD, recording a corrupted trade record with mismatched pricing and instrument identifiers.
- **Impact**: Missing defensive validation; should assert instrument consistency on each bar.

#### m3 — Opening gap take-profit fills at target limit price, discarding positive opening slippage

- **File & Line**: `lyra/trade_engine.py:228-234`, `docs/decisions/0005-trade-engine.md:144, 157`
- **Evidence**:
  When the market gaps above a take-profit target at open (e.g. entry 100, target 102, open 105), the fill is capped at `target` (102), forfeiting 300 bps of opening auction gain. In contrast, `stop_at_open` fills at the open price, fully bearing adverse gap losses.
  While inherited from Nova's conservative limit-order model, this asymmetric treatment penalizes strategies on favorable gaps while penalizing them on adverse gaps, and should be explicitly documented.

## Verified Invariants

- **Temporal Protection**: `compiler.py` restricts SQL generation to `lag` and `ROWS BETWEEN N-1 PRECEDING AND CURRENT ROW`, with no `lead`, forward joins, or future peeking.
- **Mandatory 2% Stop**: `strategy_schema.py` strictly enforces `stop_loss_pct: 0.02`, preventing widening or disabling of stops.
- **Intra-bar Stop vs Target Conflict**: `stop_inside` takes priority over `target_inside`, satisfying invariant I4 (loss takes priority).
- **No Reversals / Pyramiding**: Reversal signals during open positions are ignored, and same-bar re-entry after exit is prohibited.
- **Deterministic Identity**: `plan_hash` deterministically combines SQL, parameter values, features, and catalog snapshot.

## Minimal Reproduction Script

The following standalone script demonstrates defects C1, M1, and M2:

```python
import duckdb
from lyra.features import core_registry
from lyra.strategy_schema import parse_yaml
from lyra.compiler import compile_strategy
from lyra.trade_engine import simulate, _quote

reg = core_registry()

# 1. Verify C1: plan.sql missing OHLC columns needed by simulate()
yaml_c1 = """
version: 1
id: test_c1
timeframe_minutes: 5
direction: long
entry:
  long:
    feature: close
    op: gt
    value: open
exit:
  stop_loss_pct: 0.02
"""
plan = compile_strategy(parse_yaml(yaml_c1, reg), reg)
con = duckdb.connect()
con.execute("""
CREATE TABLE features_5m (
    instrument VARCHAR, time TIMESTAMP,
    mid_o DOUBLE, mid_h DOUBLE, mid_l DOUBLE, mid_c DOUBLE
);
INSERT INTO features_5m VALUES ('X', '2026-01-01 00:00:00', 1.0, 1.1, 0.9, 1.05);
""")
sql_rows = con.execute(plan.sql, plan.params).fetchdf().to_dict(orient="records")
try:
    simulate(plan, sql_rows)
except KeyError as e:
    print("[C1 Verified] simulate raised expected KeyError:", e)

# 2. Verify M1: feature-vs-feature type bypass
yaml_m1 = """
version: 1
id: test_m1
timeframe_minutes: 5
direction: long
entry:
  long:
    feature: close
    op: gt
    value: psar_bullish
exit:
  stop_loss_pct: 0.02
"""
plan_m1 = compile_strategy(parse_yaml(yaml_m1, reg), reg)
try:
    con.execute(plan_m1.sql)
except duckdb.BinderException as e:
    print("[M1 Verified] DuckDB raised type BinderException:", type(e).__name__)

# 3. Verify M2: _quote ghost column lookup
bar_m2 = {"mid_o": 1.0, "bid_o": 0.9990, "ask_o": 1.0010}
quoted = _quote(bar_m2, direction=1, point="mid_o", spread_bps=0)
assert quoted == 1.0, "M2 ghost column lookup failed to match bid_o"
print("[M2 Verified] _quote silently ignored real bid_o quote")
```

## Recommendations

1. **Resolve C1 (Align SQL Output with Trade Engine)**:
   - Update `_build_select` in `compiler.py` to project OHLC columns: `"mid_o" AS mid_o, "mid_h" AS mid_h, "mid_l" AS mid_l, "mid_c" AS mid_c` (plus bid/ask columns if available in the view).
   - This allows `plan.sql` output to flow directly into `simulate()` with zero in-memory joining overhead.
2. **Refactor C2 (Financing Calculation Contract)**:
   - Remove the scalar `trading_days` override from `simulate()`.
   - Have `simulate()` output trades with `entry_time`, `exit_time`, and `bars_held`, and calculate trading-day financing in the 0006 runner where the full market calendar is available; or pass a calendar trading-day predicate/lookup to `simulate()`.
3. **Fix M1 (Strict Type Validation for Column Comparisons)**:
   - When RHS is a feature column, resolve its `FeatureKind` and `unit`.
   - Disallow comparisons between `VALUE` (float) and `STATE`/`EVENT` (boolean).
   - Disallow comparisons between ordinal states and boolean states.
   - Disallow boolean constants on `VALUE` columns.
4. **Fix M2 (Correct `_quote` Column Name Construction)**:
   - In `_quote()`, extract the point suffix (`p = point[4:]` if starting with `"mid_"`) to correctly look up `bid_{p}` and `ask_{p}`.
5. **Fix M3 (Enforce Strict Whitelist on `exit.feature`)**:
   - Require `exit.feature` to be a mapping containing only `when`, and validate its expression tree strictly.
