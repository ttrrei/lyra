**结论：0009 的主要功能已落地，但当前实现和文档尚不能支撑“所有 D1–D11 均按决策完成、可直接进入 0010”的结论。** 找到 **5 项高优先级（P1）和 4 项中优先级（P2）**。其中多 track 数据串读、跨数据误判可比、特征多文件发布中断后无消费端门禁、doctor 对缺失 OCI 槽位仍报成功，以及 README 的新环境安装失败均已由代码路径或隔离探针证实。

## 高优先级发现

### H1（P1）— 同方向的独立 track 仍共享分支文件，context 会串入其他 track 的 run

**合同**：requirements R12 规定每条 track 独立拥有候选 YAML、lessons 和 run 归属；同一方向的不同 AI 应按自己的节奏演进。

**实现与复现**：

- `new_version()` 将候选写入 `strategies/<direction>/<branch>.yaml`，不含 track 路径；重复分支检查也查这个方向级文件。因此 track `alpha` 创建 `v02a` 后，track `beta` 无法创建自己的 `v02a`，而是被全局重复检查拒绝。
- `render_context()` 对每个活跃分支调用 `_runs_for_branch(workspace, direction, branch)`；该查询没有 `track_id` 参数或筛选条件。`run_meta.json` 虽记录 track，但查询会把同方向、同分支的所有 track run 一并返回。
- 隔离临时目录探针中，`alpha` 成功创建 `strategies/trend/v02a.yaml`，`beta` 创建同名候选被拒；分别为 alpha/beta 写入同方向同分支 run 后，`_runs_for_branch()` 返回了两条 run。

**影响**：不同 AI 不能在各自 track 中按相同分支标识独立形成候选；若同一分支被多个 track 使用，context/compare 会混合证据。用户要求的“互相不影响”目前没有由目录布局与查询实现保证。

**建议**：落实 R12 声明的 track-owned 候选文件，并让 context、compare 等单 track 工作流明确携带并过滤 `track_id`。跨 track synthesis 仍按用户显式调用的研究范围读取，并明确列出参与的 tracks，不能由单 track context 隐式混入。对已有方向级 YAML 定义迁移/兼容规则，并增加“同名分支可跨 track 独立创建、运行记录不串读”的回归测试。

### H2（P1）— compare 没有按 D3 的 `data_digest + feature_version` 判定可比性

0009 D3 及 §2.2 定义：两个 run 只有 `data_digest` 和 `feature_version` 都一致才可比，且要在 run 粒度显示不可比状态。

当前 `runner` 将 `data_digest` 用于 `run_id`，但没有写入 `metrics.json` 或 `manifest.json`；`metrics.json` 也没有 `feature_version`。`_runs_for_branch()` 只把 `feature_snapshot_id` 读入工作流结果，`compare_siblings()` 仅检查所有非空 snapshot id 是否相同，并返回一个总体 `comparable` 布尔值。它既不比较 D3 定义的两个身份字段，也不逐 run 标记。

因此，同一 feature snapshot 下如果底层输入数据身份不同，compare 仍可能报告 `comparable=true`；不同 `feature_version` 的 run 也没有独立校验。现有 `test_d3_compare_marks_incomparable_across_generations` 只覆盖 snapshot id 不同的情形，没有覆盖同 snapshot、不同 data digest/version。

**建议**：把 `data_digest` 与 `feature_version` 持久写入 run 的可读身份产物；compare 按 track 范围读取它们并逐 run/逐组判定。缺字段的 legacy run 应显式为 unknown/incomparable，不能以相同 snapshot id 推定可比。

### H3（P1）— feature 发布不是代际级原子切换，run 也不执行 generation 门禁

`run_features()` 会先准备 staging 文件，但发布阶段先删除过期文件，再逐个删除旧目标并 `rename` 新文件；所有文件替换结束后才写 `_generation.json`。若发布循环中途失败或进程退出，目标目录可能由新旧文件混合构成，而旧 manifest 仍在描述之前那一代。`_write_generation()` 自身也是直接覆写文件。

现有 `test_atomic_publish_failure_keeps_previous_generation` 只在 build 阶段模拟 instrument 失败，此时发布尚未开始；它没有覆盖第二个/后续文件 rename 失败。另一个关键缺口是 `validate_generation()` 在运行时只由 `lyra doctor` 调用：`lyra features` 命令没有按 D4 调用它，`lyra run` 也不在读取特征前校验。即使发布中断被发现，消费端仍可能读到混代目录。

**影响**：D4 声称的“中途失败保留上一完整 generation”及 fail-closed 门禁并未实现；run_id 中的 generation digest 也可能描述 manifest，而实际被 DuckDB 读取的文件已混代。

**建议**：以不可变代际目录加单一原子指针/目录切换，或实现可验证的备份回滚；确保 manifest 最后原子替换。`lyra run` 必须在读取特征前 fail-closed 校验。增加发布中途失败（含 prune、替换、manifest 写入）的故障注入测试。

### H4（P1）— doctor 对缺失的三个 OCI 槽位仍返回 exit 0，与 D10 硬失败约定冲突

D10 将 config 可解析且四个 OCI 槽位齐全列为硬失败条件。实际 `doctor()` 只让 `data_par_url` 因 `oci_from_dict()` 缺失而报错；`features_par_url`、`strategies_par_url`、`runs_par_url` 缺失时写入 warnings。

我用临时配置只提供 `data_par_url`，缺失另外三槽运行 `lyra doctor`：结果是 **`DOCTOR OK: 0 failures, 4 warning(s)`，exit 0**（另外一条 warning 是无 catalog）。所以这不是边界推断，而是可复现的验收门槛偏差。

**影响**：doctor 会把无法执行完整 OCI 同步/备份的配置报告为成功。它与 D10、requirements R10 的“环境/配置类问题硬失败”及 #110 所称的 0 hard fail 不一致。

**建议**：按 D10 将缺失的三个槽位改为硬失败；若产品实际决定它们在 0009 可选，则必须先修订 D10/R10 并明确 doctor 的成功代表什么，不能让实现默默降级。

### H5（P1）— README 的全新环境安装流程在 editable install 步骤失败

README 顺序是新建 venv、安装 `requirements.lock`，再执行：

```sh
.venv/bin/pip install -e . --no-deps --no-build-isolation
```

`pyproject.toml` 的 build backend 是 `setuptools.build_meta`，需要 `setuptools>=68`；但 `requirements.lock` 和 `scripts/make_lock.sh` 的包 allowlist 均不包含 setuptools。按 README 完整复现：新建临时 Python 3.12 venv，`pip install -r requirements.lock` 成功；随后上述 editable install **失败 exit 2**，错误为 `ModuleNotFoundError: No module named 'setuptools'`。

**影响**：README 的干净环境安装路径不可用；CI 因只在 checkout 根目录直接运行测试，并未安装 Lyra package，未发现这个失败。

**建议**：将 build backend 加入锁定安装路径，或允许 pip build isolation 并正确声明 build requirements；CI 应验证文档所用的安装序列，而不只是在源码目录运行测试。

## 中优先级发现

### M1（P2）— doctor 的 Python 策略和核心依赖检查落后于当前支持面

`pyproject.toml` 已钉 `>=3.12,<3.13`，但 doctor 常量仍是 `(3,11)` 到 `(3,13)`，输出也宣称 `>=3.11,<3.13`，所以 Python 3.11 会被 doctor 判为 PASS。核心 import 清单漏掉了运行时必需的 NumPy（在 lock 中但未作为 pyproject 直接依赖声明）与 pyproject 声明的 TA-Lib；它们不可 import 时不会触发此处硬失败，compile smoke 失败也只会成为 warning。

**建议**：doctor、pyproject、CI、README 共用同一 Python 支持区间；硬依赖检查覆盖实际运行时核心依赖，并增加 3.11 拒绝、缺 NumPy/TA-Lib 失败的测试。

### M2（P2）— 0009 验收与阶段状态记录没有和实现终态对齐

- `0009-polish.md` 和 `.en.md` §4 的 8 条验收仍全部是未勾选 `[ ]`，包括 R10 双语签收、全仓测试与 doctor。
- HLD §8 的 0009 行仍写 **2026-11-11、323 tests**，与 #110 的 2026-11-12、324 tests 不同。
- ACTION_LOG #110 详细行仍写 pyproject `>=3.11,<3.13`、CI `3.11+3.12`，与当前 pyproject 和 workflow 的 3.12 单点不符；状态摘要虽已写 3.12。

**影响**：读者无法从阶段验收清单及中央日志追溯 0009 实际完成范围；历史事实和最终实现混在同一条目。

**建议**：在处理本报告后刷新 0009 验收清单、HLD §8 行与双语 ACTION_LOG 的 #110 现状说明/修订记录；历史行不可重写时应追加勘误说明。

### M3（P2）— doctor 的命令名、安装态示例策略和操作提示与实际 CLI 不一致

- 实际入口是 `lyra doctor`；`pyproject.toml` 只注册 `lyra`，没有独立 `lyra-doctor` 可执行文件，但 0009 决策稿及 requirements R10 使用 `lyra-doctor`。
- 0009 §3a 声称 compile smoke 有内置 RSI fallback；实际 `_default_example_strategy()` 只搜索仓库根下 `strategies/examples/*/v01.yaml`，找不到就报错并降为 warning。策略目录没有打入 Python package，非源码 checkout 安装时该 warning 预计常驻。
- doctor 的 catalog warning 建议运行 `lyra build`，但 `lyra --help` 没有 `build` 命令；当前实际命令为 `pull`、`clean`、`aggregate`、`catalog` 等。

**建议**：统一正式命令名；将 smoke strategy 纳入 package 或使用真正的内置 fallback；warning 只提示现存 CLI 命令。

### M4（P2）— run 身份侧车写入失败不阻断成功返回，workflow 会静默丢失该 run

`lyra run` 捕获 `_write_run_meta()` 任意异常后只打印 WARN，仍输出 `OK` 并以成功结束。workflow 对有 `run_meta.json` 的 run 依赖其中的 direction/branch；若 sidecar 缺失，legacy 回退则靠 metrics 的 `spec_id` 精确匹配 branch。正式策略的 spec id 通常不是 `vNN` 分支名，因此该 run 可能不会进入 context/compare。

**建议**：run identity 作为策略搜索闭环的关键产物时，sidecar 写失败应让 CLI 失败，或由 manifest 内的等价身份字段可靠恢复；增加 sidecar 写失败与损坏测试。
