# 0004 YAML Compiler Adversarial Self-Review (2026-11-08 Batch 2)

> **Scope**: Review the 0004 YAML schema, AST, SQL compiler, CLI, tests, and decision document for HLD §8 stage 4. Focus on silent changes to strategy meaning, fail-fast schema behavior, past-only and parameter-binding boundaries, and compiled-plan identity.
>
> **Method**: Statically traced the code, reproduced boundary behavior with minimal YAML inputs, and ran the focused 0004 tests and the repository suite. This is an independent adversarial review of implementation #74. It changes no implementation and does not mean the findings have been addressed.

## Conclusion

The core temporal compilation path has verifiable support: the focused 0004 tests pass, with current assertions for past-only windows, NULL gating, exact-age after_event behavior, parameter count versus SQL placeholders, and the mandatory 2% stop. Static inspection found no interpolated SQL constants or lookahead operators.

However, this review reproduced **four high-priority issues**: STATE conflates boolean and ordinal values; exit.take_profit_pct from the tracked example is silently discarded; exit-level cost and holding-limit fields bypass validation; and unknown fields are silently ignored. Four medium-priority issues concern YAML aliases, error normalization, metadata types, and the definition of plan_hash. The first four can make a strategy that passes validation mean something different from what its author wrote. I recommend fixing them and adding regressions before signing off 0004.

Priority definitions: **High** means a reproduced violation of strategy semantics, execution metadata, or the fail-fast contract. **Medium** means a robustness, audit-field, or artifact-identity gap whose impact depends on usage or an unresolved hash contract.

## High-priority findings

### H1 — STATE mixes booleans with ordinal states, and comparison operands are not type-checked

- **Evidence**: Lyra registers sma_alignment_6_24 as STATE with numeric values -1 / 0 / +1 (lyra/features.py:278-285, 365-371). The schema restricts STATE/EVENT operators to eq/ne but does not check the type of constants or the right-hand feature (lyra/strategy_schema.py:333-378). `sma_alignment_6_24 == false` is accepted and compiled; DuckDB compares false equal to numeric 0, so it matches the “neutral” state rather than the bearish state -1. A boolean feature compared with a numeric state feature is also accepted. The VALID_NESTED fixture uses true/false, but tests only compile it and do not assert an actual state truth table (tests/_compiler_fixtures.py:112-144; tests/test_compiler.py:270-279, 447-454).
- **Impact**: An author may read false as “not true/downtrend”, while the database interprets it as numeric zero. The schema guarantees neither feature-vs-feature type compatibility nor that a boolean constant is valid for a STATE. This changes signal meaning; it is not merely an error-message issue.
- **Recommendation**: Distinguish boolean states from finite-enum/ordinal states with explicit types or value domains; validate constants and right-hand feature compatibility. Add DuckDB truth-table tests for -1, 0, +1, and true/false, and reject ambiguous inputs.

### H2 — exit.take_profit_pct is accepted but omitted from CompiledPlan

- **Evidence**: The tracked example places take_profit_pct under exit (strategies/examples/momentum_breakout/v01.yaml:21-24), and the 0004 decision lists it as exit metadata (docs/decisions/0004-yaml-compiler.md §3.1). The implementation parses take_profit_pct only from execution (lyra/strategy_schema.py:464-508); exit normalization copies stop, costs, and max_holding/time_bars, but not take_profit_pct (same file:649-682). Minimal inputs with exit.take_profit_pct=0.03 or 0.06 pass parsing, but CompiledPlan.take_profit_pct is None.
- **Impact**: A strategy appears to configure a take-profit, but the compiled result contains none while validate still reports success. If 0005 consumes only CompiledPlan, it will run without that take-profit. This is hard to spot from the CLI's VALID result.
- **Recommendation**: Normalize compatibility fields from exit and execution into one execution metadata object, then validate it once. Add a tracked-example assertion that 0.06 reaches CompiledPlan, and define precedence/conflict behavior when both locations are present.

### H3 — Exit-level costs and max_holding_bars bypass range validation

- **Evidence**: The execution block validates non-negative costs and positive integer max_holding_bars via _parse_execution (lyra/strategy_schema.py:464-508). The exit block then uses _replace to write directly into ExecutionMeta without reusing those checks (same file:664-682). Reproductions confirmed that exit.spread_bps=-50 and exit.max_holding_bars=0 are accepted. If execution.max_holding_bars is already set, exit.time_bars=0 is also silently ignored because it is validated only when the canonical value is empty.
- **Impact**: The same field receives different validation depending on its allowed location. Negative costs or a zero holding limit can enter CompiledPlan and distort later execution or cost reporting. Invalid aliases can also be hidden by canonical values, weakening auditability.
- **Recommendation**: Normalize all compatibility locations into one execution metadata object, then run a single set of type, range, positive-value, and duplicate-field conflict checks. Test every accepted alias with both valid and invalid values.

### H4 — Unknown YAML fields are ignored, so typos silently change the strategy

- **Evidence**: The decision requires a strict schema that fails fast on unknown keys (0004-yaml-compiler.md §3.1). _validate_doc reads known fields but does not check for unknown top-level keys; the execution parser also permits extras (lyra/strategy_schema.py:592-682, 464-508). A top-level unknown field and execution.commission_bps_round_trip_typo: 100 both passed reproduction; the latter never enters CompiledPlan.
- **Impact**: A user can believe a cost or control field is in effect when it was ignored, while validate succeeds. Missing cost changes later net-return calculations, and a reviewer cannot tell a valid field from a typo based on success status.
- **Recommendation**: Maintain allowed-key sets for each mapping and return SchemaError with the YAML path for unknown keys. Add unknown-key regressions at root, entry/exit, execution, boolean combinators, and temporal nodes.

## Medium-priority findings

### M1 — YAML aliases are not rejected as specified; a recursive alias raises RecursionError

The decision requires recursive aliases to be rejected (§3.1), but _SafeLoader handles duplicate keys only and does not disable aliases (lyra/strategy_schema.py:247-268). `extra: &loop [*loop]` loads as a cyclic object; _reject_nan_inf then raises a raw RecursionError during traversal (same file:558-568), rather than SchemaError. In batch validation, one such input can produce an uncontrolled exception and interrupt the caller. Detect object-graph cycles and reject aliases/recursive structures as specified, with a file and YAML path in the error.

### M2 — Malformed shapes raise raw Python exceptions; the CLI only maps parse-stage SchemaError to INVALID

exit: oops raises ValueError in dict(exit_raw); after_event: [] raises AttributeError at ae.keys() (strategy_schema.py:411-426, 511-520). Also, validate/compile catch SchemaError only around parse_strategy, then call compile_strategy outside that try block (cli.py:252-258, 281-287); compile-stage SchemaError will not use the same INVALID output. The active Python lacks typer, so CLI behavior was not executed dynamically; this finding is based on static call-path inspection. Validate mapping/list shapes at entry and normalize expected Lyra errors at the command boundary so tracebacks do not replace actionable field diagnostics.

### M3 — Some schema metadata fields do not receive exact type validation

timeframe_minutes: 60.0 passes dictionary/set membership because Python considers 60.0 equal to 60; direction can be a list; and parents: v01 is converted into a tuple of characters (strategy_schema.py:606-626, 684-714). These values mainly affect direction attribution, lineage records, and diagnostics, but can corrupt AI context/audit metadata and give downstream code expecting a direction string an unexpected type. Require a non-bool integer for timeframe and explicitly validate the shapes of direction, parents, inherited, and driven_by_lesson.

### M4 — plan_hash omits execution metadata and feature snapshot; its identity contract needs narrowing or expansion

_plan_hash includes only SQL, SQL parameters, feature names, and schema/compiler versions (compiler.py:313-319). Its call omits stop/take-profit/cost/holding settings and the feature_catalog_snapshot carried by CompiledPlan (same file:327-367). Reproduction showed two plans differing only in take_profit_pct had the same plan_hash. If this is an SQL compilation fingerprint, that is reasonable but should be explicit in its name/documentation. If it identifies the complete strategy plan or run artifact, distinct execution semantics or feature snapshots will share an identifier. Define the boundary: retain sql_hash and add execution/provenance fingerprints, or include all complete-plan fields in plan_hash.

## Checked boundaries with no issue found

- Code generation uses registered/allow-listed columns and identifier quoting, with constants passed as bind parameters; this review found no lead or forward join.
- Existing focused tests cover the mandatory 2% stop on both execution and exit paths; this review did not reproduce a way to widen the stop.

## Adversarial self-check: avoid overstatement

1. For H1, the claim is not that false must mean “downtrend.” The feature domain is -1/0/+1, while the schema accepts boolean constants and DuckDB equates false with 0. The input is undefined and does match neutral rows, so the type boundary should be fixed without assuming the author's sole intent.
2. For H2, take_profit_pct can be parsed from execution. The specific defect is that the exit location supported by the decision and tracked example is silently discarded.
3. For M4, if plan_hash is formally only an SQL-plan summary, identical hashes are not themselves a bug. The report treats this as a contract ambiguity and does not insist that the hash algorithm must change.
4. The repository test failures are explained by a requests-missing interpreter environment; they are not reported as product defects.
5. Passing focused tests do not invalidate the boundary reproductions. They show the covered temporal and safety checks work, while also showing that schema-negative cases and execution-metadata compatibility shapes lack coverage.

## Recommended disposition

Fix H1–H4 and add a minimal regression for each before accepting 0004. Also resolve the contract and error-normalization gaps in M1–M3, and define the hash scope in M4. Then rerun focused and repository tests in an interpreter with project dependencies and separately confirm CLI output. This report records review findings only and contains no implementation changes.
