# 0007 OCI 同步与 R12 工作流独立检验 + 对抗性检验（2026-11-10 批次2）

> **English**: [Independent and Adversarial Review of 0007](./对抗性review-2026-11-10-批次2.en.md)

## 范围与结论

本轮对照 requirements R7/R12、HLD §2.5/§4/§8、OCI 布局提案 B9/B11/B13/B14、0007 双语决策稿 rev0.4，以及 lyra/oci_push.py、lyra/workflow.py、lyra/cli.py 和相关测试。重点检查同步命令实际路径、I17/I19/I20、0006 run 归档、track 隔离与多分支演进。**本轮只记录审查结果，没有修改程序代码或设计决策。**

**结论：0007 目前不宜签收。** 代码已有完整命令面且全仓测试通过，但对抗探针复现了 10 项 P1：细粒度 push 静默空操作、无摘要时按 size 错误跳过、PAR token 泄漏、路径越界/符号链接上传、R12 分支命名被拒、track context 不自包含、兄弟 run 比较串线、push-runs 选错或未经校验的产物、普通 backup 漏掉默认 run、track index 无法满足 append-only 推送。另有 4 项 P2，涉及冻结基线、文档契约、认证回退和部分上传。

严重度：**P1** 会使核心命令不执行、研究结果/归属失真、破坏 OCI 不变量或造成凭据/路径安全风险；**P2** 是需要在收口前明确处理的持久化、兼容性或设计契约缺口。

## P1：必须先处理的发现

### H1 — push-strategy 与 push-direction 显示成功，却不上传任何对象

**证据**

- cli.py 的 push_strategy() 用 workspace/strategies 作为 plan_push 根目录，因此文件相对路径是 fx-trend/v01.yaml。
- oci_push.in_push_scope() 只允许顶层 strategies、runs、data、alpha。fx-trend 顶层被视为范围外并静默跳过。受控 probe 对存在的 v01.yaml 得到空 uploads、空 conflicts。
- push_direction() 仅调用 push_strategy()，所以既不会上传方向策略，也不会上传其 runs。push-strategy 文档还写成单个 direction/branch，但 CLI 参数只接收 direction；force_push 参数没有被这个手写上传路径使用。
- 现有测试没有覆盖这两个 CLI 命令。

**影响**：用户按提示执行方向推送会得到“成功但无变化”的结果；策略及 run 无法按承诺持久化。

**建议**：让被计划的相对路径保持 I17 所需的 strategies/<direction>/... 结构，按命令语义选择单 YAML 或整方向，并让 push-direction 处理规范 runs；增加真实 CLI fake-transport 测试，断言上传目标、冲突和 --force-push 行为。

### H2 — 远端无摘要时仅凭相同 size 就认定内容相同

**证据**

- oci_push._same_object() 在远端没有 sha256/md5 时以 size 相等返回 True。
- probe 用本地 b'AAAA' 与只有 size=4 的远端 metadata，得到“同一对象”。另一个同长度但字节不同的远端对象会被静默跳过。
- ACTION_LOG #89 已接受“size 不是内容证明、无可验证摘要必须重新下载”；#95 又把 size fallback 加回推送判断，和已定规则冲突。

**影响**：I17 immutable 同路径不同内容可能被当作幂等成功，破坏不可变对象身份与 run/策略归档可信度。

**建议**：无摘要时 fail-closed 并读取远端内容核验；不可只用文件长度跳过。为“相同 size、不同内容”补回归测试，并同步 #89/#95 的规则描述。

### H3 — PAR URL 脱敏保留了 OCI 路径中的签名 token

**证据**

- oci_client.redact_par_url() 保留路径前两个 segment。PAR 路径形如 /p/<token>/n/<namespace>/...，第二个 segment 就是 token。
- 当前测试只把 token 放在 query string，未覆盖 OCI PAR 的 path-token 形式。
- 受控异常 probe 传入真实形状的 /p/secret-token/... URL 后，脱敏结果仍含 secret-token。oci_push 在异常中拼入原始 transport exception；list 和 push-strategy 也直接打印原始异常。

**影响**：网络异常、日志或 CLI 输出可泄漏可写 PAR 凭据，违反 I19。

**建议**：按 OCI PAR 格式彻底遮蔽 token segment；对 exception 做统一 URL 清洗，不把原始 exception 直接串入输出。补 path-token、query-token 与 exception 自带完整 URL 的测试。

### H4 — 用户可控路径能越过 workspace，push 也会跟随外部符号链接

**证据**

- workflow.create_track() 验证 track_id，但未验证 direction；direction 直接加入 strategies/ 和 tracks/ 路径。probe 用 ../../outside 创建 track 后，在 workspace 外成功写出 track 记录。
- push-runs 把 direction、track 和 manifest 中的 run_id 直接拼入 staging 目录；没有拒绝绝对路径、.. 或路径分隔符。恶意/损坏 manifest 可令复制目标越过临时 staging 根。
- oci_push.plan_push() 对 rglob() 结果用 is_file() 并读取文件；符号链接目标会被当作普通文件。probe 在 alpha/features/leak.py 放置指向 workspace 外秘密文件的符号链接，计划将外部内容作为 immutable feature 上传。

**影响**：工作流命令可在 Lyra 目录外写文件；push 可能把仓库外的凭据或任意本地文件上传到 OCI。

**建议**：所有 direction、track、run、branch 标识都按单一路径组件验证；resolve 后强制目标仍在根目录内；拒绝遍历或上传符号链接，并对复制源和目标做边界检查。

### H5 — R12 规定的兄弟分支命名无法创建或推送

**证据**

- requirements R12 和 oci-alpha-layout 明确使用 v02a.yaml、v02b.yaml、v03a.yaml、v04ab.yaml 表示同代候选及交叉分支；“一个诊断派生多个候选”是核心流程。
- workflow._BRANCH_NAME_RE 与 oci_push._VNN_RE 只接受无后缀的 v<数字>。probe 调用 new_version(..., branch="v02a") 得到 WorkflowError；手写 v02a.yaml 又会被 I17 分类为 unclassified。
- #95 为使自产 YAML 可推而收紧到 vNN，修复了自产文件分类不一致，却让命名契约与 R12 的版本树样例冲突。

**影响**：标准兄弟分支及交叉命名被拒，AI 无法按既定树表达同一父版本的多条演进路线；即使手动写出也不能同步。

**建议**：将命名解析、new-version 校验和 I17 分类统一扩展到已定义的 generation + branch suffix + cross suffix 规则，并测试 v02a/v02b/v04ab 的创建、编译、push 和重复检测。

### H6 — track context 不是自包含文件，并混入其他 track 的 lessons

**证据**

- R12/0007 D5 要求每 track 独立拥有 hypothesis 快照引用、lessons、候选及 run 归属；requirements 还要求 context 含 hypothesis、活跃分支完整 YAML 与 feature 清单。
- render_context(track=...) 仍从 strategies/<direction>/lessons.md 读取共享 lessons；只输出 hypothesis 路径与 hash，不输出冻结内容；活跃分支只写文件名/parent，不含 YAML 正文，也没有 feature 清单。
- probe 选 track alpha 时看到了另一 track 的 lessons；v01.yaml 中的 sma_20_above_sma_50 则不在 context 中。
- 代码把各 track 的新候选写在方向根目录，而不是 proposal 所列的 tracks/<track_id>/；track record 只保存 hypothesis hash，context 仍读取可变的当前 hypothesis 文件。

**影响**：AI 不能只依据 context 文件独立工作；它看不到策略参数，又可能读到其他 AI 的研究结论或已变更的假设，破坏“各自节奏、互不影响”的核心要求。

**建议**：落实 per-track lessons/candidates/run provenance；context 写入 track 固定的 hypothesis 内容或明确可验证的不可变快照、每个活跃 YAML 全文、features 清单及本 track 的 sibling run comparison。共享规则和冻结行情可引用共同 snapshot。

### H7 — 兄弟 run 摘要会匹配错版本、跨方向串线，并只报告一个标的

**证据**

- workflow._runs_for_branch() 接受 direction 参数却不使用；遍历整个 runs 根目录，也不按 track 归属过滤。
- fallback 条件是 branch in spec；probe 显示请求 v1 会把 spec_id=v10 当作匹配。
- metrics.json 有多个 per_instrument 时，代码只取 next(iter(per.values()))；probe 有 EURUSD=1 笔和 GBPUSD=99 笔，输出只保留一个标的。
- 因此 compare_siblings() 中显示的 best 也建立在可能串线/遗漏标的的摘要之上。

**影响**：continue / prune / cross 判断可依据错误分支、方向或单一偶然标的做出；报告与 AI 搜索排序不可信。

**建议**：run provenance 必须有可验证的 direction、track_id、strategy file/hash 和 run_id；严格相等匹配分支身份；按 R5 保留各标的完整指标，禁止只取 JSON 第一个标的。

### H8 — push-runs 可能选中旧 run，并把未校验/无归属的文件永久归档

**证据**

- push_runs() 对同一个 runs/<name>/ 下的 manifest glob 排序后只拿第一个。0006 已将目录细分为日期/run_id，但命令没有日期或 run_id 参数；多次运行时不能选择目标 run。
- 代码只在 manifest 有 direction 时比较其值；未核对 manifest.run_id 与父目录，也不检查 artifacts 的必需清单或 SHA256，直接复制 manifest 同目录所有文件。
- 现有 test_push_runs_maps_to_direction_track_runid 故意使用空 artifacts、伪造的 b'PAR1' trades.parquet，仍断言 push 成功。
- --track 只写进 OCI 目录路径，原 manifest 被原样复制，没有按 D5 增补 track_id，归档后 run 本身仍不声明所属 track。

**影响**：选错 run 或本地已损坏的 artifact 会被作为 immutable 内容正式上传；manifest 无法独立证明 OCI 路径中的 track 归属。

**建议**：提供精确 run_id 选择；上传前验证 schema、manifest 路径一致性、每个 artifact 的存在性及 SHA256；将 track provenance 写入可审计的 manifest/sidecar，并测试缺失、篡改、错位与多个候选 run。

### H9 — 常规 backup 不会归档默认 lyra run 输出，也不映射规范 OCI 路径

**证据**

- runner 默认把产物写到 ~/.lyra/runs；_push_all_roots() 只扫描 resolve_data_root(...).parent 下的 workspace，并没有把默认 ~/.lyra/runs 加入 push roots。
- 即使用户把 runs 放在 workspace 内，普通 push/backup 会原样保留 runs/<name>/<date>/<run_id>；只有独立 push-runs 命令实现 runs/<direction>/<track>/<run_id> 映射。
- push_direction() 的文档说会推策略与 runs 切片，实际只调用 push_strategy()。

**影响**：最常用的一键备份可能漏掉刚完成的 run；被扫描到的 run 也可能进入错误的 OCI 路径，破坏 O2/D7。用户必须另行手动运行一个容易选错 run 的命令。

**建议**：让 backup/push 使用与 push-runs 相同的逐 run manifest 验证和规范路径映射，并纳入 Lyra 默认 runs 根目录；删除或实现 push-direction 的 runs 契约。

### H10 — 可变 track index 被标为 append-only，第一次改动就过不了 I17

**证据**

- strategies/<direction>/index/*.json 按 I17 分类为 append-only。
- create_track() 创建 active=[]；new_version() 把 active 改为 [v02] 并重写 JSON。probe 用初始 index 与新增一个分支后的 index 调用 is_append_only_superset()，结果为 False。
- prune_branch() 会从 active 删除条目并加到 pruned；旧 JSON 的行因此不再是新 JSON 的有序子序列，同样不能 push。

**影响**：track 创建后首次 fork 或 prune 产生的 index 更新会被 append-only 门禁拒绝；本地 AI 分支不能可靠同步到 OCI，达到 cap 后也无法把 prune 结果同步并继续迭代。

**建议**：将 index 改为真正只追加的事件日志（create/activate/prune 等事件），或为可变快照设计经审查的版本/冲突协议；不要用“放宽行比较”绕过 I17。

## P2：0007 收口前需要明确的设计与文档缺口

### M1 — track 的“冻结基线”没有真实 catalog/data snapshot，也没有随 OCI 持久化

workflow._baseline_for_direction() 查找 data/features/catalog.json；Lyra 实际使用 data/catalog.duckdb（catalog.json 只由 workflow 测试临时造出）。因此正常环境中的 feature_catalog_sha256 会是 None；代码也没有记录 data snapshot id。track 记录写在 workspace/tracks/下，而 push walker 明确跳过 tracks/顶层；OCI 只得到策略 index，不得到冻结基线记录。跨 workspace 恢复时就无法重建当初的快照身份。

**建议**：按真实 catalog / feature snapshot API 捕获确定性身份，将 data snapshot、规则版本和假设快照写入可同步的 append-only track metadata；测试应使用真实 catalog fixture，并包含从 OCI 另一工作区恢复的用例。

### M2 — backup 的规范仍冲突，0007 决策文档状态也没对齐

HLD §2.5 把 lyra backup 定义为 pull + push + 冲突检测；0007 D10 和实现把 backup 定义为 push-only。requirements R7 只写本地 strategies/runs 变更时的一键 sync。实现选择可以成立，但目前没有由 HLD 修订记录解决这一冲突。另，0007 元信息仍显示“提案”，§7 审批勾选仍未完成，而 rev0.4 和 ACTION_LOG 写为已实施/全仓测试通过。

**建议**：先确定 backup 是 push-only 还是 pull+push，再同步 HLD、requirements、0007 中英文案；实现状态、审批项和验收条件应区分“代码审查通过”与“R10 真实桶验收待完成”。

### M3 — 文档承诺 OCI SDK auth fallback，程序只有无凭据 requests session

0007 D4 / 附录 C1、HLD §2.5 都写可用 auth_file / OCI SDK；cli._push_transport() 实际仅创建 requests.Session，把 PAR URL 直接交给 GET/PUT，未读取 auth_file，也没有 SDK signer。遇到只读 PAR 时，错误提示“use SDK auth”并不能变成可运行的 fallback。真实桶 R10 尚未验证。

**建议**：实现并覆盖 auth_file 认证路径，或把该能力明确移出本次承诺并给出只读 PAR 下的受支持行为；之后再做 R10 真实桶读写验收。

### M4 — 多文件 push 没有原子性，回滚文档对失败状态过于乐观

oci_push.push() 逐文件 PUT；每个文件全量 read_bytes()，任一后续 PUT 失败只抛错，不回滚此前对象。排序后 manifest.json 还可能先于其他 run artifact 上传，远端会暂时出现“manifest 已发布但文件不全”的 run。0007 §6 却写未成功上传不会留下半状态。大 Parquet 同时全量读入也会造成内存峰值。

**建议**：至少将 manifest 作为最后发布标记，并明确部分上传/重试的恢复协议；若要承诺原子发布，需使用 staging/commit marker 或等价机制。上传采用分块或流式读取，文档不能把逐对象 PUT 描述成事务。
