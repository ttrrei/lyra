### 缺陷 1：【致命数据污染与列丢弃】首文件单点列嗅探致多文件下 DQ2 完全被绕过且静默丢弃报价列

* **涉及文件**：[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L197-L212) (`clean_csv_to_bronze`)、[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L265-L288) (`clean_csv_to_bronze_parquet`)。
* **严重级**：**Critical**
* **代码现实**：
  ```python
  # lyra/clean.py:265-288
  first = sorted(csv_dir.rglob("*.csv"))[0]
  cols = {
      r[0].lower()
      for r in con.execute(
          "DESCRIBE SELECT * FROM read_csv(?, header=TRUE, auto_detect=TRUE) LIMIT 1",
          [str(first)],
      ).fetchall()
  }
  missing = [c for c in REQUIRED_INPUT if c not in cols]
  if missing:
      raise CleanInputError(...)
  present = {c for c in PAYLOAD if c in cols}
  inner = _clean_sql(csv_dir, present)
  _assert_quality(con, inner, present)
  out_cols = ["instrument", "time"] + [
      c for c in ALWAYS_PRESENT if c not in ("instrument", "time")
  ]
  for c in sorted(present):
      if c not in out_cols:
          out_cols.append(c)
  select = ", ".join(out_cols)
  con.execute(f"COPY (SELECT {select} FROM ({inner}) t) TO {_quote(out_path)} (FORMAT PARQUET)")
  ```
* **一句话证据**：
  `present` 仅根据字典序首个文件 `sorted(csv_dir.rglob("*.csv"))[0]` 嗅探，当目录中存在无 bid/ask 的历史平铺 CSV 与回补的 OANDA 子目录 CSV 时，首文件无报价列导致 DQ2 校验规则完全不生成，下游含反向 spread 的脏数据静默入库，且 bronze 写出时静默丢弃后续文件的全部 `bid_*`/`ask_*` 列。
* **破坏性分析**：
  1. **DQ2 规则整体脱落**：若目录中有历史平铺 CSV `01_flat.csv`（仅包含 mid 价格），首个探测文件就是它，`present` 不含任何 `bid_*`/`ask_*`。在 `_quality_checks` 中，`point_clauses` 计算为空，`bad_spread` 规则完全不注入 `checks`。即使 OANDA 回补目录中包含严重反向 spread（如 `ask_o < bid_o`），`_assert_quality` 根本不会执行 spread 检查！
  2. **脏数据写入且丢弃报价列**：`out_cols` 仅从 `present` 挑选列，导致 DuckDB COPY 写入 bronze parquet 时，后续 OANDA CSV 中所有的 `bid_*` 与 `ask_*` 列直接被 `SELECT` 丢弃，而其包含的反向 spread 脏数据却被洗入 bronze，违反不变量 I23。
  3. **后续文件缺列静默穿透**：`REQUIRED_INPUT` 校验同样只对首个文件生效。若后续文件缺失 `mid_l`，DuckDB 的 `union_by_name` 将缺列补 `NULL`，而 DQ1 中包含 NULL 的比较在 SQL 中计算为 `NULL`（非 TRUE），导致 `mid_l` 全为 NULL 的行绕过 DQ1 写入 bronze。
* **最小复现**：
  ```python
  import tempfile, duckdb
  from pathlib import Path
  from lyra.clean import clean_csv_to_bronze_parquet

  with tempfile.TemporaryDirectory() as td:
      p = Path(td)
      # 01.csv 仅含 mid（字典序排在首位）
      (p / "01.csv").write_text("instrument,time,volume,mid_o,mid_h,mid_l,mid_c,is_complete\nX,2020-01-01T00:00:00Z,1,10,12,9,11,True\n")
      # 02.csv 含有 OANDA 完整报价，但 ask_o (5) < bid_o (10) 严重反向
      (p / "02.csv").write_text("instrument,time,volume,mid_o,mid_h,mid_l,mid_c,bid_o,bid_h,bid_l,bid_c,ask_o,ask_h,ask_l,ask_c,is_complete\nY,2020-01-01T00:01:00Z,1,10,12,9,11,10,12,9,11,5,12,9,11,True\n")
      out = p / "out.parquet"
      clean_csv_to_bronze_parquet(p, out)
      con = duckdb.connect()
      cols = [r[0] for r in con.execute("DESCRIBE SELECT * FROM read_parquet(?)", [str(out)]).fetchall()]
      assert "bid_o" not in cols  # 证据：OANDA 的报价列被投影静默丢弃，且反向 spread 未被拦截
  ```

### 缺陷 2：【致命时序崩溃】月末最后一分钟发起回补触发 `m_start > m_end` 异常崩溃

* **涉及文件**：[`lyra/oanda.py`](file:///home/ubuntu/work/lyra/lyra/oanda.py#L365-L367) (`backfill_window`)、[`lyra/oanda.py`](file:///home/ubuntu/work/lyra/lyra/oanda.py#L184) (`fetch_candles`)。
* **严重级**：**Critical**
* **代码现实**：
  ```python
  # lyra/oanda.py:365-367
  m_end = next_month_start - timedelta(minutes=1)
  m_start = max(m_start, start)
  m_end = min(m_end, end)
  ```
* **一句话证据**：
  `backfill_window` 粗暴以 `next_month_start - timedelta(minutes=1)` 计算月末边界 `m_end`，当用户给定的起始时间 `time_from` 落在月末最后一分钟内（例如 `2020-01-31T23:59:30Z`）时会导致 `m_start > m_end`，调用 `fetch_candles` 立即触发 `OandaError("--to must be at or after --from")` 崩溃。
* **破坏性分析**：
  1. `next_month_start - timedelta(minutes=1)` 计算出的 `m_end` 为 `23:59:00Z`。
  2. 若 `start` 在 `23:59:01Z` 至 `23:59:59Z` 之间，`m_start = max(00:00:00Z, start) = start`，而 `m_end = min(23:59:00Z, end) = 23:59:00Z`。
  3. 传递给 `fetch_candles` 的参数为 `time_from="23:59:30Z", time_to="23:59:00Z"`，在 L184 命中 `if end < start: raise OandaError` 直接抛错终止回补。
  4. 此外，当用户使用秒级粒度（`S5`、`S10`、`S15`、`S30`）时，硬编码减去 1 分钟会导致每月末 59 秒的数据恒定被截断丢失。
* **最小复现**：
  ```python
  import tempfile
  from pathlib import Path
  from lyra.oanda import backfill_window

  with tempfile.TemporaryDirectory() as td:
      backfill_window(
          Path(td), "GBP_USD",
          "2020-01-31T23:59:30Z", "2020-02-01T00:05:00Z",
          token="dummy_token", dry_run=False,
      )
      # 直接抛出崩溃：lyra.oanda.OandaError: --to must be at or after --from
  ```

### 缺陷 3：【严重假续传断层】非整月局部回补导致后续同月全量回补静默跳过，产生永久隐式数据缺口

* **涉及文件**：[`lyra/oanda.py`](file:///home/ubuntu/work/lyra/lyra/oanda.py#L368-L372) (`backfill_window`)。
* **严重级**：**Major**
* **代码现实**：
  ```python
  # lyra/oanda.py:368-372
  out = _chunk_path(csv_root, instrument, month, granularity)
  if out.exists() and out.stat().st_size > 0 and not force:
      log(f"[{instrument}] month {month:%Y-%m} already present ({out.name}); skipping.")
      written.append(out)
      continue
  ```
* **一句话证据**：
  断点续传仅凭月度文件是否存在且非空（`out.exists() and out.stat().st_size > 0`）即判定跳过，对非整月（局部窗口）回补生成的历史文件发生假续传，导致同月后续回补静默跳过、产生永久隐式数据缺口。
* **破坏性分析**：
  1. `_chunk_path` 严格生成月首固化文件名 `{instrument}_{granularity}_{YYYYMM}01T000000Z.csv`。
  2. 若用户曾尝试拉取过局部区间（如仅拉取月初 `2020-01-01` 至 `2020-01-02`），或者先前回补被用户手动中断，磁盘上已留下一个仅有几天数据的非空 CSV 文件。
  3. 当用户后续发起完整回补（如 `--from 2020-01-01 --to 2020-01-31`）时，程序检测到该文件存在且大小大于 0，便直接跳过该月份。
  4. 结果是该月后续数十天的数据被永久静默丢弃，且 CSV 文件名仍标记为 `20200101T000000Z.csv`，使上层误以为整月数据已完整回补。
* **最小复现**：
  ```python
  import tempfile
  from pathlib import Path
  from lyra.oanda import backfill_window

  with tempfile.TemporaryDirectory() as td:
      root = Path(td)
      partial_file = root / "GBP_USD" / "GBP_USD_M1_20200101T000000Z.csv"
      partial_file.parent.mkdir(parents=True)
      partial_file.write_text("instrument,time,volume,mid_o,mid_h,mid_l,mid_c,is_complete\nGBP_USD,2020-01-01T00:00:00Z,1,1,1,1,1,True\n")

      # 用户后续期望完整回补 1 月全部数据
      backfill_window(
          root, "GBP_USD",
          "2020-01-01T00:00:00Z", "2020-01-31T23:59:00Z",
          token="dummy_token", dry_run=False,
      )
      # 文件未被更新续传，记录数仍仅有 1 条
      assert partial_file.read_text().count("\n") == 2
  ```

### 缺陷 4：【严重边界漏检】非同名点 Partial-Quote 输入致 DQ2 规则完全脱落，全 bar 反向 spread 无法防御

* **涉及文件**：[`lyra/clean.py`](file:///home/ubuntu/work/lyra/lyra/clean.py#L117-L124) (`_quality_checks`)。
* **严重级**：**Major**
* **代码现实**：
  ```python
  # lyra/clean.py:117-124
  point_clauses = [
      f"bid_{p} IS NOT NULL AND ask_{p} IS NOT NULL AND ask_{p} < bid_{p}"
      for p in ("o", "h", "l", "c")
      if f"bid_{p}" in present and f"ask_{p}" in present
  ]
  if point_clauses:
      checks["bad_spread"] = " OR ".join(point_clauses)
  return checks
  ```
* **一句话证据**：
  `_quality_checks` 严格按单一价格点名字配对（`f"bid_{p}" in present and f"ask_{p}" in present`），若 partial-quote 来源包含错位报价点（例如仅含 `bid_l` 与 `ask_h`，或 `bid_o` 与 `ask_c`），`point_clauses` 为空导致 `bad_spread` 规则完全不生成，即使 `ask_h < bid_l`（全 bar 最高卖价低于最低买价，物理不可能）也静默放行。
* **破坏性分析**：
  1. 在 partial quotes 场景下，数据源若只包含买方低价 `bid_l` 和卖方高价 `ask_h`，遍历 `("o", "h", "l", "c")` 时，没有任何一个点 $p$ 能够同时满足 `bid_p` 和 `ask_p` 同时存在于 `present`。
  2. 导致 `point_clauses` 为空列表，整项 DQ2 检查未激活，`checks` 中完全没有 `bad_spread` 项。
  3. 即使输入数据中某一行的最高卖价仅为 5.0，而最低买价却为 10.0（整根 bar 期间任意时刻卖价都低于买价，完全反向），DQ2 依然视若无睹，静默写入 bronze。
  4. 此外，DQ1 与 DQ2 均缺少针对 IEEE 754 `NaN` 的 `isfinite()` 防御（DQ3 有而 DQ1/DQ2 无），当 `mid_h` 或 `ask_p` 为 `NaN` 时，DuckDB 的比较计算均返回 `False`，导致 `NaN` 报价静默逃逸。
* **最小复现**：
  ```python
  import tempfile
  from pathlib import Path
  from lyra.clean import clean_csv_to_bronze_parquet

  with tempfile.TemporaryDirectory() as td:
      p = Path(td)
      # 输入具备 bid_l 与 ask_h，无同名配对点；ask_h(5) < bid_l(10)
      (p / "bad.csv").write_text("instrument,time,volume,mid_o,mid_h,mid_l,mid_c,bid_l,ask_h,is_complete\nX,2020-01-01T00:00:00Z,1,10,12,9,11,10,5,True\n")
      out = p / "out.parquet"
      clean_csv_to_bronze_parquet(p, out)
      assert out.exists()  # 静默成功写入，未抛出 DataQualityError
  ```

### 缺陷 5：【凭证泄露隐患】`OandaConfig.api_token` 未设 `repr=False` 致日志与调用栈明文泄密

* **涉及文件**：[`lyra/config.py`](file:///home/ubuntu/work/lyra/lyra/config.py#L42-L56) (`OandaConfig`)。
* **严重级**：**Minor**
* **代码现实**：
  ```python
  # lyra/config.py:42-56
  @dataclass(frozen=True)
  class OandaConfig:
      api_token: str = ""
      host: str = "api-fxpractice.oanda.com"
      price: str = "MBA"
      granularity: str = "M1"
  ```
* **一句话证据**：
  `OandaConfig` 数据类中的 `api_token` 字段未声明 `repr=False`，导致在异常调用栈展示、日志输出或 `repr(ocfg)` 中直接打印出明文 API Token，违反 I12/I19 凭证不泄露边界。
* **破坏性分析**：
  在 Python dataclass 中，默认所有属性的 `repr=True`。在流水线调试、日志采集（如打印配置上下文）或测试报错堆栈捕获时，`str(ocfg)` 或 `repr(ocfg)` 会将用户的机密 token 完整暴露在屏幕或持久化日志文件中。
* **最小复现**：
  ```python
  from lyra.config import OandaConfig
  cfg = OandaConfig(api_token="oanda_secret_key_abcdef123456")
  assert "oanda_secret_key_abcdef123456" in repr(cfg)  # 证据：明文输出
  ```

  # lyra/cli.py:151-155

## 二、 批次缺陷评估汇总表

| 编号 | 缺陷项 | 严重级别 | 涉及模块 | 核心风险 |
|---|---|---|---|---|
