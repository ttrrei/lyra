# 0006 指标与运行管线独立检验 + 对抗性检验（2026-11-10 批次1）

> **English**: [Independent and Adversarial Review of 0006](./对抗性review-2026-11-10-批次1.en.md)

## 范围与结论

本轮独立检查 0006 的需求映射、设计文档、lyra/metrics.py、lyra/runner.py、lyra/cli.py 与现有测试，重点核对 R4 融资日口径、R5 指标、I5 可复现身份、产物写入以及 per-instrument 执行边界。没有修改程序代码。

**结论：R5 指标核心公式大体符合定义，策略报告也保留了逐标的口径；但 0006 目前还不能视为满足 R4 / I5 的可靠研究运行管线。** 复现探针确认了融资日规则和特征输入改变时 run_id 仍可相同；同名同日的空交易重跑会保留旧交易文件，并将其列入新 manifest。另有流式设计未兑现、空产物契约、决策文档过期以及月度测试未覆盖零开仓月等问题。

严重度：**P1** 会改变融资成本、运行身份或报告产物的可信度；**P2** 是可扩展性、契约、文档或测试覆盖风险。

## P1：必须先处理的发现

### H1 — 默认融资仍按自然日计，违反 R4 的交易日口径

**证据**

- docs/requirements.md §R4 明确要求 financing 按持仓区间内的**交易日**计数，周末及市场节假日不计。
- runner.run_strategy() 的默认 trading_days_for=None 会将 None 传给 simulate()；交易引擎据时间戳计算自然日。CLI lyra run 没有交易日历选项，也没有传入计数器。
- report.md 会把该口径标成 calendar/natural days，并称交易日口径是未来增强。相反，需求和 ACTION_LOG 当前状态仍要求后续接入真实交易日历；0006 决策稿却把 O17 写成已由自然日收口。
- 现有 test_run_financing_wired 只验证成本非零和自定义计数器被调用，没有验证跨周末/假日时默认值排除非交易日。

**影响**：持仓跨周末或假日时融资费用被多计，净收益、年化分数及策略间排序可能改变。逐笔计数器接口解决了“每笔交易可单独计数”的问题，但没有提供交易日历，也没有使自然日符合 R4。

**建议**：在融资费率非零时，默认接入可版本化的真实市场日历并 fail-closed；若产品决定采用自然日，则需先正式修订 R4/O15 及相应双语文档和测试，不能只以 O17“已收口”覆盖现行要求。

### H2 — run_id 未包含实际影响交易结果的特征值与融资计数器语义

**证据**

- _data_digest() 只摘要 view 名、instrument 和 OHLC 五列（time、mid_o/h/l/c），不摘要策略 SQL 实际读取的特征值。
- _compute_run_id() 只记录 trading_days_basis 的 "trading" / "calendar" 标签，没有纳入日历版本、每笔返回的交易日数或计数器身份。
- 对抗探针保持 OHLC、策略和路径不变，只把宽表中的注册特征 rsi_6 从全 100 改为全 0：两次 run_id 相同，但成交从 1 笔多单变成 3 笔空单。
- 同一策略、同一数据用返回 1 和 2 的两个 trading_days_for 回调运行：run_id 相同，样例交易融资成本从 0.001 变为 0.002。

**影响**：不同交易结果会共享同一个运行身份。依赖 run_id 做去重、缓存、比较或 OCI 不可变路径时，可能把两个不同实验当成同一个，破坏 I5 的审计性和可复现性。

**建议**：对实际执行查询消费的全部特征输入建立内容身份；融资日历/规则需有稳定的显式版本或内容摘要，并把实际生效的规则身份纳入 run_id。匿名 Python 回调无法自动复现，应要求调用方提供稳定的 provenance 标识，或拒绝将其用于可复现运行。

### H3 — 同名同日运行会覆盖共享目录，零交易重跑会留下旧 trades.parquet

**证据**

- 输出路径是 <out>/<name>/<YYYYMMDD>，不含 run_id；已存在目录以 exist_ok=True 复用。
- _write_artifacts() 仅在行数非零时写 signals.parquet / trades.parquet，不会删除旧文件。
- 对抗探针先在该目录写出有交易的结果，再以相同 name/date 改成不产生任何交易的策略运行：第二次 run_id 已变化、内存交易数为 0，但磁盘 trades.parquet 字节未变。新 manifest 又对这个旧文件计算并记录了有效 SHA256。

**影响**：新 run 的指标显示零交易，而配套文件仍包含旧交易；哈希只能证明文件未损坏，不能证明文件属于 manifest 的 run_id。后续 report、OCI push 或策略比较可能消费错误产物。

**建议**：每个 run_id 使用独立目录；先写入唯一临时目录，完整校验后原子发布；禁止静默复用已有 run 目录。空结果也需覆盖或拒绝旧目录，不能留下上次产物。

## P2：应纳入 0006 处置的发现

### M1 — 设计承诺 per-instrument streaming，代码却先全量读入并保留全体 bars

决策稿 D3 写的是每个 instrument 独立 DuckDB 作用域、逐标的流式处理。当前 runner 对完整 plan.sql 调用 fetchall()，接着把每一行复制成 Python dict 并保存在 bars_by_inst，直到运行完成；之后 _data_digest() 还会按标的再次 fetchall() OHLC 行。数据规模增大时，查询结果、对象化 bars 和 trades 会同时占内存。当前只隔离了 per-instrument 的 simulate() 异常，SQL 查询或前置装配失败仍会使整次 run 失败。

**建议**：以 instrument/time 排序的批次或游标逐标的消费，完成后释放输入 bars；将 I16 的隔离边界写清楚，并为大数据集增加有代表性的内存/流式验证。

### M2 — 零交易时不生成规定的 Parquet 文件，manifest 也漏掉 metrics.json 哈希

决策稿 D8 的布局将 signals.parquet、trades.parquet、metrics.json、report.md 都列为 run 产物，并要求每个产物进入 manifest 的 SHA256。当前 fresh empty run 不会创建零行 trades.parquet（若无信号行，也不会创建 signals.parquet）；manifest 的哈希循环只涵盖 signals、trades 和 report，漏掉关键消费文件 metrics.json。现有空运行测试只检查 manifest 存在，没有检查完整文件集及零行 schema。

**影响**：下游消费者无法依赖稳定文件布局；metrics.json 被改动或损坏也无法通过 manifest 校验。

**建议**：无数据时写出带固定 schema 的零行 Parquet；对 D8 中所有规定产物计算并验证哈希。若要缩小哈希范围，需在决策文档中明确列出例外。

### M3 — 0006 决策文档的融资、SQL 与测试契约未跟上 #88

双语 docs/decisions/0006-metrics-and-runner 文档仍描述旧接口：trading_days、扁平 --financing-days、SQL 与 OHLC JOIN；而代码及 #88 已改为 trading_days_for(entry, exit)、删除该 CLI flag，并由 compiler SQL 直接投影 OHLC。测试矩阵也仍写旧参数。文档还把自然日称作 R4/O15 兼容并宣告 O17 关闭，和 requirements §R4、ACTION_LOG 当前状态中的“需接入真实交易日历”冲突。

**建议**：按决策文档只增不删的惯例新增修订/勘误，更新中英成对的接口、数据流、融资裁定及测试矩阵；明确说明 O17 接口能力与 R4 交易日日历合规不是一回事。

### M4 — I5 的“bit-for-bit”范围与 generated_at 例外不一致

0006 I5 写“同一清单 → 同一产物”，但 manifest.json 含每次运行变化的 generated_at；现有可复现测试主动移除此字段后再比较。因此实际契约是“确定性数据产物相同，manifest 的生成时间可变”，并非所有产物逐字节一致。

**建议**：在 I5/D5 中明确排除 generated_at 或将生成时间移出被承诺逐字节复现的产物；测试应按写明的契约验证，而不是靠测试注释隐式缩小范围。

### M5 — “零开仓月”测试没有真的断言任何月份为零

test_metrics_monthly_rows_zero_open_months_kept 注释称 3 笔都在 2024-01，但第三笔实际时间是 2024-02-03，断言结果为 1 月 2 笔、2 月 1 笔。runner 级测试只有 2024-01 一个研究月，并断言开仓数 >= 0。当前测试集没有用例验证窗口内月份 actual_entries == 0 且该月仍被保留。_monthly_rows() 的实现看起来会补齐窗口月份，但关键不变量没有回归保护。

**建议**：用 1 月有交易、2 月无交易、3 月有交易的窗口，明确断言 2 月行存在且所有月度数值为 0。

## 验证与对抗自检

- 0006 专项：.venv/bin/python -m pytest -q tests/test_metrics.py tests/test_runner.py → **19 passed**。
- 全仓：.venv/bin/python -m pytest -q → **223 passed**。
- 静态检查：.venv/bin/python -m pyflakes lyra tests → 无输出。
- 复现探针：特征输入变更但 run_id 不变；两个融资回调的结果不同但 run_id 不变；同目录从有交易切到零交易后旧交易文件仍被新 manifest 接纳。
- 对抗性自检：检查了相反解释——逐笔 counter 并不自动等于交易日历；manifest 文件哈希并不能证明文件属于当前 run；R5 月度函数实现可补零行也不能替代真实零开仓测试。以上均有代码路径或受控探针支撑。

测试全绿说明现有断言通过，不会推翻上述发现：这些反例目前没有被测试覆盖。除三条 P1 外，R5 指标集、禁止组合收益字段、逐标的统计及报告主要元数据结构总体与目标一致。
