# Independent and Adversarial Review of 0006 (2026-11-10, Batch 1)

> **中文**: [0006 指标与运行管线独立检验 + 对抗性检验](./对抗性review-2026-11-10-批次1.md)

## Scope and conclusion

This independent review checked the 0006 requirements mapping, design document, lyra/metrics.py, lyra/runner.py, lyra/cli.py, and existing tests. It focused on the R4 financing-day basis, R5 metrics, I5 run identity, artifact writing, and per-instrument execution boundaries. No program code was changed.

**Conclusion: the core R5 metric formulas mostly match their definitions, and reports retain per-instrument metrics; however, 0006 is not yet a reliable run pipeline under R4/I5.** Reproduction probes confirmed that changing either financing-day rules or feature inputs can leave run_id unchanged. A same-name, same-day rerun with zero trades also retains the previous trade file and records it in the new manifest. Additional findings cover the unimplemented streaming design, empty-artifact contract, stale decision documentation, and missing zero-entry-month coverage.

Severity: **P1** findings can change financing costs, run identity, or artifact trustworthiness; **P2** findings concern scalability, contracts, documentation, or test coverage.

## P1: Findings to address first

### H1 — Default financing uses calendar days, contrary to R4's trading-day basis

**Evidence**

- docs/requirements.md §R4 explicitly requires financing to count **trading days** within the holding interval, excluding weekends and market holidays.
- runner.run_strategy() defaults trading_days_for=None and passes None to simulate(); the engine then derives natural/calendar days from timestamps. The lyra run CLI has no trading-calendar option and passes no counter.
- report.md labels this basis calendar/natural days and describes trading-day counting as a future enhancement. In contrast, the requirements and current ACTION_LOG state still require integration of a real trading calendar; the 0006 decision doc says O17 was closed using calendar days.
- test_run_financing_wired only checks that cost is nonzero and that a custom counter is honored. It does not verify that the default excludes weekends or holidays.

**Impact**: financing is overstated for positions held across weekends or holidays. Net returns, annualized scores, and strategy rankings can change. A per-trade counter solves the ability to count each trade separately, but it neither supplies a trading calendar nor makes calendar days compliant with R4.

**Recommendation**: when financing bps are nonzero, use a versioned real market calendar by default and fail closed if it is unavailable. If the product instead intends calendar days, formally revise R4/O15 and the paired documentation and tests first; O17's “closed” label alone cannot override the current requirement.

### H2 — run_id omits feature values and financing-counter semantics that affect results

**Evidence**

- _data_digest() hashes only the view name, instrument, and five OHLC/time columns. It does not hash the feature values actually read by the strategy SQL.
- _compute_run_id() stores only the "trading" / "calendar" value of trading_days_basis; it does not include the calendar version, per-trade day counts, or counter identity.
- An adversarial probe kept OHLC, strategy, and paths unchanged and changed the registered wide-table feature rsi_6 from all 100s to all 0s. Both runs had the same run_id, but trades changed from one long trade to three short trades.
- With the same strategy and data, two trading_days_for callbacks returning 1 and 2 produced the same run_id, while sample trade financing cost changed from 0.001 to 0.002.

**Impact**: different trading outcomes can share one run identity. Any deduplication, caching, comparison, or immutable OCI path keyed by run_id can treat distinct experiments as the same run, undermining I5 auditability and reproducibility.

**Recommendation**: derive content identity from every feature input consumed by the executed query. Give the financing calendar/rule a stable explicit version or content digest, and include that identity in run_id. Anonymous Python callbacks cannot be reproduced automatically; require a stable provenance identifier or reject them for reproducible runs.

### H3 — Same-name, same-day runs share a directory; an empty rerun retains stale trades.parquet

**Evidence**

- Output paths are <out>/<name>/<YYYYMMDD> and omit run_id; an existing directory is reused with exist_ok=True.
- _write_artifacts() writes signals.parquet / trades.parquet only when rows are non-empty and does not remove old files.
- An adversarial probe first wrote a run with trades, then reran a no-trade strategy with the same name/date. The second run_id changed and its in-memory trade count was zero, but the on-disk trades.parquet bytes were unchanged. The new manifest then calculated and recorded a valid SHA256 for that old file.

**Impact**: the new run's metrics report zero trades while its trade file contains the previous run's trades. The checksum proves the file was not corrupted; it does not prove the file belongs to the manifest's run_id. A later report, OCI push, or strategy comparison may consume the wrong artifact.

**Recommendation**: use a unique directory per run_id; write into a unique staging directory and publish atomically after validation; never silently reuse an existing run directory. Empty results must replace or reject old artifacts rather than leave prior-run files behind.

## P2: Findings to include in 0006 disposition

### M1 — The design promises per-instrument streaming, but the code materializes and retains all bars first

Decision D3 specifies an independent DuckDB scope and streaming processing for each instrument. The runner currently calls fetchall() on the complete plan.sql result, copies each row into a Python dict, and retains all instruments in bars_by_inst until the run finishes. _data_digest() later calls fetchall() for OHLC rows again, one instrument at a time. With larger datasets, query rows, objectified bars, and trades coexist in memory. Only exceptions from per-instrument simulate() are isolated; failures in the SQL query or earlier row assembly still fail the whole run.

**Recommendation**: consume ordered batches or a cursor one instrument at a time and release bars after processing. Clarify I16's failure-isolation boundary and add representative memory/streaming verification for large datasets.

### M2 — Empty runs omit required Parquet files, and the manifest omits the metrics.json hash

Decision D8 lists signals.parquet, trades.parquet, metrics.json, and report.md as run artifacts and requires each artifact's SHA256 in the manifest. A fresh empty run does not create a zero-row trades.parquet (and does not create signals.parquet if there are no signal rows). The manifest hash loop includes only signals, trades, and report, omitting the key consumer file metrics.json. The existing empty-run test checks only that a manifest exists; it does not check the complete file set or zero-row schemas.

**Impact**: downstream consumers cannot rely on a stable artifact layout, and changes or corruption to metrics.json cannot be detected through the manifest.

**Recommendation**: write zero-row Parquet files with fixed schemas when there is no data, and hash/verify every required D8 artifact. If the checksum scope should be narrower, list those exceptions explicitly in the decision document.

### M3 — The 0006 decision document's financing, SQL, and test contracts did not catch up with #88

The Chinese and English docs/decisions/0006-metrics-and-runner documents still describe the old interfaces: trading_days, flat --financing-days, and a SQL/OHLC join. The code and #88 instead use trading_days_for(entry, exit), remove that CLI flag, and project OHLC directly in compiler SQL. The test matrix also names the old parameter. The document further calls calendar days R4/O15-compliant and declares O17 closed, conflicting with requirements §R4 and the current ACTION_LOG statement that a real trading calendar is still needed.

**Recommendation**: append a new revision/correction according to the append-only decision-doc convention. Update the interface, data flow, financing ruling, and test matrix in both languages; distinguish O17's interface capability from R4 trading-calendar compliance.

### M4 — The “zero-entry month” tests never assert a month with zero entries

test_metrics_monthly_rows_zero_open_months_kept says all three trades are in January 2024, but the third trade is actually dated 2024-02-03; it asserts two January entries and one February entry. The runner-level test has only one study month (January 2024) and checks that the entry count is >= 0. Thus, no current test verifies that a month inside the window with actual_entries == 0 remains present with zero values. _monthly_rows() appears to fill months from the study window, but this key invariant has no regression protection.

**Recommendation**: use a window with trades in January and March and no trades in February, then explicitly assert that February is present and all monthly values are zero.

### M5 — I5's “bit-for-bit” scope conflicts with the generated_at exception

I5 says that the same manifest produces the same artifacts, but manifest.json includes a per-run generated_at value. The reproducibility test removes that field before comparing manifests. The actual contract is therefore “deterministic data artifacts match; manifest generation time may vary,” not byte-for-byte identity for every artifact.

**Recommendation**: explicitly exclude generated_at from I5/D5's byte-reproducibility promise or move it outside the artifacts covered by that promise. Tests should verify the written contract rather than narrow it implicitly in a test comment.

## Verification and adversarial self-check

- Focused 0006 suite: .venv/bin/python -m pytest -q tests/test_metrics.py tests/test_runner.py → **19 passed**.
- Full repository suite: .venv/bin/python -m pytest -q → **223 passed**.
- Static check: .venv/bin/python -m pyflakes lyra tests → no output.
- Reproduction probes: feature input changed with unchanged run_id; two financing callbacks returned different results with unchanged run_id; after rerunning in the same directory from trades to zero trades, the old trade file remained and was accepted by the new manifest.
- Adversarial self-check: tested contrary interpretations. A per-trade counter does not itself imply a trading calendar; a manifest file hash does not prove that the file belongs to the current run; and an implementation that can fill zero month rows does not replace an actual zero-entry regression test. Each conclusion is supported by code paths or controlled probes.

Passing tests show that current assertions pass; they do not refute these findings because the counterexamples are not covered. Apart from the three P1 findings, the R5 metric set, forbidden portfolio-return fields, per-instrument statistics, and main report metadata are generally aligned with the intended design.

## Recommended disposition

Address H1–H3 before treating 0006 as a stable input to 0007. Then align M1–M5 across implementation boundaries, bilingual design documents, and regression tests. This review records findings only; it does not change code or decision documents.
