### 缺陷 1：【致命架构断层】存储路径与 Snapshot ID 同 0002 及外部表 Catalog 体系严重脱节

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §1（L23）、§3.1（L134-137、L154-157）。
* **严重级**：**Critical**
* **现实陈述**：
  在 §3.1 中，0003 方案规划：
  1. 输出路径为：`data/features/<minutes>m/<snapshot_id>/<instrument>.parquet`；
  2. 声明：`特征宽表的 snapshot id = (market snapshot id, timeframe, FEATURE_VERSION, 注册表全参数集 sha256, ...) 的派生字符串`。
* **致命冲突剖析**：
  1. **输入源已无 `market snapshot id`**：在 0002 收口阶段（D4 决议），Lyra 已经**正式废弃了目录级 snapshot 状态机**，市场层统一落为单文件外部表：`<data_root>/ohlcv_5m/ohlcv_5m.parquet` 与 `<data_root>/ohlcv_1h/ohlcv_1h.parquet`。上游 0002 根本不存在所谓的 `market snapshot id`！0003 将一个已废除的幽灵概念作为派生输入，导致派生公式在第一项就无法取值。
  2. **“恒重算”与“目录级 snapshot”自相矛盾造成磁盘爆仓**：§3.1 承诺对齐 0002 A1 的“恒重算、恒覆盖”，每次执行无缓存。但如果输出路径中内嵌 `<snapshot_id>`，一旦 `FEATURE_VERSION` 或参数变动，每次运行就会生成一个全新的目录！旧特征目录（21 标的 × 多周期 = 数十个几百 MB 的 Parquet 文件）没有任何清理与轮转机制，将无休止堆积在本地磁盘，严重违背轻量运维与磁盘安全原则。
  3. **完全遗漏 Catalog 视图注册与下游对接**：0002 确立了 `Catalog`（DuckDB 外部表）作为下游统一消费层（`bronze / ohlcv_5m / ohlcv_1h`）。0003 生成的特征宽表是下游 0004 compiler 与 0005 trade engine 的直接底座，但 0003 全文**完全没有设计 Catalog 接入**（是否注册视图？按什么命名注册？如何支持多标的外部表并查？）。若 0004 必须去扫文件系统下的 snapshot 目录拼路径，则 0002 辛辛苦苦建立的 Catalog 抽象层形同虚设。
* **修改建议**：
  * 对齐 0002 模式：废弃 `<snapshot_id>` 目录层级，落盘为确定性的单标的文件或统一目录（如 `features_<minutes>m/<instrument>.parquet`）；
  * 特征版本管理通过 Parquet 文件元数据（metadata key-value）记录 `feature_version`、参数集哈希与生成时间戳，而非依赖路径多层级；
  * 显式规划在 `Catalog` 中注册 `features_5m` / `features_1h` 视图或统一检索接口。

### 缺陷 2：【致命环境阻断】强引入 C 库 `TA-Lib` 直接违背 R8 跨平台免编译承诺

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §3.3 K1（L175-185）、§7（L366）。
* **严重级**：**Critical**
* **现实陈述**：
  K1 定案：“标准指标全部来自 TA-Lib，含 `talib.SUPERTREND`……直接采用库实现”。并在审批项中列出：`pyproject.toml 加 TA-Lib 依赖`。
* **致命冲突剖析**：
  1. **直接践踏 R8 可移植性底线**：[`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L149) R8 明确写死：“**可移植：POSIX + Windows；不依赖系统包（纯 Python / pip pre-built wheels）**”。
  2. **PyPI 官方 `TA-Lib` 无通用预编译 Wheel**：Python 的 `TA-Lib` 是对底层 C 库 `ta-lib` 的 Cython 包装。在 Linux/macOS 上执行 `pip install ta-lib` 时，若宿主机未提前安装 C 库（即未通过 `apt-get install libta-lib0` 或下载源码 `./configure && make install`），pip 安装将**直接抛出 C 头文件缺失并编译失败崩溃**！在 Windows 上，官方 PyPI 同样长期不提供预编译 wheel，需要开发者手动配置 MSVC 或寻找第三方不可信 wheel。
  3. **CI 与受限开发环境直接暴毙**：Lyra 面向轻量、低配置、易分发的环境。如果 0003 强绑定 `TA-Lib` 作为 core 依赖，任何全新机器或标准沙箱（如无 root 权限环境）在执行 `pip install -e .` 时都将直接中断，彻底破坏“开箱即用”原则。
  4. **版本号表述存在事实漏洞**：文档中声称“TA-Lib 0.8.2 已内置 SUPERTREND”，然而官方 TA-Lib C 语言库长期停留在 0.4.0（近期 GitHub 推进至 0.6.4），Python TA-Lib 封装库为 0.4.x。所谓的 0.8.2 极易与第三方未经验证的 fork 混淆，依赖源极不稳定。
* **修改建议**：
  * 全面评估是否可用具备纯 Python / 纯 NumPy 实现且有 pre-built wheels 的成熟指标库，或以纯 NumPy/Numba/Pandas 实现标准指标（保持 §2.3 采纳的“NumPy in, NumPy out”纯函数边界）；
  * 若执意使用 `TA-Lib`，必须提供纯 Python 回退路径（Fallback），或者确保指标计算层具备可插拔引擎，不得使 C 编译成为安装 Lyra 的硬门槛。

### 缺陷 3：【严重概念虚妄】不变量 F2 “缺口传播闭包” 脱离数据实际，未来将掩盖真正的数据腐化

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §4 F2（L317）、§8（L377）。
* **严重级**：**Major**
* **现实陈述**：
  不变量 F2 规定：“`warm-up NULL 语义：NULL 只出现在 warm-up 前缀 或 上游合法缺失的传播（市场缺口 bar 无数据 → 依赖它的窗口特征在该 bar 及后续窗口期合法为 NULL，非 bug）；越界 NULL = bug`”。并在 v0.4 修订中自称“对抗性自检修复”。
* **现实荒谬性剖析**：
  1. **上游数据根本不存在“缺口 bar”**：在 0002 产生并在 Catalog 中注册的 `ohlcv_5m` 表中，**只存在发生交易的真实 bar**。对于周末、节假日或无成交时段，数据中根本没有插入填满 NULL 的空占位行！周五最后一根 bar 的下一行就是周日开盘 bar。
  2. **0002 已保证输入 OHLCV 零 NULL**：0002 的 DQ1 校验已强力拦截所有价格异常，输入给 0003 的行中，`mid_o, mid_h, mid_l, mid_c` **全为确定性正浮点数，完全没有 NULL**。
  3. **TA-Lib / 向量化计算绝不会在非前缀处自发产生 NULL**：将一段长度为 1000 的连续价格数组传给 TA-Lib 或 Rolling 函数，除了开头的 `warmup_bars` 必然为 NaN/NULL 之外，中间遇到周末跨度时，NumPy 依然视其为数组下标 $k$ 与 $k+1$ 连续计算，**在 warm-up 之后绝不会凭空输出任何 NULL**！
  4. **伪概念掩盖真 Bug**：除非 0003 刻意在算完特征后去比对时间戳并人工注入 NULL，否则正常计算下“缺口传播产生合法 NULL”在当前架构下是个**完全不存在的假象**！F2 建立了一个庞大的“缺失传播闭包”概念，反而为后续出现由于算法除零（如振幅为 0）产生的异常 NaN 提供了合法的“脱罪借口”，使真正的计算脏数据被误认为是“合法的缺口传播”。
* **修改建议**：
  * 戳破这层概念泡沫：由于 0002 输入表不补空行且无 NULL，特征宽表在 warm-up 前缀之后**恒定不允许出现任何 NULL**；
  * 将 F2 澄清为纯粹而严格的规则：**“对于无缺失的已存在 bar 序列，NULL 仅允许出现在前 `warmup_bars` 行；warm-up 之后出现任何 NULL/NaN 即判定为指标计算崩溃或除零 Bug（Gate 4 拦截）”**。

### 缺陷 4：【严重语义真空】R3.1 语义与结构特征缺乏数学形式化定义（算法处于真空状态）

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §3.4 标准特征清单（L286-302）。
* **严重级**：**Major**
* **现实陈述**：
  清单中列出了多达 19 个自研语义与结构特征，但对其数学公式、除零边界、极值提取规则几乎完全留白：
  * `sma_alignment_6_24 ∈ {-1, 0, 1}`：仅有两种周期的均线，何来多头/空头“排列”？若是 `sma_6 > sma_24`，浮点数几乎不可能完全相等，返回值 0 在何种阈值下触发？是否结合了价格 `close`？
  * `rsi_divergence_up / down`：技术分析中“背离”是出了名的主观与歧义概念。是峰谷点比对？是回看 24 根的斜率比对？还是简单的价格创新低而 RSI 未创新低？回看窗口是多少？
  * `path_eff_24`：路径效率（Path Efficiency）的分子分母是什么？是考夫曼效率比（净位移 / 总位移）？还是基于高低价差？
  * `rel_quote_activity`：相对报价活跃度是成交量均值比？还是点差与 ATR 的比值？
  * `prior24_range_pos`：计算公式是否为 `(close - prior24_low) / prior24_range`？当出现平价 bar 导致 `prior24_range == 0` 时，如何防御除零？
* **破坏性分析**：
  0003 在不变量 F4 中高调承诺“特征值逐位一致 (Bitwise)”，但核心计算特征连基本的数学伪代码或规范方程都未在决策文档中定稿！如果数学公式本身是模糊的，不同的开发者或不同的 AI 实现将写出完全不同的代码，所谓的“黄金测试（Golden Test）”也将沦为实现者“自己出题自己做”的无源之水。
* **修改建议**：
  * 在 §3.4 针对每一个自研语义/结构特征补齐**精确到变量名与运算符的确定性数学定义**；
  * 对涉及除法的所有特征（`path_eff`、`range_pos`、`shift6_atr`、`bar_range_atr`）显式定义分母为 0 或接近 0 时的平滑兜底规则（如 `denom == 0 -> 0.0` 或返回 NULL）。

### 缺陷 5：【严重内存失控隐患】特征计算未显式强制单标的流式迭代，面临多标的堆叠 OOM 风险

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §3.1（L126-137）。
* **严重级**：**Major**
* **现实陈述**：
  输入为 `ohlcv_5m`（全 21 标的近 1000 万行）。§3.1 仅描述“输入：ohlcv_5m / ohlcv_1h……输出：data/features/<minutes>m/<snapshot_id>/<instrument>.parquet……pandas → pyarrow 写 Parquet”。
* **破坏性分析**：
  * 0002 的经验（批次 5 与批次 7）表明：1000 万行的 DataFrame 包含 60 个 float64 列，单次完整常驻内存需要 **4.8 GB 物理内存**，加上 Pandas 计算过程中的中间 Series、副本及 PyArrow Table 转换，瞬时峰值将**轻松突破 12 GB ~ 16 GB**！
  * 0003 决策文档**并未在方案中强制规定计算流水线必须按标的逐个循环（Per-instrument loop）**。
  * 若实现代码一次性从 DuckDB 读取全量 `ohlcv_5m` 转为单一 Pandas DataFrame 进行向量化运算，在低配开发机（4GB–8GB RAM）上将必定重蹈覆辙，被操作系统的 OOM Killer 直接截杀。
* **修改建议**：
  * 在 §3.1 明确数据流控制律：**特征引擎必须在外层显式按标的遍历（`for inst in instruments:`）**；
  * 每次仅向 DuckDB 请求单标的数据（`SELECT * FROM ohlcv_5m WHERE instrument = ? ORDER BY time`），计算完成并落盘该标的 Parquet 后立即释放内存，将单次工作集严格控制在 300MB 以内。

### 缺陷 6：【轻度物理失真】不变量 F4 “逐位一致 (Bitwise)” 脱离浮点跨硬件与跨编译器物理现实

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §4 F4（L319）。
* **严重级**：**Minor**
* **现实陈述**：
  F4 声称：“计算确定性：同输入 + 同 FEATURE_VERSION + 同数值栈版本 → **特征值逐位一致（bitwise，非'逐行一致'……收紧为逐位）**”。
* **现实物理规律反驳**：
  * 在现代计算体系中，即使固定了 Python、NumPy 与 Pandas 的大版本，底层使用的数学库（如 OpenBLAS / MKL / glibc libm / MSVCRT）在不同 CPU 微架构（如 x86-64 的 AVX2 vs AVX-512 FMA 融合乘加指令，或 ARM64 NEON）下的浮点求值顺序与四舍五入均存在 1 个 ULP（Unit in the Last Place，约 $10^{-16}$）的物理扰动。
  * 浮点数加法与乘法不满足结合律：$(a + b) + c \neq a + (b + c)$。C 语言底层（包括 TA-Lib 的 `-O2/-O3` 编译优化）在不同平台生成的指令流水线截然不同。
  * 0002 的 I18 非常克制地采用了“逐行一致（值 + 行序一致，不承诺文件字节一致）”。0003 盲目收紧为“逐位一致 (Bitwise)”，将导致在 Linux 上生成的 Golden 测试基准在 Windows 或 macOS 上因最后一个二进制 bit 差异而频繁出现虚假报警。
* **修改建议**：
  * 将 F4 修正为符合数值计算规律的确定性标准：**严格定义浮点容差（如 `np.allclose(atol=1e-12, rtol=1e-12)`）**；对整数与布尔标志位要求逐位一致，对浮点特征列要求高精度一致（对齐 moneta Gate 1 门禁标准）。

### 缺陷 7：【轻度契约留白】Alpha 扩展点缺乏明确的 Python Callable 签名与运行期防护

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §3.1（L139-150）。
* **严重级**：**Minor**
* **现实陈述**：
  §3.1 规定了 `lyra.features.load_from(directory)` 扫描 `*.py` 并调用 `register(registry)`，但未规定任何 API 契约细节：
  1. `registry` 对象提供了哪些方法？（是 `registry.register_feature(name, fn, params, ...)` 吗？）
  2. 计算函数 `fn` 的入参是什么？（是接受整张输入 DataFrame？还是按名称传入特定的 NumPy 数组？返回值是一维数组还是字典？）
  3. 若 alpha 模块存在语法错误、缺少依赖包或抛出异常，加载机制如何降级？
  4. 当 alpha 特征的内部计算逻辑被作者修改，但参数名没有变化时，由于 `FEATURE_VERSION` 属于 git 追踪的核心代码常量，alpha 侧无法推进 `FEATURE_VERSION`，导致其在事实上脱离了版本控制。
* **修改建议**：
  * 补齐 `register` 接口的具体函数签名与入参契约规范；
  * 明确 Alpha 特征计算函数的数据流契约（如纯 NumPy 函数接口）；
  * 明确 Alpha 模块加载失败时的报错行为（fail-fast 阻断而非静默跳过）。

### 缺陷 8：【轻度口径矛盾】1m 粒度特征在方案叙述与 CLI 参数之间口径打架

* **涉及章节**：`docs/decisions/0003-feature-builder.md` §1（L23）、§3.1（L120）。
* **严重级**：**Minor**
* **现实陈述**：
  * 在 §1 中写道：“本 feature 解决：从 0002 产出的 **bronze / 5m / 1h** Parquet，算出 R3.1 定义的全部标准特征”；
  * 但在 §3.1 的 CLI 规范中却写道：“CLI：`lyra features [--minutes 5 60]`”。
* **逻辑矛盾剖析**：
  `bronze` 是 1-minute 粒度（1m）。如果 0003 确实需要对 1m 计算全部 60 列特征，4884 万行数据展开后特征宽表将膨胀至 **> 20 GB**；而如果 0003 明确只支持 5m 和 1h，那么 §1 中声称消费 `bronze` 就是不准确的（5m/1h 已由 0002 聚合完毕，0003 直接消费 `ohlcv_5m` 和 `ohlcv_1h`，根本无需碰 `bronze`）。
* **修改建议**：
  * 统一口径：明确 0003 仅对 `5m` 和 `1h`（或显式说明是否包含 `1m`）计算特征宽表；
  * 若仅针对 5m 与 1h，在 §1 和背景中删除对 `bronze` 的直接消费表述，明确输入基准为 0002 聚合层。

## 三、 审查结论与推进建议

0003 决策文档在参数网格化（K8）、特征清单收敛（§3.4）以及前代教训总结（§2.3）上做出了极具价值的提炼。
然而，文档目前处于“**架构设计与前序 0002 成果脱节、算法底层与跨平台基石悬空**”的状态。特别是：
1. **D1（Snapshot 体系断层）**：必须废除残余的 Nova 式层级目录，全面接入 0002 已验证的 Catalog 体系；
2. **D2（TA-Lib 依赖陷阱）**：必须化解 C 库编译与 R8 跨平台承诺的直接冲突；
3. **D4（特征数学定义真空）**：必须补齐 19 个自研特征的严密数学方程，否则代码与测试无法落地。

**判定**：**当前 0003 提案文档（v0.6）不具备直接批准并编码的条件**。建议在开发前针对上述 D1–D8 缺陷完成修订，形成 v1.0 稳定基线后再行启动代码实现。
