## I. Detailed Defect Analysis

### Defect 1: [Critical Architectural Break] Storage Path & Snapshot ID Severely Disconnected from 0002 and Catalog Architecture

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §1 (L23), §3.1 (L134-137, L154-157).
* **Severity**: **Critical**
* **The Reality in the Proposal**:
  In §3.1, 0003 proposes:
  1. Output path: `data/features/<minutes>m/<snapshot_id>/<instrument>.parquet`;
  2. Snapshot ID defined as: `A derived string of (market snapshot id, timeframe, FEATURE_VERSION, registry parameters sha256, ...)`.
* **Critical Flaws**:
  1. **Non-Existent Input `market snapshot id`**: In 0002 (formalized in Batch 7 D4), Lyra **explicitly abandoned directory-level snapshot state machines**. Market data is stored as single-file external tables: `<data_root>/ohlcv_5m/ohlcv_5m.parquet` and `<data_root>/ohlcv_1h/ohlcv_1h.parquet`. Upstream 0002 has NO `market snapshot id`! 0003 bases its derivation formula on a ghost concept.
  2. **"Always Recompute" Contradicts "Directory-Level Snapshot" Causing Disk Bloat**: §3.1 promises to follow 0002 A1's rule: "always recompute, always overwrite; no stale derived caching". However, embedding `<snapshot_id>` in the directory path means whenever `FEATURE_VERSION` or parameters change, a brand new directory is created! Old feature files (21 instruments × multiple timeframes = dozens of 300MB Parquet files) have no cleanup or rotation mechanism, permanently accumulating on disk and violating lightweight operational constraints.
  3. **Complete Absence of Catalog Integration**: 0002 established `Catalog` (DuckDB persistent external tables) as the unified interface for consumers. The feature wide tables are the foundation for 0004 compiler and 0005 trade engine, yet 0003 **completely omits Catalog integration** (no views defined, no naming scheme, no multi-instrument querying interface). If 0004 has to glob file paths under snapshot folders manually, the Catalog abstraction built in 0002 is rendered useless.
* **Recommendations**:
  * Align with 0002: drop the `<snapshot_id>` directory hierarchy and output to deterministic filenames/directories (e.g. `features_<minutes>m/<instrument>.parquet`);
  * Store feature version metadata (version number, parameter hash, generation timestamp) inside Parquet file key-value metadata, rather than path hierarchies;
  * Explicitly specify how feature tables register into `Catalog` (e.g. registering `features_5m` / `features_1h` views).

### Defect 2: [Critical Portability Blocker] Hard Dependency on C Library `TA-Lib` Violates R8 Cross-Platform Promise

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §3.3 K1 (L175-185), §7 (L366).
* **Severity**: **Critical**
* **The Reality in the Proposal**:
  K1 states: "Standard indicators all come from TA-Lib, including `talib.SUPERTREND`... adopt library implementation directly." §7 lists: `pyproject.toml add TA-Lib dependency`.
* **Critical Flaws**:
  1. **Direct Violation of R8**: [`docs/requirements.md`](file:///home/ubuntu/work/lyra/docs/requirements.md#L149) R8 explicitly mandates: "**Portable: POSIX + Windows; no system package dependencies (pure Python / pip pre-built wheels)**".
  2. **No Pre-Built Wheels on PyPI for `TA-Lib`**: Python's `TA-Lib` is a Cython wrapper around the underlying C library `ta-lib`. Running `pip install ta-lib` on Linux/macOS without system-level C libraries installed (`libta-lib0` via apt or compiling from source) **crashes immediately with compilation errors (`ta_libc.h: No such file or directory`)**! On Windows, official wheels are not provided on PyPI, requiring manual MSVC compilation or hunting for untrusted unofficial binaries.
  3. **Breakdown of CI and Zero-Setup Environments**: Lyra targets low-resource, lightweight, sandboxed developer environments. Making C-compilation a core dependency blocks standard `pip install -e .` on fresh VMs without build tools, destroying the "zero-friction installation" principle.
  4. **Factual Confusion Regarding Version 0.8.2**: The proposal claims "TA-Lib 0.8.2 has built-in SUPERTREND". The official TA-Lib C library has remained at 0.4.0 for over a decade (only recently reaching 0.6.4 on GitHub), and Python wrapper releases are numbered 0.4.x. Claiming 0.8.2 suggests confusion with an untracked fork or third-party package.
* **Recommendations**:
  * Adopt pure-Python / NumPy / Numba implementations with universal pre-built binary wheels, adhering to §2.3's "NumPy in, NumPy out" pure function boundary;
  * If `TA-Lib` is retained, it must have a pure-Python fallback path so that failing to build the C library does not prevent Lyra from installing and running.

### Defect 3: [Major False Invariant] Invariant F2 "Gap Propagation Closure" is Detached from Data Reality and Masks Real Bugs

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §4 F2 (L317), §8 (L377).
* **Severity**: **Major**
* **The Reality in the Proposal**:
  Invariant F2 states: "`warm-up NULL semantics: NULL only appears in warm-up prefix or propagation of legitimate upstream missing data (market gaps with no data → dependent window features legitimately output NULL; out-of-bounds NULL = bug)`".
* **The Reality Breakdown**:
  1. **Upstream Data Contains No "Gap Bars"**: In 0002's `ohlcv_5m` Parquet tables, **only actual trading bars exist**. For weekends, market closures, or zero-volume intervals, there are NO empty placeholder rows filled with NULL! The row immediately following Friday 17:00 is Sunday 17:00.
  2. **Input OHLCV Has 0 NULLs**: 0002's DQ1 check ensures that every single input row has valid, positive `mid_o, mid_h, mid_l, mid_c`. There are zero NULL prices in `ohlcv_5m`.
  3. **Indicators Do Not Spontaneously Generate NULL Across Gaps**: Passing a continuous array of 1000 prices to TA-Lib or rolling functions produces NaNs only for the initial `warmup_bars`. From index `warmup_bars` onward, **it never outputs NULLs across weekend jumps**.
  4. **Fictitious Concept Masks Real Division-by-Zero Bugs**: Unless 0003 explicitly inspects timestamps and manually injects NULLs, "gap-propagated NULLs" simply do not exist in the pipeline. Inventing a "gap propagation closure" creates an excuse that could mask real calculation bugs (such as unhandled division by zero on flat bars producing NaN), falsely classifying them as "legitimate gap propagation".
* **Recommendations**:
  * Eliminate the gap propagation fiction: because input data has no gap rows and zero NULLs, features after the warm-up prefix **must never contain any NULL/NaN**;
  * Clarify F2: **"For valid bar sequences, NULL is strictly permitted only in the initial `warmup_bars` rows; any NULL/NaN occurring after warm-up is classified as an indicator crash or unhandled zero-division bug (enforced by Gate 4)"**.

### Defect 4: [Major Semantic Vacuum] R3.1 Semantic & Structural Features Lack Formal Mathematical Definitions

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §3.4 Feature Table (L286-302).
* **Severity**: **Major**
* **The Reality in the Proposal**:
  The feature table lists 19 custom semantic and structural features, but completely omits their mathematical formulas, division-by-zero guards, and peak/trough algorithms:
  * `sma_alignment_6_24 ∈ {-1, 0, 1}`: Alignment requires at least three moving averages (short > medium > long). With only two periods (6 and 24), how is alignment defined? If it is simply `sma_6 > sma_24`, floating-point values are never exactly equal — under what condition does it return 0? Does it incorporate `close`?
  * `rsi_divergence_up / down`: "Divergence" is notoriously ambiguous in technical analysis. Is it peak-to-peak? Over what lookback window? Using local extrema? Or simple 24-bar slope comparison?
  * `path_eff_24`: What is the formula for path efficiency? Is it Kaufman's Efficiency Ratio (`net_displacement / sum(abs(price_deltas))`)? Or based on high-low range?
  * `rel_quote_activity`: Is it volume relative to its 24-bar moving average? Or spread relative to ATR?
  * `prior24_range_pos`: Is the formula `(close - prior24_low) / prior24_range`? If a flat bar occurs where `prior24_range == 0`, how is division-by-zero guarded?
* **Impact Analysis**:
  While F4 promises "bitwise determinism", leaving these 19 algorithms undefined means different implementations will produce completely divergent results, making the "Golden Tests" arbitrary.
* **Recommendations**:
  * Provide rigorous, unambiguous mathematical formulas for every custom semantic and structural feature in §3.4;
  * Explicitly specify zero-division edge cases (e.g. `denom == 0 -> 0.0` or NULL) for all ratio indicators (`path_eff`, `range_pos`, `shift6_atr`, `bar_range_atr`).

### Defect 5: [Major Memory Exhaustion Hazard] Pipeline Lacks Explicit Per-Instrument Iteration Constraints

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §3.1 (L126-137).
* **Severity**: **Major**
* **The Reality in the Proposal**:
  Input is `ohlcv_5m` (~10 million rows across 21 instruments). §3.1 simply outlines: "Input: ohlcv_5m / ohlcv_1h... Output: data/features/<minutes>m/<snapshot_id>/<instrument>.parquet... pandas → pyarrow write Parquet".
* **Impact Analysis**:
  * 10 million rows with 60 float64 columns requires **4.8 GB of raw RAM**. During Pandas calculations, intermediate Series, DataFrame copies, and PyArrow Table conversions easily push transient memory usage to **12 GB ~ 16 GB**!
  * The decision document **fails to mandate that feature building must iterate per-instrument**.
  * If an implementation reads the whole `ohlcv_5m` view into memory at once before grouping, machines with 4GB–8GB RAM will be killed by the Linux OOM Killer, repeating the lessons from 0002 Batch 7 D3.
* **Recommendations**:
  * Explicitly mandate in §3.1: **The feature computation loop must iterate per instrument (`for inst in instruments:`)**;
  * Each iteration queries only that instrument's data (`WHERE instrument = ? ORDER BY time`), computes features, writes the Parquet file, and drops the DataFrame, keeping peak memory under 300 MB.

### Defect 6: [Minor Physical Unreality] Invariant F4 "Bitwise Determinism" Ignores Hardware & Math Library Variations

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §4 F4 (L319).
* **Severity**: **Minor**
* **The Reality in the Proposal**:
  F4 states: "Computational determinism: Same input + same FEATURE_VERSION + same numerical stack version → **bitwise identical feature values (not just row-identical... tightened to bitwise)**".
* **Physical Reality**:
  * In modern computing, even with identical Python/NumPy versions, differences in underlying BLAS/C runtime libraries (glibc vs MSVCRT ucrt) or CPU instruction sets (AVX2 vs AVX-512 FMA) cause 1-ULP (Unit in the Last Place, $\approx 10^{-16}$) shifts due to fused multiply-add operations and operation reordering.
  * Floating point addition is non-associative: $(a + b) + c \neq a + (b + c)$. Compiler optimizations (`-O2/-O3`) in TA-Lib generate different instruction sequences across platforms.
  * 0002's I18 prudently required "row-identical (values + row order)". Tightening this to "bitwise identical" in floating-point math creates an unmaintainable constraint that will fail across different CPU architectures (x86 vs ARM64) or OSes.
* **Recommendations**:
  * Revise F4 to realistic numerical tolerance: **Bitwise identical for boolean/integer flags, and strict floating-point tolerance (e.g. `np.allclose(atol=1e-12, rtol=1e-12)`) for float columns**, aligning with moneta Gate 1.

### Defect 7: [Minor Contract Omission] Alpha Extension Point Lacks Formal Callable Signature and Sandboxing

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §3.1 (L139-150).
* **Severity**: **Minor**
* **The Reality in the Proposal**:
  §3.1 specifies `lyra.features.load_from(directory)` scanning `*.py` and calling `register(registry)`, but omits:
  1. What methods does `registry` expose?
  2. What is the callable signature of the feature function? (Does it take a DataFrame or NumPy arrays? Does it return a Series or array?)
  3. How are import errors or exceptions during alpha loading handled?
  4. If an alpha feature changes its internal code without changing parameters, how is it versioned, given that `FEATURE_VERSION` is a hardcoded constant in core git repository?
* **Recommendations**:
  * Specify the exact method signatures for `registry.register(...)` and the feature callable;
  * Define fail-fast behavior on alpha module syntax or import errors.

### Defect 8: [Minor Scope Discrepancy] 1m Resolution Feature Scope Contradicts CLI Arguments

* **Affected Sections**: `docs/decisions/0003-feature-builder.md` §1 (L23), §3.1 (L120).
* **Severity**: **Minor**
* **The Reality in the Proposal**:
  * In §1: "This feature solves: from 0002's **bronze / 5m / 1h** Parquet, calculate all standard features...";
  * In §3.1 CLI: "CLI: `lyra features [--minutes 5 60]`".
* **Contradiction**:
  `bronze` is 1-minute (1m). Calculating 60 feature columns on 48.8 million 1m rows would produce over **20 GB** of feature tables. If 0003 only supports 5m and 1h (60m), §1 should not claim to compute features from `bronze`.
* **Recommendations**:
  * Harmonize terminology: clarify that 0003 consumes 0002's aggregated layers (`ohlcv_5m` and `ohlcv_1h`), removing misleading claims of computing directly on 1m bronze.

## III. Conclusion & Roadmap Recommendations

0003 decision document makes commendable progress on parameter grid discipline (K8) and feature list pruning (§3.4).
However, it currently suffers from **architectural disconnect from 0002**, **a critical C-library portability blocker**, and **mathematical ambiguity in custom indicators**.

**Verdict**: **0003 proposal (v0.6) is NOT ready for approval or implementation**. It is recommended to address D1–D8 and produce a stabilized v1.0 baseline before commencing code development.
