# 0003 Feature Builder Adversarial Self-Review (2026-11-08, Batch 1)

> **Scope**: Review step 3 in `docs/hld.en.md` §8 against the implemented 0003 v1.3 decision and code. Inspected `lyra/features.py`, `lyra/registry.py`, `lyra/indicators.py`, `lyra/catalog.py`, the feature CLI and test sources, `docs/decisions/0003-feature-builder.en.md`, the HLD, and requirements.
>
> **Method**: Static tracing of code paths, API contracts, metadata, and test coverage. **Tests were not run in this review.** The previously reported 104 passing tests and other status are cited only as existing ACTION_LOG #65 records, not as results from this review.

## Verdict

The main computation boundary in 0003 is clear: it reads aggregated data one instrument at a time, computes in Python/NumPy/TA-Lib, carries the source columns into the feature table, and writes one Parquet per instrument. The tests and real-data E2E recorded earlier in the ACTION_LOG support that work. This review found **four high-priority defects**, two of which directly affect the local write boundary and feature artifact traceability, plus several registry, Catalog, and documentation/test-coverage gaps. **Resolve the high-priority items and rerun the relevant regression checks before signing off 0003 or moving to 0004.** This report records findings; it does not mean they have been fixed.

Priority levels: **High** means a safety boundary, declared interface, or artifact consistency can be violated; **Medium** means fixed-parameter, metadata, downstream-consumption, or regression guarantees can diverge from the settled contract.

## High-priority findings

### H1 — `instrument` is not validated before being used in an output path

- **Evidence**: `list_instruments()` reads instrument values from the aggregated data, `clean` has no path-character validation for `instrument`, and `feature_path()` interpolates the value directly into `Path(data_root) / "features" / layer / f"{instrument}.parquet"` (`lyra/features.py:775-785`).
- **Impact**: An input value containing `../`, path separators, or Windows separators can move the output outside the intended feature subdirectory, potentially beyond the data root. The data normally comes from a controlled OCI source, but the write-path boundary is not enforced in code.
- **Recommendation**: Reject path separators and `.`/`..` path components at both the data boundary and `feature_path()`, and verify before writing that the resolved target remains under the expected layer directory. Align the accepted instrument character set with the 0002 data contract.

### H2 — The published alpha compute signature differs from runtime behavior

- **Evidence**: Decision §3.1 says alpha `compute` accepts `(mid_o, mid_h, mid_l, mid_c, volume, time, *extra)` and may return a 1-D array or `{col: array}`. `compute_features()` instead always calls `spec.compute(ctx, spec)` and only accepts one `np.ndarray` with shape `(ctx.n,)` (`lyra/features.py:572-580`). The existing alpha fixture uses the runtime signature, opposite to the documented one.
- **Impact**: Alpha features written to the published contract fail at runtime. The promised multi-column return is also unsupported. R3.2 therefore has no single dependable extension API.
- **Recommendation**: Choose one interface, then align the docs, type/runtime validation, and fixtures. If `(ctx, spec) -> ndarray` is retained, define how alpha registers multiple output columns or remove that promise. If the raw-array signature and multi-column return are retained, implement the adapter and column-registration rules.

### H3 — Alpha implementation versions are absent from the Parquet version identity

- **Evidence**: Decision §3.1 says alpha semantic versions are carried in module docstring version labels. `feature_version_string()` hashes only registration names, `params`, and `warmup_bars`, then adds core `FEATURE_VERSION` and Python/NumPy versions (`lyra/features.py:584-599`). The loader neither reads nor validates alpha version labels, and the metadata contains no alpha source digest.
- **Impact**: Alpha code can change while keeping the same registration name, parameters, and warm-up, leaving the version identifier unchanged. Feature Parquets with different semantics then cannot be distinguished from the existing version metadata alone, weakening reproducibility and run provenance. OCI immutability at a path constrains remote overwrites but does not identify which implementation produced a local artifact.
- **Recommendation**: Make the alpha version a required, parsed registry field written to Parquet metadata, or include a digest of the actually loaded alpha module source in the version identity. Cover the chosen rule in docs and regression tests.

### H4 — Multi-instrument recomputation is not published atomically

- **Evidence**: `run_features()` computes and immediately overwrites each instrument's final path, with no staging/publish barrier or whole-run version check (`lyra/features.py:852-861`). Catalog views `features_5m` / `features_1h` glob every Parquet file in the directory (`lyra/catalog.py:92-119`).
- **Impact**: If computation or writing fails for one instrument, earlier files contain the new run while later files remain from the old run. The Catalog can still expose a mixed-version set; a schema change can also make the glob fail downstream. A failed command does not leave the previous complete output set intact.
- **Recommendation**: Write the full run to an isolated generation/staging location, then switch visibility only after all files pass version and schema checks; alternatively, add a manifest/publish marker and have Catalog/downstream consumers accept only one fully published, version-consistent set.

## Medium-priority findings

### M1 — Registered parameters are mutable dictionaries, bypassing the fixed-parameter rule

`FeatureSpec` is `frozen=True`, but `Registry.register()` stores a normal `dict` and exposes it through `get()`. A caller can mutate `reg.get("rsi_24").params["n"]`, and the compute closure reads that mapping, changing actual parameters without changing the registration; `window_params` can then disagree with the effective parameter (`lyra/registry.py:46-71, 109-119`). Freeze parameters deeply at registration or avoid exposing mutable internal state, and test that mutation is rejected or has no effect.

### M2 — `load_from()` loses the `self_implemented` marker when cloning core entries

The core-spec copy in `out.register(...)` does not pass `self_implemented=spec.self_implemented` (`lyra/features.py:635-645`). The standard CLI calls `load_from()` even with no alpha modules, so Heikin Ashi loses its K7 `True` marker in the registry used by the normal feature command. The current K7 test checks `build_registry()` directly and misses the loader path. Preserve the field and assert it remains set after `load_from()`.

### M3 — The version string omits timeframe, and its stack fields differ from the recorded contract

Decision §3.1 and HLD §2.2 say the version identity includes timeframe and Python/NumPy/pandas. `feature_version_string(reg)` does not accept a timeframe and only includes Python and NumPy. The same registry therefore produces the same `version_string` for 5m and 60m, although a separate `input_minutes` metadata field exists. Include timeframe in the version string, or revise the contract to state that it is carried separately; also clarify whether pandas is part of the calculation stack (the runtime feature builder does not use pandas).

### M4 — Catalog inspection hides the feature views

`upsert_feature_views()` creates `features_5m` / `features_1h`, but `Catalog.views()` filters only `_LAYERS` (bronze, ohlcv_5m, ohlcv_1h). As a result, `lyra catalog` does not show the feature views that were just created. This can mislead users using the command to check Catalog completeness. Include feature views in listing and refresh behavior and cover the CLI behavior.

### M5 — The D5 test does not verify the documented memory bound

`test_per_instrument_streaming` calls `build_instrument()` once and checks the returned row and column counts. It does not measure peak memory, exercise the full multi-instrument loop and release behavior, or assert a `<300MB` ceiling (`tests/test_features.py`, corresponding test section). The `run_features()` source visibly processes instruments in sequence and deletes `built`, but the test is not a memory regression gate for that control law. Update the test or narrow the decision document's description of what it proves.

### M6 — HLD status and output paths conflict with the current decision and implementation

- HLD §8 row 3 still says “v0.1 skeleton, reference scan in progress,” contradicting implemented 0003 v1.3 and ACTION_LOG #65.
- HLD §2.2/§3 uses `data/features/<minutes>m/...` (for example `features/5m`), while the 0003 decision and code use `data/features/ohlcv_5m/...` and `data/features/ohlcv_1h/...`.

After this review is dispositioned, sync the Chinese and English HLD versions. Use the output path approved by the 0003 contract to avoid leaving two path conventions for 0007/0004.

## Verified boundaries and limits of this review

- 0003 still consumes 5m/1h aggregate views; no feature-layer implementation of trade execution or portfolio returns was found.
- The `run_features()` control flow visibly processes instruments one at a time. The findings concern publication consistency after failure and insufficient test proof, not loading all instruments into memory at once.
- This review did not rerun the 104 tests, pyflakes, or real-data E2E listed in ACTION_LOG #65; those pass states are historical records only.
- The §5b A5 deferrals for OHLC volatility, Connors RSI, and cross-sectional features remain for user ruling. This review does not change that scope decision.

## Recommended disposition

Resolve H1–H4 first, then address M1–M6 or have the user explicitly accept their boundaries. Add regression checks for the fixes, sync the HLD and bilingual decision docs, then reconfirm 0003 sign-off. Until then, do not treat the current artifact version string as complete alpha-code provenance or consume the feature Catalog after a partially failed run.
