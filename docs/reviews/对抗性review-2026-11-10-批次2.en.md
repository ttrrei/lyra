# Independent and Adversarial Review of 0007 OCI Sync and R12 Workflow (2026-11-10, Batch 2)

> **中文**: [0007 OCI 同步与 R12 工作流独立检验 + 对抗性检验](./对抗性review-2026-11-10-批次2.md)

## Scope and conclusion

This review compared requirements R7/R12, HLD §2.5/§4/§8, OCI layout proposal B9/B11/B13/B14, the bilingual 0007 decision at rev0.4, and lyra/oci_push.py, lyra/workflow.py, lyra/cli.py, and their tests. It focused on actual sync-command paths, I17/I19/I20, archiving 0006 runs, track isolation, and multi-branch evolution. **This review records findings only; it changes no program code or design decision.**

**Conclusion: 0007 should not be signed off yet.** The command surface exists and the full test suite passes, but adversarial probes reproduced 10 P1 findings: silent no-op fine-grained pushes, a size-only false idempotent match, PAR token leakage, path escape and symlink upload, rejection of R12 branch names, non-self-contained track context, sibling-run cross-contamination, wrong or unverified push-runs artifacts, ordinary backup missing the default run root, and track indexes that cannot pass the append-only push rule. Four P2 findings concern baseline snapshots, documentation contracts, auth fallback, and partial uploads.

Severity: **P1** findings prevent core commands from working, distort research evidence or ownership, break OCI invariants, or create credential/path-safety risks; **P2** findings are persistence, compatibility, or design-contract gaps to resolve before closure.

## P1: Findings to address first

### H1 — push-strategy and push-direction report success but upload nothing

**Evidence**

- cli.py’s push_strategy() passes workspace/strategies as the plan_push root, so file paths are relative to it, e.g. fx-trend/v01.yaml.
- oci_push.in_push_scope() only permits top-level strategies, runs, data, or alpha. The fx-trend top-level is silently skipped as out of scope. A controlled probe with an existing v01.yaml produced empty uploads and empty conflicts.
- push_direction() only calls push_strategy(), so it uploads neither direction strategies nor their runs. The push-strategy docs also describe a single direction/branch, while the CLI accepts only a direction; its force_push argument is not used by this hand-written upload path.
- Existing tests do not cover either CLI command.

**Impact**: a user following the documented direction-push command gets a “successful” no-change result; strategies and runs are not persisted as promised.

**Recommendation**: keep the I17-required strategies/<direction>/... shape in planned relative paths, and implement either a single-YAML or whole-direction operation according to the command contract. Make push-direction handle canonical run paths. Add CLI tests with a fake transport that assert upload targets, conflicts, and --force-push behavior.

### H2 — Without a remote digest, equal size alone is treated as identical content

**Evidence**

- oci_push._same_object() returns True when the remote has no sha256/md5 but has the same size as the local file.
- A probe compared local b'AAAA' with remote metadata containing only size=4 and got “same object”. A different remote byte sequence of the same length would be silently skipped.
- ACTION_LOG #89 accepted that size is not proof of content and that the remote must be re-read if no verifiable digest exists. #95 added the size fallback back into push comparison, contradicting that settled rule.

**Impact**: different bytes at an I17 immutable path can be treated as an idempotent success. This directly undermines the identity guarantee for archived runs and strategies.

**Recommendation**: fail closed and read back/verify remote content when no digest is available; never skip based only on length. Add a same-size/different-content regression test and reconcile the #89/#95 rule.

### H3 — PAR URL redaction preserves the signed token in the OCI path

**Evidence**

- oci_client.redact_par_url() preserves the first two path segments. A PAR path has the form /p/<token>/n/<namespace>/..., so the second segment is the token.
- The current test puts the token only in the query string; it does not cover OCI’s path-token form.
- A controlled exception probe with /p/secret-token/... still showed secret-token in the redacted result. oci_push interpolates the original transport exception into errors; list and push-strategy also print raw exceptions.

**Impact**: network errors, logs, or CLI output can expose a writable PAR credential, violating I19.

**Recommendation**: fully redact the token segment for OCI PAR URLs and sanitize exceptions centrally instead of concatenating raw exceptions. Test path tokens, query tokens, and exceptions that include the complete URL.

### H4 — User-controlled paths can escape the workspace, and push follows external symlinks

**Evidence**

- workflow.create_track() validates track_id but not direction; direction is inserted directly into strategies/ and tracks/ paths. A probe with ../../outside successfully wrote a track record outside the workspace.
- push-runs inserts direction, track, and manifest-provided run_id directly into its staging path without rejecting absolute paths, .., or separators. A malicious or damaged manifest can direct copy targets outside the temporary staging root.
- oci_push.plan_push() treats rglob() results as files via is_file() and reads their contents; file symlinks are followed. A probe placed a symlink at alpha/features/leak.py pointing to an external secret file, and the plan included the external contents as an immutable feature upload.

**Impact**: workflow commands can write outside Lyra’s directories; push may upload credentials or arbitrary local files from outside the workspace to OCI.

**Recommendation**: validate all direction, track, run, and branch identifiers as single path components; resolve paths and assert they remain under their root; refuse symlink traversal/upload and check both copy source and destination boundaries.

### H5 — R12’s sibling-branch names cannot be created or pushed

**Evidence**

- requirements R12 and oci-alpha-layout explicitly use v02a.yaml, v02b.yaml, v03a.yaml, and v04ab.yaml for same-generation candidates and cross branches. Deriving multiple candidates from one diagnosis is a core workflow.
- workflow._BRANCH_NAME_RE and oci_push._VNN_RE accept only v<digits> with no suffix. A probe calling new_version(..., branch="v02a") raised WorkflowError; a hand-written v02a.yaml is classified as unclassified by I17.
- #95 tightened generated names to vNN to make tool-generated YAML pushable, fixing the generated-file classification mismatch while creating a conflict with R12’s version-tree examples.

**Impact**: standard sibling and cross names are rejected, so AI cannot represent multiple evolution paths from the same parent as specified; even a manually written file cannot be synced.

**Recommendation**: extend branch parsing, new-version validation, and I17 classification together to the defined generation + branch-suffix + cross-suffix rules. Test creation, compilation, push, and duplicate detection for v02a/v02b/v04ab.

### H6 — Track context is neither self-contained nor isolated from other tracks’ lessons

**Evidence**

- R12/0007 D5 require each track to own its hypothesis snapshot reference, lessons, candidates, and run attribution. Requirements also require context to include the hypothesis, complete active-branch YAML, and feature list.
- render_context(track=...) still reads shared strategies/<direction>/lessons.md; it prints only the hypothesis path/hash rather than frozen content; it lists active filenames/parents but not YAML bodies and has no feature list.
- A probe selecting track alpha saw another track’s lesson, while sma_20_above_sma_50 from v01.yaml was absent from the context.
- Code writes each track’s new candidates in the direction root rather than proposal’s tracks/<track_id>/; the track record stores only the hypothesis hash, while context reads the mutable current hypothesis file.

**Impact**: an AI cannot work from the context file alone; it lacks strategy parameters and may read another AI’s research conclusions or a changed hypothesis. This breaks the core “independent pace, no interference” requirement.

**Recommendation**: implement per-track lessons/candidates/run provenance. Put the track’s fixed hypothesis content or a verifiable immutable snapshot, full active YAMLs, feature list, and this track’s sibling-run comparison into context. Shared rules and frozen market data can reference common snapshots.

### H7 — Sibling run summaries can match the wrong version, cross directions, and report one instrument only

**Evidence**

- workflow._runs_for_branch() accepts direction but never uses it; it scans the whole runs root and does not filter track ownership.
- Its fallback is branch in spec; a probe showed a request for v1 matching spec_id=v10.
- When metrics.json contains multiple per_instrument entries, the code takes only next(iter(per.values())). A probe with EURUSD=1 trade and GBPUSD=99 trades returned only one instrument.
- Therefore compare_siblings() “best” rows are built from summaries that may already be cross-contaminated or incomplete.

**Impact**: continue/prune/cross decisions can be based on the wrong branch, direction, or one arbitrary instrument; reports and AI search ordering are unreliable.

**Recommendation**: require verifiable direction, track_id, strategy path/hash, and run_id provenance. Match branch identity exactly. Preserve all per-instrument R5 metrics; do not select only the first JSON entry.

### H8 — push-runs can select an old run and permanently archive unverified or unattributed files

**Evidence**

- push_runs() sorts all manifests under one runs/<name>/ and uses only the first. 0006 now scopes directories by date/run_id, but the command has no date or run_id argument, so it cannot select a requested run when there are several.
- It only compares direction when the manifest contains it; it does not check manifest.run_id against its parent directory, validate the required artifacts, or verify their SHA256 values. It copies every file beside the manifest.
- Existing test_push_runs_maps_to_direction_track_runid deliberately uses empty artifacts and a fake b'PAR1' trades.parquet, yet asserts push success.
- --track is inserted only into the OCI directory path. The original manifest is copied unchanged, so the archived run itself does not declare its track as D5 requires.

**Impact**: the wrong run or a locally corrupted artifact can be permanently uploaded as immutable content; the manifest cannot independently prove the track ownership encoded by the OCI path.

**Recommendation**: select an exact run_id; validate manifest schema/path consistency, required artifacts, and each SHA256 before uploading. Write track provenance into an auditable manifest/sidecar. Test missing, modified, misplaced, and multiple candidate runs.

### H9 — Normal backup misses Lyra’s default run output and does not map the canonical OCI path

**Evidence**

- runner defaults artifacts to ~/.lyra/runs; _push_all_roots() scans only the workspace parent of resolve_data_root(...), and does not add the default ~/.lyra/runs root.
- Even if runs are colocated in the workspace, ordinary push/backup preserves runs/<name>/<date>/<run_id>. Only the separate push-runs command maps to runs/<direction>/<track>/<run_id>.
- push_direction() is documented to push strategy and run slices but actually calls only push_strategy().

**Impact**: the ordinary one-shot backup may omit the run just completed; any run it does find can be stored under the wrong OCI path, violating O2/D7. Users must manually call a command that can select the wrong run.

**Recommendation**: make backup/push use the same per-run manifest validation and canonical path mapping as push-runs, and include Lyra’s default runs root. Either implement push-direction’s run contract or remove it from the docs.

### H10 — Mutable track indexes are classified append-only, so their first update fails I17

**Evidence**

- strategies/<direction>/index/*.json is classified as append-only by I17.
- create_track() creates active=[]; new_version() changes active to [v02] and rewrites the JSON. A probe passed the initial index and the index after adding one branch to is_append_only_superset(); it returned False.
- prune_branch() removes an entry from active and adds it to pruned; the old JSON lines are no longer an ordered subsequence of the new JSON, so that update cannot be pushed either.

**Impact**: the first fork or prune after track creation is rejected by the append-only gate; local AI branches cannot be reliably synchronized, and after hitting the cap a prune cannot be synced to allow continued iteration.

**Recommendation**: make the index a genuinely append-only event log (create/activate/prune events), or design a reviewed version/conflict protocol for mutable snapshots. Do not bypass I17 by merely weakening the line comparison.

## P2: Design and documentation gaps to resolve before 0007 closure

### M1 — The “frozen baseline” has no real catalog/data snapshot and is not persisted to OCI

workflow._baseline_for_direction() searches for data/features/catalog.json, while Lyra actually uses data/catalog.duckdb (catalog.json is fabricated only by workflow tests). In a normal workspace feature_catalog_sha256 is therefore None; the code also records no data snapshot id. The track record is stored under workspace/tracks/, whose top-level directory the push walker deliberately skips. OCI receives the strategy index but not the frozen baseline record. A track restored in another workspace therefore cannot reconstruct the original snapshot identity.

**Recommendation**: capture stable identity through the actual catalog/feature-snapshot API, record data snapshot, rule version, and hypothesis snapshot in syncable append-only track metadata. Use a real catalog fixture and test restoring a track in a second workspace.

### M2 — The backup contract conflicts, and the 0007 decision status is stale

HLD §2.5 defines lyra backup as pull + push + conflict detection; 0007 D10 and the implementation define backup as push-only. requirements R7 says one-key sync when local strategies/runs change. The implementation choice may be valid, but no HLD revision resolves the conflict. Also, the 0007 metadata still says “Proposal” and §7 approval boxes remain unchecked, while rev0.4 and ACTION_LOG say implemented/full tests passed.

**Recommendation**: decide whether backup means push-only or pull+push, then align HLD, requirements, and both 0007 documents. Separate “code review passed” from “R10 real-bucket acceptance pending” in implementation status, approval items, and acceptance criteria.

### M3 — OCI SDK auth fallback is documented but the program only has an unauthenticated requests session

0007 D4/Appendix C1 and HLD §2.5 say auth_file / OCI SDK can be used. cli._push_transport() only creates requests.Session and passes PAR URLs to GET/PUT; it does not read auth_file or create an SDK signer. For a read-only PAR, the error “use SDK auth” does not provide a working fallback. Real-bucket R10 has not been verified.

**Recommendation**: implement and cover the auth_file path, or explicitly remove that capability from this release and document supported behavior with read-only PARs. Then complete R10 real-bucket read/write acceptance.

### M4 — Multi-file push is not atomic, and rollback docs overstate failure behavior

oci_push.push() PUTs files one at a time; each file is fully loaded with read_bytes(), and a later PUT failure only raises an error—it does not roll back earlier objects. Sorted paths can upload manifest.json before the other run artifacts, so the remote may temporarily show a run with a published manifest and missing files. 0007 §6 says unsuccessful uploads will not leave a partial state. Loading large Parquet files fully also creates memory peaks.

**Recommendation**: at minimum publish the manifest last and specify the partial-upload/retry recovery protocol. If atomic publication is promised, use staging/commit marker or an equivalent mechanism. Use chunked or streamed upload; do not describe per-object PUTs as a transaction.

## Verification and adversarial self-check

- Focused 0007 suite: .venv/bin/python -m pytest -q tests/test_oci_push.py tests/test_workflow.py → **59 passed**.
- Full repository suite: .venv/bin/python -m pytest -q → **287 passed**.
- Static check: .venv/bin/python -m pyflakes lyra tests → no output.
- Controlled probes reproduced: empty fine-grained strategy plan; same-size/no-digest treated as identical; visible PAR path token; direction traversal writing outside the workspace; external symlink included in upload plan; track context sharing lessons and omitting YAML bodies; v1 matching v10 and summary containing only one instrument; initial branch-index update and prune failing append-only; v02a rejected.
- test_push_runs_maps... uses empty artifacts and a fabricated trades Parquet fixture, corroborating that push-runs does not validate manifest contents.
- The adversarial re-check asked whether “all 287 tests pass” disproves these findings. It does not: the paths above are not asserted, and multiple test fixtures explicitly permit incomplete runs. **R10 real OCI bucket end-to-end acceptance was not performed**, so mock PUT is not presented as real read/write acceptance.

## Recommended disposition order

Address H1–H4 first (silent failure, content identity, credentials, and path safety); then H5–H8 and H10 (restore multi-branch AI search, correct comparisons, verifiable run archiving, and index sync); make H9’s default backup include 0006 runs. Resolve M1–M4 before deciding whether 0007 satisfies R7/R12 and can proceed to final R10 acceptance.

This review fixes none of the findings and did not connect to real OCI. Acceptance/held/rejected dispositions should be recorded item by item in a later disposition turn; this report itself is not 0007 sign-off.
