# 0005 Trade Engine Adversarial Review (2026-11-08 Batch 3)

> **Scope**: Review the 0005 trade engine under stage 5 of `docs/hld.en.md` §8, focusing on financing day count, timestamp handling, tests, and the 0005 decision document. The main check is whether the settled R4/O15 meaning of “trading days” is silently replaced by calendar days in implementation or tests.
>
> **Method**: Statically traced `lyra/trade_engine.py` and `tests/test_trade_engine.py`; constructed minimal inputs spanning a weekend, different timeframes, and incompatible timezone awareness; ran the focused 0005 tests and the full repository suite. This review records findings only; implementation and tests are unchanged.

## Conclusion

The existing tests for the rest of 0005 still pass, but this review reproduced **one high-priority contract violation** and **two medium-priority risks**. Most critically, financing is calculated from physical seconds between two timestamps divided by 86400. The engine neither excludes weekends nor has a market calendar to exclude holidays. This directly contradicts requirements R4 and closed question O15. The current financing test covers only three hours and expects the natural-time fraction, so it lets the wrong convention pass. Agreement with nova also does not prove compliance with Lyra’s contract because both use the same calendar-day algorithm.

Priority: **High** means a violation of settled Lyra trading semantics that can change net returns or strategy ranking; **Medium** means an input boundary can silently change financing, or a proposed substitute introduces timeframe dependence.

## High-priority finding

### H1 — Financing uses calendar days, violating the R4/O15 trading-day rule

- **Evidence**: `lyra/trade_engine.py:108-113` calculates days as `(exit_time - entry_time).total_seconds() / 86400`, then multiplies by `financing_bps_per_day`. This uses only physical elapsed time: it does not read a trading calendar or identify weekends and market holidays. Requirements R4 (`docs/requirements.en.md:163-166`) and closed O15 (`docs/open-questions.en.md:27`) explicitly require counting trading days in the holding interval and excluding weekends and market holidays.
- **Reproduced difference**: A synthetic position enters at 2026-10-30 (Friday) 00:00 UTC and exits at 2026-11-06 (Friday) 00:00 UTC: seven calendar days elapse; there are five weekdays in `[entry, exit)`, with weekends excluded. At `financing_bps_per_day=100`, the current code returns `cost_return=0.07`; the trading-day result should be `0.05` (assuming no market holiday in that interval). A holding interval containing a market holiday cannot be handled by the current formula either.
- **Test gap**: `test_cost_financing_proportional` (`tests/test_trade_engine.py:259-277`) covers only three hours and asserts a cost based on `3/24` of a physical day. It has no weekend or holiday case. It tests and locks in the wrong convention rather than R4/O15.
- **Oracle misuse risk**: The previous 300-case / 381-trade cross-check against nova proved that Lyra reproduces nova’s calendar-day behavior. It does not prove compliance with Lyra’s R4/O15. The decision document already records the conflict between those conventions; predecessor parity cannot supersede Lyra’s explicit requirement.
- **Impact**: Positions held over weekends incur extra financing charges. For longer-holding strategies, this can change costs, net returns, annual scores, and strategy rankings. Leaving O17 as a user choice between calendar and trading days obscures an existing ruling: O15 is closed and already selects trading days. Unless the user explicitly overturns O15, R4/O15 should govern.

**Recommendation**: Define the date-boundary rule (how entry and exit dates count), and make financing consume auditable trading-day/market-calendar information or a trading-day count computed upstream under the same rule. Add tests for weekend spans, market holidays, sub-day holds, and exact day boundaries. Mark financing-only differences against nova as expected contract-priority differences instead of treating whole-field parity as the acceptance criterion.

## Medium-priority findings

### M1 — `bars_held` is not a trading-day count and cannot directly replace calendar elapsed time

The 0005 decision document §5 suggests approximating financing days from the number of held bars, or letting 0006 recompute financing from `bars_held`. But `bars_held` counts bars, not trading days. For the same 24-hour position, a probe returned `bars_held=24` on 60m bars and `bars_held=288` on 5m bars. If used directly as a day count at 100 bps/day, those values imply 24% and 288% financing; the current elapsed-time formula returns 1% for both. Normalizing by timeframe/session length still requires explicit market-session, weekend/holiday, and partial-session rules; `bars_held` alone is insufficient.

**Recommendation**: Do not use a raw bar count as days. If 0006 owns the cost calculation, pass it a reproducible trading-day count or calendar result consistent with R4/O15. Verify that the same 24-hour hold has identical financing from 5m and 60m inputs.

### M2 — A failed timestamp subtraction silently sets financing to zero

`_finish()` catches `AttributeError` / `TypeError` and sets `days=0.0` (`lyra/trade_engine.py:109-112`). In a minimal reproduction, the entry time was a naive `datetime` and the exit time was a UTC-aware `datetime`. Subtraction raised `TypeError`, which was caught; the trade was still emitted, but financing at 100 bps/day became `0.0`. Unexpected time types whose difference lacks `total_seconds()` take the same silent path.

**Impact**: Bad timezone or time-type input is disguised as zero financing. The simulation does not fail or emit a diagnostic, so the resulting trade report can appear valid.

**Recommendation**: Validate consistent time type, timezone, and ordering at the input boundary. If financing duration cannot be computed, raise an error with field context instead of continuing with zero cost. Add rejection tests for mixed naive/aware timestamps and unsupported time types.

- This review did not rerun the 300-case nova cross-check, pyflakes, a real-market runner, or OCI flows. Their historical results remain prior ACTION_LOG records, not results from this review.

## Adversarial self-check: avoid overstatement

1. This is not merely a difference from the predecessor: R4/O15’s trading-day meaning is an explicit Lyra rule, and O15 is closed.
2. The weekend example counts the starting Friday and excludes the following Friday at the exit instant under `[entry, exit)`. If the project chooses another day-boundary convention, it must be specified first; either way, seven calendar days cannot be equated directly with trading days when weekends are excluded.
3. This review did not use a real market-holiday calendar to calculate a specific market’s holiday count. However, the current formula receives and consults no holiday calendar, so its inability to exclude market holidays is statically established.
4. The cross-timeframe `bars_held` probe proves only that a raw bar count has no day unit. A design normalized by timeframe and session length may be possible, but it still needs explicit calendar semantics.
5. The full suite can pass while the financing contract is violated; this review does not misreport passing tests as an implementation regression.

## Recommended disposition

First fix the R4/O15 trading-day count and boundary rule, then add weekend/holiday and cross-timeframe regressions; invalid timestamps should fail closed. If the intent is to retain nova’s calendar-day algorithm, the user must explicitly add a decision superseding R4/O15 rather than treating closed O15 as still awaiting a choice. This report contains no implementation change. 0005 should not be considered fully compliant with Lyra’s cost semantics until the financing convention matches the contract.
