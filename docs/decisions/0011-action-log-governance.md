## 1. 问题

中央日志已经没法被人或 AI 一次读完：它记的不是"做了什么"，而是每次开发的完整过程，而且状态区会过时。需要让日志重新变成一条简短的、可信的时间线。

## 2. 背景

- 规模：旧 `ACTION_LOG.md` 251 行、约 157K 字符，`ACTION_LOG.en.md` 262 行、约 261K 字符，大量内容是单行超长段落（#132、#133 各数千字：需求背景、逐条审查意见、回归测试清单、E2E 过程）。弱模型和人都无法在一次读取里消化。
- 两套账：#1–#83 在 `## 2026-11-05 / 11-06` 的日期表里，#84–#133 全部追加在末尾的 `## 修订记录` 表里（列为 日期 / 版本 / 变更 / 落点）；版本列不单调，例如 #133（1.80）排在 #132（1.79）之前。
- 状态区过时：`## 当前状态` 里同时有 `更新于` 和 `更新于（前）` 两行（各数千字重复描述 #129–#133），并且仍写着"待 `git push`、`origin/main = 526f2ea`"，而 GitHub main 已前进。
- 现行规则（`AGENTS.md`）要求"每个 working turn 都必须记一行并刷新状态块"，这直接导致日志为满足规则而膨胀。

## 3. 方案

### 3.1 做什么

1. 旧日志整体冻结为归档：`git mv` 为 `docs/ACTION_LOG.archive.md` / `docs/ACTION_LOG.archive.en.md`，只加一段归档横幅并修正首部互链，内容不动。
2. 新的 `docs/ACTION_LOG.md` / `.en.md` 只含三部分：简短的维护规则、不超过 10 行的当前状态、#134 起的一张条目表（`# | 日期 | 类别 | 内容 | 落点`）。
3. 改写 `AGENTS.md` 中的日志规则（Where we are、Documentation conventions、Non-negotiables、Working style、References）：
   - 只有实际变更或重要决策 / 审查结论才记；纯讨论、排查而无变更不记；
   - 每条 2–4 句，详情放 `docs/decisions/`、`docs/review/` 或 commit；
   - 当前状态是"现在的状态"，原地覆盖，不写历史；
   - 中英文信息一致即可，不要求逐字翻译；
   - 查旧编号时到归档里搜索，不整份加载。

### 3.2 不做什么

- 不改写、不压缩、不删除旧历史，也不重新编号。
- 不自动生成旧账的索引：旧日志有两套表格格式，无法可靠地机器解析。
- 不改任何代码；不改其他文档（它们对 `#N` 的引用保持有效，编号都在归档里）。

### 3.3 边界

- 归档冻结后不再修改；新条目只写在新日志里，编号从 #134 接续。
- 新日志里的条目不能重新长成开发报告：超过约 600 字说明详情放错了位置。

## 4. 不变量

- 日志只增不删；被推翻的条目追加"推翻 #N"。
- 编号单调递增且不重复（#134 起，接续归档的 #133）。
- `ACTION_LOG.md` 与 `.en.md`、归档的 `.md` 与 `.en.md` 始终成对存在，信息一致。
- `## 当前状态` 不超过 10 行，只描述当前状态。

## 5. 测试

没有代码改动，检查项如下：

- 新日志与归档四个文件都存在，相对链接可解析。
- `grep -n "#113" docs/ACTION_LOG.archive.md` 能命中旧条目。
- `bash scripts/alpha_gate.sh`、`python -m pyflakes lyra tests`、`python -m pytest -q` 不受影响。

## 6. 回滚

`git revert` 该提交即可恢复原文件；归档是用 `git mv` 得到的，旧日志的历史没有丢。
