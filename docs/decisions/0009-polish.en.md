## 0. Background and scope

0009 is the second-to-last stage of HLD §8's build order. It has two parts:

1. **Closeout of the overall-design review parked findings** (#109 disposition):
   - R1 — track context renders all tracks merged; hypothesis "freezing" is only a SHA256 (no content snapshot)
   - R2 — `lyra run` defaults to `~/.lyra/runs` while the workflow scans `<workspace>/runs`; official v01 `spec_id`s match no branch; `compare` silently mixes runs across data generations
   - R7 — feature wide tables are overwritten per instrument, no staging/atomic publish; the catalog does not check generation consistency
   - R8 — `_counter_fingerprint` probes only 2 fixed points; distinct counters can share a fingerprint
   - R9 — `feature_catalog_snapshot` is a name list, not a data identity
2. **R12 deliverables**: README rewrite against the real CLI, single lockfile + Python version policy, CI, `lyra-doctor`.

**Out of scope** (explicitly not done): 0010 temp/ triage (next stage); new features/indicators; concurrency/scheduling (R9 out-of-scope preserved); re-opening any settled user ruling.

## 2. Key design notes

### 2.1 D2 runs-dir unification boundary

- Only the **default** and the **identity sidecar** change; explicit `--out` behavior and every landed legacy run are untouched.
- `push-runs` keeps a one-version compatibility scan of `~/.lyra/runs` (`LYRA_RUNS_ROOT` env var + old default) so existing artifacts don't go orphaned; removable from 0010.
- `run_meta.json` is written by the CLI layer (it knows config→workspace→direction/branch context); the runner core stays workspace-agnostic.

### 2.2 D3 comparability rule

- Comparable = same `data_digest` **and** same `feature_version`. Different directions are naturally comparable (same data); same direction with different parameters is comparable too — the only difference is the strategy itself, which is exactly what compare is for.
- `compare` stays read-only; "incomparable" is a label, not a blocker (humans can judge).

### 2.3 D4 atomic publish semantics

- The staging dir lives on the same filesystem as the target (under the same `data_root`), so `Path.rename` is an atomic move.
- Failure mid-run: the next `run_features` start cleans the staging residue; the target dir keeps the last complete generation — **never half-new-half-old**.
- `_generation.json` is the trust anchor for `lyra-doctor` (D10 ④) and the 0010 triage.

### 2.4 D6 relation to the existing run_id

- `data_digest` (already in 0006, covers consumed columns) is kept; `feature_snapshot_digest` covers the **entire feature layer** (all instrument files); they complement each other: the former guarantees "data I used changed ⇒ run_id changed", the latter "the whole data layer is a new generation ⇒ run_id changed".
- `feature_version_string` already fingerprints registry/alpha/pandas/numpy; D6 adds only the **data-file** dimension.

## 3a. Self-check / adversarial review record

Design self-check (v0.1→0.2) corrected 4 points: D8 single lock source; D9 TA-Lib C-library CI prerequisite; D10 two severity levels; D6 snapshot digest derived from the generation manifest (no big-table re-hash).

**Adversarial review findings (v0.2→0.3, all fixed)**:
1. **(P1, fixed) lock incompatible with CI 3.11**: `requirements.lock` was generated from a local **Python 3.12** venv, where **numpy 2.5.4 ships cp312 wheels only (cp311=0, sdist-only)**; a CI matrix that includes 3.11 fails to install numpy (or falls back to a C build). → **support pinned to 3.12**: `pyproject` `>=3.12,<3.13`, CI matrix reduced to a single **py3.12** (aligned with the lock). The design self-check had only probed pandas/duckdb/ta-lib wheels, missing numpy.
2. **(P3, fixed) D4 stale files**: after atomic publication, an instrument dropped from the dataset left its parquet in the view dir. → `run_features` prunes non-current `.parquet` files (by the `instruments` whitelist) so `validate_generation`'s whitelist stays exact (no false-positive stale). Regression test added.
3. **(P3, fixed) doctor compile smoke depended on cwd**: `_default_example_strategy` located the example YAML by the **package install location** (not the project root), so it was missing when run from an install/CI. → now probes up to the project root's `strategies/examples/` from the `lyra` package location, with a built-in minimal RSI fallback, so the compile smoke is stable from any working directory.
4. **(P3, fixed) doctor opened the catalog twice**: the compile-smoke branch called `Catalog(cat_file)` again. → reuses the already-open `cat` handle.
5. **(P3, fixed) D3 `distinct_feature_generations` semantics**: was `len(set(ids))` (counting `None`), misleading when only some runs carry an identity. → now counts distinct **non-empty** feature_snapshot_ids; runs lacking identity are reported separately via `runs_without_data_identity`.
6. **(P2, fixed) D2 `run_meta` identity match**: the run_meta branch of `_runs_for_branch` only required the branch to match, so a **different direction's** run could be counted here. → added a `direction`-equality guard (the spec_id fallback branch keeps its H7 exact-`spec_id` constraint).
7. **(P2, fixed) D2 push-runs identity**: was branch-only. → now also checks `direction`; legacy manifests with `direction=None` remain compatible (backwards-compatible).
8. **(P2, fixed) `lyra run` default out**: the design said `<workspace>/runs`, but `runner._default_out` still pointed at `~/.lyra/<ws>/runs` (a different root). → the CLI `run` default out is now explicitly `<workspace>/runs` (0007 D7 tree); the runner-internal default keeps the old value for library callers.
9. **(P2, fixed) `branch` source in run_meta**: was the strategy `id` (e.g. `directions_momentum_exhaustion`) instead of `v01`. → the CLI derives the branch from the **file name** (`vNN[_variant]`), with `--track` supplying track identity, matching workflow branch semantics.
10. **(P3, fixed) "3.11–3.12" wording in README/HLD/requirements**: aligned to the 3.12 single-point along with #1.

All fixes are regression-verified (see the test plan); no outstanding P1/P2.

## 5. D12 / D13 — track-level candidate layout and per-run comparability (11-12 batch-1 H1/H2, user ruling 2026-11-13 "do it now", **landed in #112**: pytest 333 passed + 9 adversarial probes green + full CLI end-to-end verified)

### D12. Candidate files belong to a track (H1)

**Layout**:
```
strategies/<direction>/
├── hypothesis.md                  ← direction-level shared (read-only baseline; frozen into each track's baseline)
├── lessons.md                     ← direction-level shared lessons
├── v01.yaml                       ← direction-level baseline (legacy read-only; shared starting point)
├── index/t<track>.jsonl           ← track event log (unchanged)
├── <track_a>/v02a.yaml            ← track-owned (new layer, H1)
├── <track_a>/v03.yaml
└── <track_b>/v02a.yaml            ← coexists with track_a's v02a (the H1 core)
```

**Rules**:
1. **Direction-level vNN.yaml = shared baseline, read-only semantics**: `new_version`/`merge` no longer write direction-level; direction-level files remain readable (as parent / baseline) and pushable. The existing 12 directions' `v01.yaml` stay in place (zero migration: `~/.lyra/default` has an empty tracks dir, no track data).
2. **Duplicate check becomes track-scoped**: `new_version`'s "branch exists" check now rejects only if it exists **inside this track's directory**; same-named branches across tracks are legal (`strategies/<direction>/<track>/v02a.yaml` no longer conflicts).
3. **`_branch_file` resolution**: prefer `<track>/<branch>.yaml`, fall back to direction-level (baseline); `--from` parent likewise (the direction-level baseline is always a valid parent).
4. **Runs isolation**: `_runs_for_branch` gains a `track` parameter — matches `run_meta.track_id` (without the parameter the old behavior is preserved, for `synthesize` to read cross-track with labelled provenance). `context --track` lists only this track's runs (the H1 core requirement).
5. **merge**: target file written into this track's directory; the auto-name (next free vNN) computes the free number over **this track + direction-level** sets.
6. **OCI compatibility**: `classify_path` classifies by file name (`_VNN_RE` on the last segment), so `strategies/<dir>/<track>/vNN.yaml` is still immutable — **no oci_push change needed** (verified).
7. **cap/event log**: unchanged (already track-level).

### D13. compare per-run identity criteria (H2)

1. **Identity fields**: `metrics.json` and `manifest.json` gain `data_digest` (already computed by the runner, previously only in the run_id payload) and `feature_version` (already in the manifest). `run_meta.json` unchanged (identity=attribution; data identity lives in metrics).
2. **Judgment**: `compare_siblings` decides `comparable` over the compared run set = all runs share the same `data_digest` **and** `feature_version` **and** `feature_snapshot_digest` (the existing 0009 D3 dimension kept as the third). Any run missing a field (legacy) → `comparable=None` (unknown, not presumed comparable) + listed in `runs_without_data_identity`; fields present but differing → `False` + per-run `incomparable_reason` (`data_digest`/`feature_version`/`feature_snapshot`).
3. **Per-run output**: each run row carries `data_digest` / `feature_version` / `comparable`, so an AI can see *why* one run is not comparable with another.
4. **synthesize**: cross-track synthesis explicitly lists track provenance + per-run identity fields (I22 explicit entry, not implicit mixing).

### Test plan (new)
- H1: two tracks each `new_version v02` succeed (direction-level exclusivity lifted); `context --track` does not read the other track's runs; `--from` pointing at the direction-level baseline works; OCI classification still immutable for the track subdir.
- H2: two runs with same snapshot but different data_digest → `comparable=False` + reason; a legacy run missing data_digest → `comparable=None`; all three fields equal → `True`; metrics.json/manifest.json carry both fields.
- Regression: existing track-semantics tests (`test_cap_is_per_track_not_global` etc.) stay green (the layout only adds a subdirectory layer and does not change existing assertion paths).
